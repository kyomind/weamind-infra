## Q1

### 題目

如果只用一句話先區分 `kubectl describe pod`、`kubectl logs`、`kubectl logs --previous`、`kubectl exec -it`，你會怎麼描述它們各自最適合看的東西？請不要只背指令名稱，而是直接說「它比較像在拿哪種證據」。

### 對照檔案

- `manifests/deployment.yaml`
- `PROGRESS.md`

### 使用者回答摘要

- 使用者對四個工具已有初步直覺，但目前還在用較口語、較模糊的方式理解它們。
- 對 describe，使用者目前理解為「描述元件細節」，能抓到它是在看 Pod 等資源的狀態與資訊，但還不確定 describe 後面是否只能接單數資源，或能否用複數與未指定單一名稱的形式。
- 對 logs，使用者能把它類比成 docker logs，並判斷它主要是在看 Pod 內 container 的標準輸出與標準錯誤內容。
- 對 logs --previous，使用者目前還不確定它補的是哪一種額外資訊。
- 對 exec -it，使用者能正確抓到它比較像進到 Pod 內的 container 做互動式操作，並把它類比成較接近容器內部操作的入口。

### AI 修正與補充

- 主方向是對的，而且你已經抓到今天最重要的骨架：這四個工具不是都在回答同一個問題，它們是在拿不同種類的證據。
- 第一，describe 可以先收斂成這句：它比較像在看 Kubernetes 怎麼看這個資源。以 Pod 來說，高價值資訊通常是排程結果、狀態條件、container state、重啟次數和 events。也就是說，它比較偏叢集控制面與資源狀態的觀點，不是 app 自己的觀點。
- 你剛剛提到的單數、複數問題，也是一個好觀察。更準確地說，describe 後面接的是資源型別，單數或複數通常都可以，例如 pod 或 pods；而且若你只寫資源型別，也可以列出該 namespace 內多個同類資源的描述。真正的核心不是單複數，而是你有沒有把目標資源指定清楚。
- 第二，logs 你抓得很接近完整答案了。它可以先收斂成這句：logs 比較像在看 container 或 app 自己吐出的執行期訊息。像 Python exception、啟動過程、收到 webhook 後的請求紀錄，通常比較會在這裡看到。
- 第三，logs --previous 可以先收斂成這句：它是在看上一個已經死掉的 container 留下的最後訊息。這對反覆重啟的 Pod 很重要，因為一般 logs 看到的可能是現在這次啟動的內容，但你真正想找的錯，可能發生在上一輪剛掛掉之前。
- 第四，exec -it 你的理解也對。它可以先收斂成這句：exec -it 比較像進到 container 內做最小驗證，例如看環境變數、DNS 解析、HTTP 請求、TCP 連線或檔案是否存在。它提供的是 Pod 內視角，不是 Kubernetes 事件視角，也不是外部流量路徑的全貌。
- 第五，若要把四個工具壓成最小可講版，可以這樣說：describe 看 Kubernetes 對資源的觀察；logs 看 app / container 自己輸出的訊息；logs --previous 看上一個已死亡 container 的最後訊息；exec -it 則是進到 container 內做最小互動式驗證。
- 第六，今天這題真正重要的不是把定義背熟，而是開始建立一個直覺：當你想知道 Pod 為什麼排不起來、被重啟幾次、events 在說什麼時，先想到 describe；當你想知道 app 自己噴了什麼錯時，先想到 logs；當你懷疑它上一輪啟動時就死掉，想到 logs --previous；當你想從 Pod 內部驗證環境與連線，才想到 exec。

## Q2

### 題目

如果今天看到 Pending、ImagePullBackOff、CreateContainerError、CrashLoopBackOff，這四種狀態在第一輪通常比較適合先開哪一種 kubectl 工具？這裡的「工具」是指今天這四個：`kubectl describe pod`、`kubectl logs`、`kubectl logs --previous`、`kubectl exec -it`，不是在問你要先看哪份 YAML 或文件。請不要追求唯一正解，而是說明你為什麼先選那個工具，以及你期待先拿到什麼證據。

### 對照檔案

- `manifests/deployment.yaml`
- `README.md`
- `PROGRESS.md`

### 使用者回答摘要

- 使用者對 Q2 的整體方向已有初步判斷，但目前最卡的不是「要選哪個工具」，而是「選了這個工具之後，應該期待看到哪一類證據」。
- 對 Pending，使用者會先選 `kubectl describe pod`，並直覺認為高價值資訊可能在 Pod 的 events，但目前還不夠確定 describe 的輸出裡，哪些訊息才是真正能指出 Pending 原因的關鍵。
- 對 ImagePullBackOff，使用者也傾向先選 `kubectl describe pod`，理由是 container 還沒有真正成功啟動，因此目前比較像應先看 Pod 狀態與 Kubernetes 對這個 Pod 的描述，而不是先看 app logs。
- 對 CreateContainerError，使用者目前不太確定該先看 logs 還是其他工具，並意識到這裡的關鍵疑問在於：如果 app 還沒真正跑起來，logs 到底能不能提供有價值的證據。
- 對 CrashLoopBackOff，使用者能抓到這比較像 container 已經啟動過，但 app 執行失敗後又掛掉，因此傾向先用 `kubectl logs` 或 `kubectl logs --previous`；目前還不夠確定的是，兩者在這個情境下各自較適合看哪個時間切面。

### AI 修正與補充

- 你這題的回答方向其實是對的，而且你現在卡住的點非常關鍵：不是「背答案」，而是要建立一個連結，也就是某種 Pod 狀態為什麼會讓你優先想拿某一種證據。
- 第一，Pending 先選 `kubectl describe pod` 是對的。因為 Pending 代表 Pod 還沒有順利進入真正執行 container 的階段，所以這時第一輪最有價值的，通常不是 app log，而是 Kubernetes 事件與排程訊號。你在 describe 裡特別要找的是 events，例如 `0/2 nodes are available`、資源不足、node selector 不符、taint / toleration 不匹配這類訊息。這就是為什麼 Pending 常先看 describe：你要先知道 Pod 為什麼連被排上去都做不到。
- 第二，ImagePullBackOff 先選 `kubectl describe pod` 也對。因為這一層的問題是 image 拉取失敗，container 往往還沒真正正常啟動，所以 app logs 不一定會有你要的東西。這時 describe 裡的 events 常會直接給你像 `Failed to pull image`、`ErrImagePull`、registry 權限或 tag 不存在這類訊號。換句話說，你期待拿到的證據不是 app 怎麼崩，而是 kubelet / container runtime 為什麼連 image 都拿不到。
- 第三，CreateContainerError 在第一輪通常也更適合先看 `kubectl describe pod`，而不是先看 logs。你的懷疑是對的：如果 container 在建立階段就失敗，logs 很可能根本沒有足夠內容，因為 app 還沒真正進入穩定執行。這時 describe 的 events 與 container state 反而比較可能直接提示問題，例如 Secret / ConfigMap 注入錯誤、container 建立失敗、掛載或環境變數處理失敗。WeaMind 的 `CreateContainerError (invalid UTF-8)` 就很適合放在這一類。
- 第四，CrashLoopBackOff 就是你抓得最準的一題。這通常表示 container 已經啟動過，但 app 撐不住而反覆重啟，所以 `kubectl logs` 與 `kubectl logs --previous` 都很有價值。差別在於：若目前這次 container 還活著，`logs` 會先讓你看到現在這輪的輸出；若你懷疑真正的錯發生在上一輪剛掛掉前，那 `logs --previous` 常更直接。更實務的口訣是：CrashLoopBackOff 想看「現在這輪」先用 logs，想看「上一輪死前最後一句」就用 logs --previous。
- 第五，所以這四題可以先收斂成一個很實用的模式：還沒順利進到 app 執行期的狀態，像 Pending、ImagePullBackOff、CreateContainerError，第一輪通常先看 describe，因為你要先拿 Kubernetes / node / runtime 這一層的事件證據；已經進到 app 執行期但反覆掛掉的狀態，像 CrashLoopBackOff，才更常先看 logs 或 logs --previous，因為這時你要的是 app 自己留下的訊號。
- 第六，你剛剛一直在問「我選這個工具，到底是想得到什麼內容」，這正是今天 Q2 的核心。最小版本可以記成：describe 拿控制面與事件證據；logs 拿 app 執行期證據；logs --previous 拿上一輪已死 container 的最後訊息；exec 則是拿 Pod 內部驗證證據，但它通常不是這四種狀態的第一輪起手式。

- 即使如此，使用者仍能抓到這兩題的共通點：它們都比較像流量還沒正確命中應用的正確入口，因此第一輪應先查外層 routing 細節，而不是先進 Pod 內部。

- 使用者也補充了一個很好的觀察：在這種情況下，就算先看 `kubectl logs`，也可能只是發現沒有對應請求紀錄，這反而更支持問題出在外層 routing，而不是 Pod 內部執行。

### AI 修正與補充

- 你的主判斷是對的，而且這題最重要的不是背哪個指令，而是先看「404 是在哪一層產生的」。這兩個案例都比較像流量尚未正確命中預期路由，因此第一輪確實應先把注意力放在外層 routing，而不是 Pod 內部。
- 第一，Hetzner LB health check 未帶 Host header 導致 `/health` 回 `404`，這題最典型的高價值觀察點就是 Hetzner LB 設定與 [manifests/ingress.yaml](manifests/ingress.yaml)。因為 Ingress 規則是 host-based routing，若請求沒帶 `Host: k8s.kyomind.tw`，Traefik 就不會命中你預期的規則。這時 `404` 比較像是 routing 沒命中，而不是 app 在 Pod 內部壞掉。
- 第二，你說「既然是 404，就代表它沒有打到正確路徑」這個方向是對的，但可以再修得更精準：回 `404` 不一定保證完全沒進到叢集，只是很常代表它沒有命中正確的應用路由規則。在這個案例裡，真正的第一個修正點是在 LB health check 沒帶對 Host header，而不是 Pod 內部程式碼。
- 第三，對 webhook 路徑填錯這題，你記得它本質上也是 routing 問題，這點是對的。根據 [PROGRESS.md](PROGRESS.md)，當時 LINE Developers 的 webhook URL 一開始被設成 `https://k8s.kyomind.tw/webhook`，結果 Verify 回 `404`；後來透過 Pod 內 introspection 確認 FastAPI 實際路由是 `/line/webhook`，修正後才成功。這表示它雖然最後有用到 Pod 內觀察，但第一個高價值訊號仍然是「外部打錯了路徑」。
- 第四，所以這兩題雖然都和 `404` 有關，但切入點稍微不同。LB health check 404 比較適合先看 LB 設定、Host header 與 Ingress 規則；webhook URL 404 則比較適合先看外部填入的 webhook URL 與應用實際暴露的路由是否一致，再視需要用 logs 或 Pod 內 introspection 輔助確認。
- 第五，你對 `exec` 的判斷也對。這兩題不該一開始就 `kubectl exec -it`，因為那是在拿 Pod 內部視角的證據；如果問題其實是外層 request 根本沒命中正確 host / path，先進 Pod 內部很可能只會看到「Pod 自己看起來正常」，卻無法解釋外部為什麼回 `404`。
- 第六，補一個更精準的工作口訣：當你懷疑是 host / path 沒命中、LB / Ingress / webhook URL 配置錯誤時，先查外層 routing 設定；當你已確定請求有進 Pod，但 app 回錯、噴 exception、或行為異常時，再把重點轉到 logs、logs --previous 或 exec。
- 第七，若要把這題壓成 WeaMind 的最小可講版，可以講成：LB health check `404` 先查 Hetzner LB 與 Ingress host 規則；webhook Verify `404` 先查外部填入的 URL 是否和應用真實路由一致。這兩題都不該先 `exec`，因為它們的第一個高價值異常訊號都在外層 routing，而不是 Pod 內部。

## Q4

### 題目

`kubectl exec -it` 在 WeaMind 這個專案裡最適合拿來驗證哪些事情？又有哪些事情即使你 `exec` 進 Pod 了，也不能因此直接下結論說外部流量路徑沒問題？

### 對照檔案

- `manifests/configmap.yaml`
- `manifests/service.yaml`
- `README.md`

### 使用者回答摘要

- 使用者坦白表示，自己過去無論在 Kubernetes 或單機 Docker 場景，都不算常用 `exec` 類工具，因此對它「最適合驗證什麼」目前沒有很穩定的直覺。
- 使用者回想自己以前在工作上用 `docker exec -it`，主要用途通常是進容器裡直接看檔案型 log，或檢查環境變數是否有被正確注入。
- 使用者目前能先抓到一個重要邊界：即使 `exec` 成功，也只能證明目前這個 container 至少是可進入、不是完全失聯；但這不代表應用邏輯一定正常，也不代表外部流量路徑一定沒有問題。
- 使用者也補問了一個很關鍵的概念問題：`kubectl exec` 到底是「進 Pod」還是「進 container」；尤其當一個 Pod 裡有多個 containers 時，應該怎麼決定進哪一個。

### AI 修正與補充

- 你現在的直覺其實是對的，而且很接近 `exec` 在實務上的真正定位：它不是萬能 debug 工具，而是「Pod 內部最小驗證工具」。
- 第一，對 WeaMind 這個專案來說，`kubectl exec -it` 最適合驗證的通常是 Pod 內部視角的事情，例如：環境變數是否有正確注入、DNS 解析是否正常、Pod 內能不能打到 `weamind-line-bot` Service、Pod 內能不能連到 `10.0.0.2:5433` 或 Redis、容器內某個檔案或設定是否存在。這些都屬於「我想知道 container 內看到的世界是什麼」這一類問題。
- 第二，所以你說以前常用它來看環境變數或檔案型 log，這完全合理。只是今天這個 lesson 想補的重點是：`exec` 擅長的是內部驗證，不是外部路由判讀。
- 第三，你說「exec 成功只能證明這個 container 目前可以被連進去，但不能證明邏輯正常」這句非常準。更精確地說，`exec` 成功通常代表：Pod 已經存在、至少有一個 container 正在運行且可接命令；但它不能直接證明應用行為正確，也不能證明 readiness、Ingress、LB、DNS 或 webhook URL 全都正常。
- 第四，回答你最後那個概念問題：`kubectl exec` 的命令入口是以 Pod 名稱為目標，但實際執行命令時，是進到 Pod 裡的某一個 container。也就是說，從使用者角度你是對著 Pod 下指令，但真正執行命令的對象仍然是某個 container。
- 第五，若 Pod 只有一個 container，通常不需要額外指定，`kubectl exec -it <pod-name> -- /bin/sh` 就可以；若 Pod 有多個 containers，應使用 `-c <container-name>` 指定，例如 `kubectl exec -it <pod-name> -c app -- /bin/sh`。若你不指定而 Pod 又有多個 containers，kubectl 可能會報錯，或依預設 container 設定決定目標。
- 第六，所以最短的正確說法是：`kubectl exec` 是「以 Pod 為入口，進到其中一個 container 執行命令」。這也正好對回你剛剛的疑問：它不是進某種抽象的 Pod 空間本身，而是進 Pod 裡實際某個 container。
- 第七，回到題目本身，這也是為什麼即使你能成功 `exec`，仍不能直接下結論說外部流量路徑沒問題。因為 `exec` 只是在回答「container 內部現在看到什麼」；它不會自動證明 LB 有沒有帶對 Host header、Ingress 規則有沒有命中、LINE webhook URL 有沒有填對。
- 第八，若要把 Q4 壓成 WeaMind 的最小可講版，可以講成：`kubectl exec -it` 最適合拿來做 Pod 內部最小驗證，例如看環境變數、DNS、HTTP 或 DB/Redis 連線；但即使能成功進 Pod，也只代表某個 container 目前可操作，不代表外部 DNS、LB、Ingress 或 webhook routing 一定都沒問題。
