## Q1

### 題目

如果只用一句話先區分 `kubectl describe pod`、`kubectl logs`、`kubectl logs --previous`、`kubectl exec -it`，你會怎麼描述它們各自最適合看的東西？請不要只背指令名稱，而是直接說「它比較像在拿哪種證據」。

### 對照檔案

- `manifests/deployment.yaml`
- `PROGRESS.md`

### 使用者回答摘要

- 使用者對四個工具已有初步直覺，但目前還在用較口語、較模糊的方式理解它們。
- 對 describe，使用者目前理解為「描述元件細節」，能抓到它是在看 Pod 等資源的狀態與資訊，但還不確定 describe 後面是否只能接單數資源，或能否用複數與未指定單一名稱的形式。
- 對 logs，使用者能把它類比成 docker logs，並判斷它主要是在看 Pod 內 container 的標準輸出與標準錯誤內容。
- 對 logs --previous，使用者目前還不確定它補的是哪一種額外資訊。
- 對 exec -it，使用者能正確抓到它比較像進到 Pod 內的 container 做互動式操作，並把它類比成較接近容器內部操作的入口。

### AI 修正與補充

- 主方向是對的，而且你已經抓到今天最重要的骨架：這四個工具不是都在回答同一個問題，它們是在拿不同種類的證據。
- 第一，describe 可以先收斂成這句：它比較像在看 Kubernetes 怎麼看這個資源。以 Pod 來說，高價值資訊通常是排程結果、狀態條件、container state、重啟次數和 events。也就是說，它比較偏叢集控制面與資源狀態的觀點，不是 app 自己的觀點。
- 你剛剛提到的單數、複數問題，也是一個好觀察。更準確地說，describe 後面接的是資源型別，單數或複數通常都可以，例如 pod 或 pods；而且若你只寫資源型別，也可以列出該 namespace 內多個同類資源的描述。真正的核心不是單複數，而是你有沒有把目標資源指定清楚。
- 第二，logs 你抓得很接近完整答案了。它可以先收斂成這句：logs 比較像在看 container 或 app 自己吐出的執行期訊息。像 Python exception、啟動過程、收到 webhook 後的請求紀錄，通常比較會在這裡看到。
- 第三，logs --previous 可以先收斂成這句：它是在看上一個已經死掉的 container 留下的最後訊息。這對反覆重啟的 Pod 很重要，因為一般 logs 看到的可能是現在這次啟動的內容，但你真正想找的錯，可能發生在上一輪剛掛掉之前。
- 第四，exec -it 你的理解也對。它可以先收斂成這句：exec -it 比較像進到 container 內做最小驗證，例如看環境變數、DNS 解析、HTTP 請求、TCP 連線或檔案是否存在。它提供的是 Pod 內視角，不是 Kubernetes 事件視角，也不是外部流量路徑的全貌。
- 第五，若要把四個工具壓成最小可講版，可以這樣說：describe 看 Kubernetes 對資源的觀察；logs 看 app / container 自己輸出的訊息；logs --previous 看上一個已死亡 container 的最後訊息；exec -it 則是進到 container 內做最小互動式驗證。
- 第六，今天這題真正重要的不是把定義背熟，而是開始建立一個直覺：當你想知道 Pod 為什麼排不起來、被重啟幾次、events 在說什麼時，先想到 describe；當你想知道 app 自己噴了什麼錯時，先想到 logs；當你懷疑它上一輪啟動時就死掉，想到 logs --previous；當你想從 Pod 內部驗證環境與連線，才想到 exec。
