# 2026-05-06 Terraform Drift SSH Boundary QA

## Q1

### 題目

如果你要用今天這次實作，解釋「Terraform 的 instance metadata `ssh-keys` 有什麼價值」，你會怎麼講？

### 答題引導

1. 先回答：今天 Terraform 明確補了哪些 SSH access prerequisite，例如 firewall、tag、instance metadata `ssh-keys`。
2. 再回答：既然後來 project metadata 也能支撐登入，為什麼 Terraform 的 instance metadata 路徑仍然有意義。
3. 最後補一句：它最適合的是哪一種場景，為什麼不該直接被 project metadata 取代。

### 對照檔案

- `terraform/gcp-free-tier-vm/main.tf`
- `terraform/gcp-free-tier-vm/ISSUE-ssh-access-for-personal-service-vm.md`

### 使用者回答摘要

- 使用者先指出：今天 Terraform 明確補了 SSH firewall rule 與 VM tag，讓帶有對應 tag 的 VM 能打通 22 port，建立 SSH 的 network prerequisite。
- 使用者也指出：Terraform 把指定 public key 寫進 instance metadata，讓這台 VM 有一條明確的 instance-level SSH identity path。
- 使用者進一步收斂：即使後來 project metadata 也能支撐登入，instance metadata 仍有價值，因為它是 by-instance 的做法，能減少對較大 scope 共用設定的依賴。
- 使用者目前也已抓到適用場景方向：這條路特別適合單一 VM、單人或小範圍管理的情境，但最後一句的口頭收斂還沒完全講順。

### AI 修正與補充

- 這題的核心回答已經接近完整，最值得保留的點是你有把 network prerequisite 和 identity path 分開講，這是對的。
- 更精準的說法可以是：今天 Terraform 補了兩層前提，一層是 `allow-ssh` tag 加 firewall rule，讓 22 port 的 ingress path 成立；另一層是把指定 public key 寫進 instance metadata，讓「這台 VM 接受哪把 key」變成 IaC 可明示的單機登入規則。
- 即使後來 project metadata 也能支撐登入，instance metadata 仍有價值，因為它把 scope 收斂在單一 VM，不必把登入權限擴散到整個 project，也比較適合做單機歸因、單機控管與 lesson 這種最小可驗證路徑。
- 第三段若要講得更完整，可以收斂成：它最適合單一 VM、個人使用、範圍小且希望把登入權限明確綁在某台機器上的場景；不該直接被 project metadata 取代，因為 project metadata 是 project-level 共用規則，雖然方便，但更容易放大權限範圍，也**更容易污染你對「到底是哪條登入路徑生效」的判讀**。

## Q2

### 題目

如果今天有人說「`gcloud compute ssh` 能登入，所以 Terraform 的 `ssh-keys` 一定有生效」，你會怎麼反駁或修正這句話？

### 答題引導

1. 先回答：`gcloud compute ssh` 成功，最多先證明了哪幾件事。
2. 再回答：今天有哪些證據說明成功路徑可能來自 project metadata / helper，而不是 instance metadata。
3. 最後補一句：之後遇到 SSH 成功事件時，應該改問哪個更準確的問題。

### 對照檔案

- `terraform/gcp-free-tier-vm/ISSUE-ssh-access-for-personal-service-vm.md`
- `terraform/gcp-free-tier-vm/docs/ssh-runtime-validation-and-gcloud-key-behavior.md`
- `terraform/gcp-free-tier-vm/docs/ssh-metadata-isolation-experiments.md`

### 使用者回答摘要

- 使用者先收斂：`gcloud compute ssh` 成功，最多先證明 Google Cloud 的驗證與 helper 鏈路可運作，能幫忙建立或補齊連線所需條件，不能直接證明 Terraform 的 instance metadata `ssh-keys` 一定在發揮作用。
- 使用者用第一次登入經驗作證據：當時因為預設 key 路徑沒有現成 key pair，`gcloud` 先幫忙建立 key，再把 public key 更新到 project metadata，代表第一次成功很大一部分是 helper 自己補完的結果。
- 使用者也指出：後來即使改用指定 key path 的 `gcloud compute ssh`，該 key 仍被寫進 project metadata；再加上後續直接查 project metadata 時，裡面確實看得到兩條 `kyo` SSH key，因此這不是純 instance metadata 的成功事件。
- 使用者最後把問題收斂成更準確的判讀方式：之後看到 SSH 成功，不該直接問 Terraform 的 `ssh-keys` 有沒有生效，而應該問這次成功到底是走 project metadata 還是 instance metadata 的 key path。

### AI 修正與補充

- 這題的核心判讀是對的，而且你有抓到最重要的證據鏈：`gcloud` 建 key、`Updating project ssh metadata`、指定 key path 後 project metadata 仍有新增條目，以及最後直接查到 project metadata 裡真的有兩條 `kyo` key。
- 第一段可以再更精準一點：`gcloud compute ssh` 成功，至少先證明 VM 可達、你對該專案 / 執行個體有足夠控制面存取能力，而且目前存在至少一條可工作的 SSH identity path；但它本身不保證那條 path 來自 Terraform 管理的 instance metadata。
- 第二段最值得記住的是：`gcloud compute ssh` 是 client entry method，不是 identity source；一旦它混入 key 生成與 metadata 更新，就會污染你對真正成功來源的歸因。
- 最後一句若要口頭講得更完整，可以收斂成：遇到 SSH 成功事件時，應該改問「這次成功依賴的 identity source 是哪一層，project metadata、instance metadata、還是 OS Login / helper 流程？」而不是直接把成功歸功給某一條 IaC 設定。
