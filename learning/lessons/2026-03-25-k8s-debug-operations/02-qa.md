## Q1

### 題目

如果今天拿到的故障敘述是：「`https://k8s.kyomind.tw/health` 可以回 `200`，但 LINE Developers 的 webhook Verify 回 `404`」，你第一輪會先把問題放在哪一層，為什麼？你會先查哪個設定或證據，而不是立刻先進 Pod？

### 對照檔案

- `docs/LINE-Webhook-切換流程.md`
- `PROGRESS.md`
- `manifests/ingress.yaml`

### 使用者回答摘要

- 使用者先把這題判成 routing 類問題，而不是 Pod 內部壞掉，主方向正確。
- 使用者的理由是：既然 `https://k8s.kyomind.tw/health` 已能回 `200`，代表至少有一條外部路徑已能從對外端點進到 Kubernetes 內的 app，因此 Pod 與 app 本身大機率是正常的。
- 使用者也進一步判斷：既然 LINE Developers webhook Verify 回 `404`，那就比較像 webhook 對應的 routing 有問題，而不是整個服務完全打不通。
- 目前使用者傾向把問題放在 Load Balancer 到 Ingress / Service 之間的 routing 層，並認為 Service 既然能讓 `/health` 成功回應，應該不是第一個最值得懷疑的地方。

### AI 修正與補充

- 主方向是對的，而且你已經做對今天最重要的第一步：沒有因為看到 `404` 就直接跳進 Pod，而是先把它判成較像外層 routing / URL 對應問題。
- 第一個要補得更精準的地方是：`/health` 回 `200`，代表的是「這一條特定路徑」已經能走通 LB、Ingress、Service 到 Pod，最後由 app 正常回應；它不能直接證明所有外部路徑都正確，只能證明 `/health` 這條路徑是通的。
- 第二個更關鍵的修正是：以這個 repo 目前的 [manifests/ingress.yaml](manifests/ingress.yaml) 來看，Ingress 規則是 `host: k8s.kyomind.tw` 搭配 `path: /` 的 Prefix。這代表 Ingress 會把這個 host 底下的大部分路徑都轉給同一個 Service，而不是只接受 `/health`。所以這題若 Verify 回 `404`，第一輪更值得優先懷疑的，通常不是「LB 到 Service 這段根本沒導到」，而是「外部填入的 webhook path 和 app 真正暴露的路由不一致」。
- 根據 [PROGRESS.md](PROGRESS.md#L136)，WeaMind 的真實案例就是：一開始把 webhook URL 設成 `https://k8s.kyomind.tw/webhook`，結果 Verify 回 `404`；後來確認 app 實際路由是 `/line/webhook`，修正後才成功。也就是說，這個 `404` 很可能不是 Ingress 完全沒命中，而是請求其實已經被轉進 app，但 path 不存在，所以由應用層回了 `404`。
- 所以這題第一輪最有價值的檢查點，應該先是「LINE Developers 裡填的 webhook URL 路徑到底是什麼」，然後把它對照 app 真正暴露的路由證據；Ingress 規則可以作為第二個輔助確認點，但不一定是第一嫌疑。
- 你不該第一步就 `exec` 進 Pod，這個判斷是對的。因為在還沒先對 URL path 與外層設定做比對前，先進 Pod 容易拿到低價值資訊。這題的第一個高價值證據，是外部 webhook URL 與實際路由是否一致，而不是 container 內部此刻能不能執行命令。
- 如果把這題壓成最短可講版，可以這樣說：`/health` 回 `200` 代表整條入口不是全壞，Webhook Verify 回 `404` 則更像特定 path 對錯了。第一輪先查 LINE Developers 裡填的 URL 與 app 真實 webhook 路徑是否一致，再視需要回頭確認 Ingress host / path 規則，而不是先 `exec` 進 Pod。
