## Q1

### 題目

如果今天拿到的故障敘述是：「`https://k8s.kyomind.tw/health` 可以回 `200`，但 LINE Developers 的 webhook Verify 回 `404`」，你第一輪會先把問題放在哪一層，為什麼？你會先查哪個設定或證據，而不是立刻先進 Pod？

### 對照檔案

- `docs/LINE-Webhook-切換流程.md`
- `PROGRESS.md`
- `manifests/ingress.yaml`

### 使用者回答摘要

- 使用者先把這題判成 routing 類問題，而不是 Pod 內部壞掉，主方向正確。
- 使用者的理由是：既然 `https://k8s.kyomind.tw/health` 已能回 `200`，代表至少有一條外部路徑已能從對外端點進到 Kubernetes 內的 app，因此 Pod 與 app 本身大機率是正常的。
- 使用者也進一步判斷：既然 LINE Developers webhook Verify 回 `404`，那就比較像 webhook 對應的 routing 有問題，而不是整個服務完全打不通。
- 目前使用者傾向把問題放在 Load Balancer 到 Ingress / Service 之間的 routing 層，並認為 Service 既然能讓 `/health` 成功回應，應該不是第一個最值得懷疑的地方。

### AI 修正與補充

- 主方向是對的，而且你已經做對今天最重要的第一步：沒有因為看到 `404` 就直接跳進 Pod，而是先把它判成較像外層 routing / URL 對應問題。
- 第一個要補得更精準的地方是：`/health` 回 `200`，代表的是「這一條特定路徑」已經能走通 LB、Ingress、Service 到 Pod，最後由 app 正常回應；它不能直接證明所有外部路徑都正確，只能證明 `/health` 這條路徑是通的。
- 第二個更關鍵的修正是：以這個 repo 目前的 [manifests/ingress.yaml](manifests/ingress.yaml) 來看，Ingress 規則是 `host: k8s.kyomind.tw` 搭配 `path: /` 的 Prefix。這代表 Ingress 會把這個 host 底下的大部分路徑都轉給同一個 Service，而不是只接受 `/health`。所以這題若 Verify 回 `404`，第一輪更值得優先懷疑的，通常不是「LB 到 Service 這段根本沒導到」，而是「外部填入的 webhook path 和 app 真正暴露的路由不一致」。
- 根據 [PROGRESS.md](PROGRESS.md#L136)，WeaMind 的真實案例就是：一開始把 webhook URL 設成 `https://k8s.kyomind.tw/webhook`，結果 Verify 回 `404`；後來確認 app 實際路由是 `/line/webhook`，修正後才成功。也就是說，這個 `404` 很可能不是 Ingress 完全沒命中，而是請求其實已經被轉進 app，但 path 不存在，所以由應用層回了 `404`。
- 所以這題第一輪最有價值的檢查點，應該先是「LINE Developers 裡填的 webhook URL 路徑到底是什麼」，然後把它對照 app 真正暴露的路由證據；Ingress 規則可以作為第二個輔助確認點，但不一定是第一嫌疑。
- 你不該第一步就 `exec` 進 Pod，這個判斷是對的。因為在還沒先對 URL path 與外層設定做比對前，先進 Pod 容易拿到低價值資訊。這題的第一個高價值證據，是外部 webhook URL 與實際路由是否一致，而不是 container 內部此刻能不能執行命令。
- 如果把這題壓成最短可講版，可以這樣說：`/health` 回 `200` 代表整條入口不是全壞，Webhook Verify 回 `404` 則更像特定 path 對錯了。第一輪先查 LINE Developers 裡填的 URL 與 app 真實 webhook 路徑是否一致，再視需要回頭確認 Ingress host / path 規則，而不是先 `exec` 進 Pod。

## Q2

### 題目

如果今天 rollout 後某個 Pod 變成 CrashLoopBackOff，你會怎麼排第一輪與第二輪觀察順序？請不要只回答指令名稱，要一起說明你第一輪想拿哪一類證據、第二輪又是為了補哪個缺口。

### 對照檔案

- `manifests/deployment.yaml`
- `PROGRESS.md`

### 使用者回答摘要

- 使用者已能把 CrashLoopBackOff 的排查拆成兩輪，主線正確。
- 第一輪，使用者會先看 kubectl describe pod，重點放在 Pod 目前狀態、restart 次數與 events，想先拿 Kubernetes 視角的證據，了解它已經重啟了幾次、目前落在什麼狀態，以及叢集事件在提示什麼。
- 使用者也能說出第一輪的目的不是直接找出程式碼哪一行錯，而是先確認這個 Pod 的整體重啟情況與事件脈絡。
- 第二輪，使用者會改看 kubectl logs；若 Pod 已重啟多次，會進一步使用 --previous 去看上一輪已死 container 的完整 log，想補上 app 為什麼實際崩掉的證據。
- 使用者已經抓到兩輪之間的分工：第一輪偏 Kubernetes / Pod 狀態視角，第二輪偏 app 內部錯誤訊息視角。

### AI 修正與補充

- **這題你的主線是對的，而且已經比只背工具名稱更進一步了。** 你現在不是在說先用哪個指令、再用哪個指令，而是在說第一輪和第二輪各自要補哪一類證據，這正是今天要練的重點。
- **第一輪先看 `describe pod` 是合理的。** 因為 `CrashLoopBackOff` 的第一個高價值問題通常不是 app 具體哪一行壞了，而是 Kubernetes 目前怎麼看這個 `Pod`。這一輪你特別該看的欄位，通常會是 `current state`、`last state`、`restart count` 和 `events`。它們回答的是：container 現在是在 `waiting`、`running` 還是 `terminated`，上一輪怎麼死的，已經重啟幾次，以及 `kubelet` / 叢集事件怎麼描述這個現象。
- 你提到想先看 `restart count`，這個判斷是對的。不過可以再修得更精準一點：不是因為 `restart count` 多就一定代表語法問題，而是 `restart count` 越高，越能支持**這不是單次偶發，而是 container 正在反覆失敗**這件事。至於根因是語法錯、環境變數錯、啟動指令錯、依賴連線失敗，還要靠第二輪證據去分。
- 你說 `events` 平常正常時可能是 `none`，這個方向也對，但更精準地說，`events` 不是只有錯誤才會出現；只是對 `CrashLoopBackOff` 這類情境來說，若有像 `Back-off restarting failed container` 這種事件，就特別有判讀價值。
- **第二輪接 `logs`，甚至在需要時直接看 `logs --previous`，這個接法也對。** 因為 `describe` 幫你回答的是 Pod 正在反覆失敗，但它通常不能完整告訴你 app 為什麼崩；這時就要改從 app 視角拿證據，看啟動過程裡到底噴了什麼錯。
- 這裡還有一個很重要的細節：在 `CrashLoopBackOff` 情境下，`logs --previous` 常常不是如果重啟很多次才加上去而已，而是很常在第二輪就值得直接考慮。原因是目前這一輪 container 可能剛被拉起來、還沒吐出完整錯誤，真正最有價值的訊息往往留在上一輪死前最後幾行。
- **所以這題最短可講版可以收斂成：** 第一輪先用 `describe pod` 拿 Kubernetes 對 `Pod` 重啟狀態與事件的描述，確認它是否真的在反覆失敗、上一輪怎麼結束；第二輪再用 `logs` 或 `logs --previous` 補 app 視角的錯誤訊息，找出 container 為什麼實際崩掉。
- **若再往前推一步，這兩輪其實各自回答不同問題：第一輪回答它是怎麼壞的，第二輪回答它為什麼壞。** 這就是你這題已經抓到的核心差別。

## Q3

### 題目

如果 Pod 本身是 Running、Ready，看起來也有被 Service 選到，但 webhook 請求進來後 bot 行為異常，甚至懷疑連 PostgreSQL 或 Redis 有問題，這時你會怎麼區分「外部流量路徑問題」和「Pod 到 VM 依賴問題」？第一輪各自較值得查什麼？

### 對照檔案

- `manifests/configmap.yaml`
- `manifests/service.yaml`
- `README.md`
- `PROGRESS.md`

### 使用者回答摘要

- 使用者已能先根據症狀做初步分流：若請求已經進到 `Pod` 且看到 bot 行為異常，問題不一定還在外部流量路徑；但若錯誤型態是 `500` 或 `timeout`，範圍仍然可能很大，不能太快武斷。
- 對外部流量路徑問題，使用者目前能抓到這要看錯誤類型；若是 `timeout`，仍可能涉及 `Pod` 本身狀態或外層路徑，不一定能立刻排除。
- 對 `Pod` 到 VM 依賴問題，使用者的第一反應是先看 `logs`；若 `logs` 看不出來，再用 `kubectl exec -it` 進到 container 內部做最小驗證，例如 `printenv` 檢查資料庫連線相關設定。
- 使用者也能主動補出一個正確邊界：`kubectl exec -it` 嚴格來說是進到某個 container，而不是抽象地進到整個 `Pod` 本體。

### AI 修正與補充

- **你的主方向是對的：這題不能只看 `Running`、`Ready` 就直接下結論，而要先看症狀到底比較像哪一層。** 你有抓到一個很重要的邊界，就是「請求進來後 bot 行為異常」這句話本身，已經比「外部完全打不進來」更往內層了一步。
- 第一個要收得更精準的地方是：如果我們已經有證據顯示 webhook 請求**真的進到 app**，例如 `logs` 裡看得到對應請求，或至少看得到應用層錯誤，那第一輪就**不該再優先懷疑外部流量路徑**。這時更值得優先看的，是 app 自己的 `logs` 是否有 `PostgreSQL`、`Redis`、timeout、exception 或 downstream error 的訊息。
- 以這個 repo 來說，`Pod` 到 VM 依賴的第一輪高價值檢查點，通常是兩類：第一，應用 `logs` 裡有沒有連線失敗跡象；第二，設定值是否和 [manifests/configmap.yaml](manifests/configmap.yaml) 一致，例如 `POSTGRES_HOST=10.0.0.2`、`POSTGRES_PORT=5433`、`REDIS_URL=redis://10.0.0.2:6379/0`。
- **所以如果你懷疑的是 `Pod` 到 VM 依賴問題，第一輪通常先看 `logs`，第二輪才考慮 `kubectl exec -it`。** 因為 `logs` 先回答的是 app 在實際處理請求時有沒有噴出資料庫或快取連線錯誤；若 `logs` 不夠明確，再進 container 內用 `printenv`、最小連線測試或其他已存在工具確認設定與內部視角。
- 反過來說，若你懷疑還是外部流量路徑問題，第一輪更值得查的是「請求到底有沒有進到 app」。這時高價值證據會是：有沒有 webhook 請求 log、回的是 `404`、`405`、`500` 還是 `timeout`，以及外部 URL / Ingress / LB 設定是否一致。**若連請求紀錄都沒有，才更像外層 routing；若請求紀錄已經出現，但處理過程失敗，就更像 app 或依賴問題。**
- 你剛剛提到 `timeout` 會讓範圍比較大，這個判斷是對的。`timeout` 比 `404` 更模糊，可能出在外部流量路徑，也可能出在 app 卡住、連 `PostgreSQL` 太慢、等 `Redis`、或某個 downstream call 卡住。所以 `timeout` 的第一輪關鍵不是立刻猜根因，而是先分清楚 timeout 發生在外層還是請求進入 app 之後。
- **這題最短可講版可以收斂成：** 若請求是否進到 app 還不確定，第一輪先查外部流量路徑證據，例如 webhook log 是否出現、URL / Ingress / LB 是否一致；若已確定請求進到 app 但 bot 行為異常，第一輪先看 app `logs` 是否出現 `PostgreSQL` / `Redis` 相關錯誤，再視需要用 `kubectl exec -it` 進 container 驗證 `POSTGRES_HOST`、`POSTGRES_PORT`、`REDIS_URL` 等設定與內部連線視角。
- **真正的分界點不是 `Pod` 是不是 `Running`，而是請求有沒有進到 app、以及 app 自己有沒有留下依賴錯誤證據。** 這是你這題下一步要慢慢練熟的判斷軸。
