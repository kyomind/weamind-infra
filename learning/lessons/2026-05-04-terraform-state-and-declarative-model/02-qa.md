## Q1

### 題目

如果只看今天的 prework 與 W9 計畫，你會怎麼用自己的話解釋：Terraform 的 `state` 為什麼不是單純 cache？

### 答題引導

1. 先回答：`state` 幫 Terraform 解的是哪一類問題？
2. 再回答：如果沒有 `state`，Terraform 在 `plan` / `apply` 階段最容易哪裡判斷失真？
3. 最後補一句：這件事和「資源長怎樣」相比，哪一層更關鍵？

### 對照檔案

- `learning/prework/2026-05-04-terraform-core-workflow-and-state.md`
- `references/phase2/w9-iac-minimum-spec.md`

### 使用者回答摘要

- `state` 解的是 Terraform local config 和雲端真實資源之間的對應關係，不只是單純暫存資料。
- 若沒有 `state`，Terraform 在 `plan` / `apply` 階段就無法知道哪些雲端資源屬於目前 config 管理的對象，因此容易無法正確對上目標。
- 使用者已指出：缺少正確 mapping 時，Terraform 可能不知道該 update 誰，進而出現直接重建、誤建新資源或其他錯誤操作。
- 結論上，和「資源長怎樣」相比，**資源身份與 mapping** 更關鍵；因為如果連對象都對不起來，就談不上正確變更。

### AI 修正與補充

- 你的主結論是對的，而且重點有抓到：`state` 的核心不是快取內容，而是維持 **Terraform resource 和真實雲端資源 ID 之間的身份對應**。
- 可以再講得更準一點：`state` 幫 Terraform 解的不是一般的「同步效率問題」，而是 **資源 identity 與變更判斷問題**。這也是為什麼它會直接影響 `plan` 和 `apply` 的可信度。
- 你提到「不知道要向誰 apply」這句很接近本質。更精確的講法是：如果沒有 `state`，Terraform 就很難判斷某個 resource 應該 **update 既有資源、create 新資源，還是誤判成需要 destroy 再 recreate**。
- 最後一句也抓得對：比起「資源長怎樣」，**先知道它是誰** 更重要。因為 Terraform 做變更前，第一件事不是欣賞 spec，而是確認這個宣告到底在管理哪個真實對象。
- 若要再壓成一句面試版，可以說：**Terraform 的 `state` 不是單純 cache，而是資源身份對應表；沒有它，Terraform 就無法穩定判斷變更應該套到誰身上。**

## Q2

### 題目

對照 `terraform/README.md`、`terraform/gcp-free-tier-vm/README.md` 和 `manifests/deployment.yaml`，你會怎麼比較 Terraform 與 Kubernetes manifest 都是宣告式，但它們的 reconcile 與 lifecycle 差在哪裡？

### 答題引導

1. 先講共同點：兩者都在描述什麼？
2. 再講最大差異：誰在持續 reconcile，誰需要明確的 `plan` / `apply` 週期？
3. 最後把這個差異對回 repo：為什麼 `terraform/` 不應直接和 `manifests/` 混成同一種 deploy source？

### 對照檔案

- `terraform/README.md`
- `terraform/gcp-free-tier-vm/README.md`
- `manifests/deployment.yaml`

### 使用者回答摘要

- Terraform 和 Kubernetes manifest 的共同點，都是在描述期望的最終資源狀態。
- 使用者已指出最大差異在 reconcile 模型：Kubernetes 有持續運作的 reconcile loop，會自動對照期望狀態與實際狀態；Terraform 則要等人主動跑 `plan` / `apply`，這個週期本質上是人為觸發的。
- 使用者也有抓到 repo 邊界：Kubernetes manifest 控制的是 Kubernetes 叢集裡的資源；Terraform 則偏向控制雲端或基礎設施層的資源，因此兩者不應混成同一種 deploy source。
- 已能說出：雖然 Terraform 也可以接進 CI/CD，但它的 lifecycle 仍不是像 Kubernetes controller 那樣持續自動運作。

### AI 修正與補充

- 你的主線是對的：兩者的共同點確實都是在描述 **desired state**，而不是一步一步寫死「怎麼做」。
- 你對最大差異的描述也成立，而且已經碰到最核心的詞：**Kubernetes 是持續 reconcile，Terraform 是顯式、週期性地 reconcile**。更精確地說，Kubernetes 把 desired state 交給 controller 持續逼近；Terraform 則是在 `plan` / `apply` 那一刻，根據 config、state 和 provider 查到的現況做一次變更決策。
- 你說 Kubernetes 是以 YAML 或 state 當 source of truth，這裡可以再收斂一下：對使用者來說，通常是以提交到 API server 的資源宣告為起點；真正被 controller 持續維持的是 cluster 內的資源狀態。Terraform 那邊則更依賴 **config + state** 這組組合來做判斷。
- 對 repo 邊界的回答也對，但可以再多補一句：`manifests/` 是 **目前 WeaMind cluster runtime 的 deploy source**；`terraform/` 目前是 **Terraform 能力與可執行 IaC 資產**，但不是當前 K3s 叢集應用部署的入口，所以不應混成同一層。
- 若要壓成一句面試版，可以說：**Terraform 和 Kubernetes 都是宣告式，但 Kubernetes 依靠 controller 持續 reconcile，Terraform 則依靠 state 與明確的 plan/apply 週期做一次次的人為 reconcile；因此兩者雖然都在描述 desired state，卻不屬於同一種 deploy source。**

## Q3

### 題目

如果明天要進 W9 Day 2 的 GCP 實作，光有 `.tf` 檔還不夠。你認為根據這個 repo 目前的規格，最低還要留下哪些證據，才算真的走過一次最小 IaC workflow？

### 答題引導

1. 先回答：哪些證據是跟「Terraform 有真的算過 diff 並執行變更」有關？
2. 再回答：哪些證據是跟「這台 VM 符合 Free Tier 邊界」有關？
3. 最後補一句：這些證據為什麼對之後講 state / drift 或面試重講有用？

### 對照檔案

- `references/phase2/w9-iac-minimum-spec.md`
- `terraform/gcp-free-tier-vm/README.md`
- `.privatedocs/Phase2三週計畫.md`

### 使用者回答摘要

- 使用者先補問了一個重要邊界：Terraform 能控制的資源範圍，不是無限的；直覺上會同時受 provider 能力、目標平台 API 與 Terraform 描述能力限制。
- 對 Q3 本體，使用者已先抓到第一層方向：若要證明 Terraform 真的走過一次 IaC workflow，重點不能只有 `.tf` 檔，而必須和 `state`、實際變更、以及後續 drift 講法接得起來。
- 使用者對第三小題已能說出：若沒有 `state` 對應，就很難確定 drift 發生在哪些資源、影響範圍多大，因此那些操作證據對之後講 `state` / `drift` 很重要。
- 對第二小題，使用者有卡住「符合 Free Tier 邊界」到底在問什麼；已意識到這應該和實際雲端資源規格驗證有關。

### AI 修正與補充

- 你先補問的那個問題很對，而且值得放進 note。更準的答案是：**Terraform 能管理到哪裡，不只受 HCL 限制，也不只受雲端 API 限制，而是同時受目標平台 API、provider 實作品質，以及該資源是否適合宣告式管理這三層限制。**
- 回到 Q3 本體，這題要的不是「理論上會用 Terraform」，而是 **明天做完之後，這個 repo 要留下哪些可驗收證據，能證明你真的走過一次最小 IaC workflow。**
- 第一類證據，是跟 **Terraform 真的算過 diff 並執行變更** 有關的：
	- 一次完整的 `terraform plan`
	- 一次完整的 `terraform apply`
	- 一份可讀的 Terraform 檔案骨架，而不是只有一個模糊大資源塊
	- 一次對 `state` 或資源變更結果的實際觀察
- ⭐️第二類證據，是跟 **這台 VM 真的符合 Free Tier 邊界** 有關的。這一題問的就是：你不能只說「我建出一台 VM」，還要能證明它沒有偏離這週規格，例如：
	- region 落在允許範圍
	- machine type 真的是 `e2-micro`
	- boot disk type 是標準 HDD
	- disk size 沒超出安全範圍
	- network tier 是 `STANDARD`
	- 沒有混入多餘 backup / monitoring 類設定
- 所以第二小題其實是在問：**你要留下哪些規格核對證據，證明這台雲端資源不是隨便建一台，而是有對齊 W9 的 Free Tier 驗收邊界。**
- 你第三小題的方向是對的，但可以再講完整一點：這些證據之所以重要，是因為它們會讓你之後不只說「我寫過 Terraform」，而是能說 **我真的看過 plan、apply 過資源、知道 state 怎麼對應、也知道 drift 發生時該從哪裡懷疑。**
- 若要壓成一句面試版，可以說：**最小 IaC workflow 的證據，不只是 `.tf` 檔，而是 plan、apply、資源規格核對與 state / drift 觀察；這些證據才足以證明我真的走過一次 Terraform 的完整變更循環。**
