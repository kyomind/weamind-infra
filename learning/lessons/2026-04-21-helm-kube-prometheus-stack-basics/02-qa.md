## Q1

### 題目

今天這次 Helm 安裝，`release`、`chart`、`values` 三者各自回答什麼問題？為什麼這次不能把它簡化成「只是另一種 `kubectl apply`」？

### 答題引導

1. 先分開講 `chart`、`release`、`values` 各自站在哪一層。
2. 再回答這三者在今天的安裝過程裡分別留下了什麼可觀察證據。
3. 最後補一句 Helm 和 raw manifests 的最小差異，不要展開到 W8 的完整比較。

### 對照檔案

- `.privatedocs/Phase2三週計畫.md`
- `docs/Kubernetes-Dashboard-臨時安裝紀錄.md`

### 使用者回答摘要

- 使用者目前對 Helm 還不熟，先抓到一個大方向：`chart` 像是 Helm 管理資源的一種方式，可能能取代大量 YAML，但還說不清楚它到底站在哪一層。
- 對 `release` 目前幾乎沒有把握，還不能穩定說出它代表什麼。
- 對這次實際看到的結果有清楚觀察：`kube-prometheus-stack` 安裝後，叢集裡同時出現 `Deployment`、`StatefulSet`、`DaemonSet` 與對應 Pod，而且都正常運作中。

### AI 修正與補充

- 可以先把這三層切開講：`chart` 是一份可重複安裝的 Helm 套件，裡面包的是模板、預設值與要建立的一組 Kubernetes 資源，不只是「很多 YAML」，而是**把一套資源如何生成、如何參數化**都包在一起。
- `release` 則是「某個 chart 在某個 cluster / namespace 裡實際安裝出來的一個實例」。今天這次安裝裡，`observability` 就是 release name；`helm status observability -n observability`、`REVISION: 1`、`STATUS: deployed` 這些都是 release 層的證據。
- `values` 站在更細一層，它回答的是：這次安裝要用哪些參數去餵這個 chart。今天雖然幾乎沒自訂 values，但這不代表 values 不存在，而是代表**這次先採用 chart 預設值做最小安裝**。
- 所以比較穩的講法是：**chart 是安裝藍圖，release 是安裝後的實例，values 是這次實例化時帶進去的參數。**
- 為什麼這不能簡化成「只是另一種 `kubectl apply`」：因為 `kubectl apply` 比較像把既定 manifest 送進 API server；Helm 則多了 **模板渲染、values 覆蓋、release 管理、revision 與 upgrade / rollback 邊界** 這一層。今天你看到的 `REVISION: 1` 就是 raw manifests 不會自然給你的 release 管理訊號。
- 你觀察到「這次安裝後同時出現 `Deployment`、`StatefulSet`、`DaemonSet`，而且都正常運作」這點是很好的實作證據，因為它證明這次不是只裝出一堆抽象資源，而是真的把整套 observability stack 的核心 workload 建立起來了。

## Q2

### 題目

`kube-prometheus-stack` 裡至少有哪幾個主要元件？今天這些元件裡，哪些是你真的在叢集裡看到的核心 workload，哪些只是你先建立了最小角色理解？

### 答題引導

1. 先列出今天最小必須會講的元件：Prometheus Operator、Prometheus、Grafana、Alertmanager、Node Exporter、`kube-state-metrics`。
2. 再回答它們各自解的是什麼最小問題。
3. 最後把答案收斂回今天實際看到的資源，不要只背 prework 名詞。

### 對照檔案

- `.privatedocs/Phase2三週計畫.md`
- `references/phase2/w7-observability-minimum-spec.md`

### 使用者回答摘要

- 使用者已能從 Headlamp GUI 直接對回幾個核心 workload：`Deployment` 包含 Grafana、Prometheus Operator、`kube-state-metrics`；`StatefulSet` 包含 Prometheus 與 Alertmanager；`DaemonSet` 是 Node Exporter。
- 對 Node Exporter 為什麼是 `DaemonSet` 的直覺正確，知道它是每個 node 都需要有一份。
- 對 Prometheus 為什麼是 `StatefulSet` 也已有初步理解，知道它和 time-series database 的有狀態特性有關。
- 目前比較不確定的是 Alertmanager 為什麼也常被放在 `StatefulSet`。

### AI 修正與補充

- 你這題的主結構已經對了，而且是貼著今天實際看到的 workload 在回答，這比只背 prework 名詞更好。
- 今天最少要能穩定講出的核心元件可以收斂成這六個：Prometheus、Grafana、Prometheus Operator、Alertmanager、Node Exporter、`kube-state-metrics`。
- 它們的最小角色可以這樣講：Prometheus 負責抓、存、查 metrics；Grafana 負責 dashboard；Prometheus Operator 負責用 Kubernetes / CRD 模型管理 Prometheus、Alertmanager 等觀測元件；Alertmanager 負責告警分群、路由與通知；Node Exporter 提供 node 層 metrics；`kube-state-metrics` 提供 Kubernetes objects / state 類型的 metrics。
- workload 型別對應也可以收斂成一版穩定說法：Grafana、Prometheus Operator、`kube-state-metrics` 是 `Deployment`；Prometheus 與 Alertmanager 是 `StatefulSet`；Node Exporter 是 `DaemonSet`。
- Node Exporter 為什麼是 `DaemonSet` 這題你答得很好，因為它的任務就是每個 node 各跑一份 exporter，去暴露該 node 的 metrics，這和每節點型工作負載的模型完全一致。
- 你對 Prometheus 為什麼是 `StatefulSet` 的方向也對：重點不是「它有 Pod」，而是它需要用有狀態工作負載模型來管理資料與身份。
- Alertmanager 之所以也常走 `StatefulSet`，理由不是因為它像 Prometheus 一樣是完整 TSDB，而是因為它仍有穩定身份與持久化邊界的需求，例如 silences、notification log、cluster peer 狀態與高可用協調。它不是最重的資料面元件，但也不是適合隨意漂移的純 stateless web app。

## Q3

### 題目

如果今天出現「Helm release 建了，但某些 Pod 起不來」的情況，第一輪你會怎麼縮圈？為什麼今天不應直接把問題跳成 app metrics 或 Grafana dashboard 設計？

### 答題引導

1. 先回答最小排查入口應先看哪些 Helm / Kubernetes 訊號。
2. 再回答這種故障目前仍屬於哪一層問題。
3. 最後補一句今天 lesson 的邊界，說明為什麼先不擴到後續 observability 主題。

### 對照檔案

- `06-implementation.md`

### 使用者回答摘要

- 使用者第一輪會先從 namespace 內的 Pod 狀態開始看，至少先 `get pods` 確認哪些 Pod 起不來，再視需要用 `describe` 看錯誤原因。
- 使用者已正確抓到：如果是 Pod 起不來，這比較像 Kubernetes runtime 層的問題，而不是先跳去想 app metrics 或 Grafana dashboard。
- 對 Helm 在這種情況下還能回答哪一層問題，目前還不太確定。
- 對為什麼不該直接跳去 app metrics 或 dashboard 的判斷方向正確：因為 app metrics 收集與 dashboard 觀察根本還沒開始，現在連基礎 workload 都還沒穩定。

### AI 修正與補充

- 你這題的第一步選得對：**先看 `kubectl get pods -n observability`，必要時補 `kubectl describe pod`**，這是最合理的 runtime 入口。
- 更完整一點的第一輪縮圈可以收斂成：先看 `helm status observability -n observability` 確認 release 層有沒有明顯失敗訊號，再看 `kubectl get pods -n observability` 找出壞掉的 workload，最後對特定 Pod 做 `describe` 或看 `events`。
- 這樣就把 Helm 層和 Kubernetes runtime 層分開了：Helm 回答的是 **release 有沒有成功建立、chart install 有沒有在模板或安裝流程就失敗**；`get/describe/events` 回答的是 **資源已建立後，Pod 為什麼沒成功跑起來**。
- 所以如果情境是「release 建了，但某些 Pod 起不來」，更精準的說法是：**Helm install 可能已經成功，問題主體現在更像 Kubernetes runtime / workload 健康層，而不是 chart 來源層。**
- 你說不該直接跳去 app metrics 或 Grafana dashboard，這個判斷也是對的。因為今天若連核心 workload 都沒穩定，後面的 app metrics、ServiceMonitor、dashboard 都還沒有可靠基礎，這時候往下跳只會把問題擴散。
- 這題最穩的短版收斂可以講成：**先用 Helm 看 release 邊界，再用 Kubernetes runtime 證據看 Pod 為什麼起不來；在核心 workload 還沒穩之前，不進 app metrics 或 dashboard。**
