## Q1

### 題目

如果只看 WeaMind 的 README、架構文件與成本設定，你會怎麼解釋這個專案為什麼選 K3s，而不是 kubeadm、EKS 或 GKE？

### 對照檔案

- `README.md`
- `docs/WeaMind Infra核心架構.md`

### 使用者回答摘要

- 使用者的主結論是：K3s 對 WeaMind 來說，是介於 kubeadm 與 EKS / GKE 之間的一個務實折衷。
- 相較 kubeadm，使用者認為 K3s 更簡化，需自行安裝與組裝的元件較少，資源負擔也較低，因此比較適合單人維運。
- 相較 EKS / GKE，使用者認為 managed Kubernetes 雖然穩定、方便、可擴充，但成本更高，而且不利於展示自己對節點與叢集底層的掌握與操作能力。
- 使用者最後收斂成：選 K3s 的核心，是因為它在可操作性、客製化、實驗靈活性與成本之間，提供了一個好的折衷。

### AI 修正與補充

- 主方向是對的，而且你已經抓到這題真正的關鍵不是「哪個最強」，而是「哪個最符合 WeaMind 這個專案的規模、目標與展示需求」。
- 第一，對 kubeadm 的比較你抓得很準。從 [README.md](README.md) 與 [docs/WeaMind Infra核心架構.md](docs/WeaMind%20Infra核心架構.md) 來看，這個專案明顯偏向**小型叢集、單人維運、成本敏感**，而且希望能快速把叢集搭起來並保留足夠的實作感。這種情境下，K3s 的「單一二進位、整合度高、內建 Traefik」就很符合需求；若換成 kubeadm，雖然更接近標準裸組裝路線，但你要自己處理的安裝與整合面會更多，對這個專案來說不夠務實。
- 第二，對 EKS / GKE 的比較也對，但可以再修得更精準：問題不只是雲服務比較貴，也不只是「不利於展示能力」，而是這個 repo 本來就在展示自己怎麼建一個可控的 K8s 基礎設施。若直接用 managed Kubernetes，**很多控制平面與平台層工作會被雲端服務抽掉**，雖然生產上很合理，但和這個專案的**學習目標與作品集定位不完全一致**。
- 第三，你提到「K3s 對某些部分進行簡化，比如 etcd，它並不是真正的 cluster 狀態儲存」，這句要再修正。更準確的說法是：K3s 仍然需要有 cluster state datastore，只是它在不同部署模式下可以使用較輕量的預設方案，或使用 embedded etcd 等做法；重點不在於「它沒有真正的 cluster 狀態儲存」，而在於 K3s 把很多元件整合與簡化，降低了你建叢集的進入成本。
- 也就是說，不能把 K3s 理解成「少了 Kubernetes 本來需要的狀態儲存」，而要理解成「它仍是正規 Kubernetes distribution，只是幫你把很多平台層決策預先整合好」。
- 第四，若回到 repo 文字證據，這題最穩的收斂其實有三個支點：
- [README.md](README.md) 直接寫了 `K3s over kubeadm`，理由是單一二進位、內建 Traefik、對單人維運的小型叢集更務實。
- [docs/WeaMind Infra核心架構.md](docs/WeaMind%20Infra核心架構.md) 直接把 K3s 與成本模型綁在一起，指出 2C/4GB 的控制平面對單一 line-bot workload 已足夠，省下的成本可放到 Hetzner LB。
- 這個專案本身也是在展示從單機 Docker 遷移到可控的 K8s 架構，因此需要保留足夠的 infra 操作面，而不是把整個平台層都交給雲服務代管。
- 這題在 WeaMind 裡最小可講版可以收斂成：K3s 不是因為「比較簡單所以隨便選」，而是因為這個專案需要一個夠輕量、夠省成本、夠好維運，同時又能保留叢集操作與架構展示價值的 Kubernetes 發行版；它比 kubeadm 更務實，比 EKS / GKE 更符合這個作品集與學習目標。

## Q2

### 題目

在 WeaMind 的 K3s 叢集裡，control-plane、worker、Scheduler、kubelet 分別落在哪一側？這和昨天的 `nodeSelector.nodepool=worker` 有什麼直接關係？

### 對照檔案

- `README.md`
- `docs/WeaMind Infra核心架構.md`
- `PROGRESS.md`
- `manifests/deployment.yaml`

### 使用者回答摘要

- 使用者已能先把四個項目分成兩側：control-plane 與 Scheduler 在同一側，worker 與 kubelet 在同一側。
- 使用者能說出 control-plane 這一側主要包含 API Server、Scheduler、controller manager 與儲存 cluster state 的元件；worker 這一側的重要元件則是 kubelet。
- 使用者目前的理解是：kubelet 是 worker node 的代理，因為它能觀察與操作 node 上的資源，所以 worker 上很多實際執行相關的事情都會經過 kubelet。
- 使用者也能把昨天的 `nodeSelector.nodepool=worker` 對回今天的 control-plane / worker 分工：若不加限制，Pod 可能被排到 control-plane，破壞角色分工；因此透過在 worker node 上加 `nodepool=worker` label，再讓 Pod 只選這種 node，就能把 workload 固定在 worker。
- 使用者最後收斂成：control-plane 沒有 `nodepool=worker` 這個 label，因此不會符合這個 selector；結果就是 Pod 只會跑在 worker nodes 上。

### AI 修正與補充

- 主方向是對的，而且你已經把這題最重要的骨架講出來了：control-plane / Scheduler 是一側，worker / kubelet 是另一側；`nodeSelector.nodepool=worker` 則是把這個角色分工落到實際排程限制上。
- 第一，你提到 control-plane 裡的核心元件時，方向正確，但名稱可以再修得更精準一點：⭐️比較標準的說法是 `kube-apiserver`、`kube-scheduler`、`kube-controller-manager`，以及 cluster state datastore。面試時若要穩一點，建議直接用這組名稱。
- 第二，你對 kubelet 的理解主幹是對的，但「所有事情都要透過 kubelet」這句可以縮小一點。⭐️更準確的說法是：**kubelet 是每台 node 上的 agent**，負責 watch API Server 上已被指派給自己的 Pods，然後協調 container runtime 把 Pod 真正落地，並**持續回報 node 與 Pod 狀態**。它很重要，但不是整個 worker 上所有事情的唯一總入口。
- 第三，這題也可以更明確地跟昨天的執行鏈接起來：Scheduler 在 control-plane 這一側，只負責決定 Pod 應該去哪台 node；真正把 Pod 跑起來的是目標 node 上的 kubelet。這就是為什麼昨天一直強調不能把 Deployment / Scheduler / kubelet 混成同一層。
- 第四，你對 `nodeSelector` 的收斂是對的。`nodeSelector.nodepool=worker` 不是在告訴 kubelet 怎麼執行 container，而是在**告訴 scheduler**：可選 node 必須先通過這個 label 條件。因此只要 control-plane node 沒有 `nodepool=worker`，scheduler 在這條 workload 上就**不會**把 control-plane 當成**候選節點**。
- 第五，這裡還有一個很貼 WeaMind 的專案細節值得保留：根據 `PROGRESS.md`，這個專案觀察到 K3s worker 節點的 `ROLES` 顯示為 `<none>` 是正常的，所以不能只靠 `ROLES` 欄位去做排程限制。也因此另外補 `nodepool=worker` 這個自訂 label，才會成為一個合理且可控的做法。
- 這題在 WeaMind 裡最小可講版可以收斂成：control-plane 這一側負責叢集控制與決策，Scheduler 也在這一側；worker 這一側負責實際承載 workload，kubelet 是每台 node 上把 Pod 落地執行的 agent。`nodeSelector.nodepool=worker` 的作用，就是把這個角色分工真正轉成 scheduler 的選節點條件，避免 app workload 跑到 control-plane。

## Q3

### 題目

這個專案的 kubeconfig、SSH tunnel 與 kubectl 是怎麼串起來的？特別是 `cluster`、`user`、`context` 各自回答什麼問題，為什麼 `server` 會改成 `https://127.0.0.1:6443`？

### 對照檔案

- `PROGRESS.md`
- `README.md`

### 使用者回答摘要

- 使用者已能先抓到主骨架：kubeconfig 是 kubectl 使用的連線設定檔，本機會靠 kubeconfig 內的資訊，再透過 SSH 路徑連到 control-plane。
- 使用者目前的理解是：本機這條路徑會透過堡壘機再到 control-plane，因此 kubeconfig 裡的 `server` 改成 `https://127.0.0.1:6443`，是因為本機透過 SSH tunnel 之後，等於把遠端 API server 映射到本機的 localhost port。
- 使用者實際去看了本機 kubeconfig，已觀察到 `cluster` 底下包含 `certificate-authority-data` 與 `server`，並知道這一塊和連線資訊有關。
- 使用者目前還不夠確定 `cluster`、`user`、`context` 三者各自最精準的語意，只知道 `context` 底下會把 `cluster` 與 `user` 組在一起，而目前看到的值是 `default`。
- 使用者也補出一個很重要的對照：在堡壘機上，因為不是走同一條本機 SSH tunnel，所以 `server` 不會是 `127.0.0.1`，而會更接近直接打 control-plane 的內網 API 位址。

### AI 修正與補充

- 主方向是對的，而且你已經抓到這題真正的核心不是背 kubeconfig 欄位名，而是把「本機怎麼連到叢集」說成一條完整路徑。
- 第一，回到 `PROGRESS.md`，這個 repo 其實有兩條很直接的證據：
- 它明確記了把 control-plane 上的 K3s kubeconfig 複製到本機，放到標準位置 `~/.kube/config`。
- 也明確記了本機是用 SSH tunnel `-L 6443:127.0.0.1:6443` 存取 API server，因此 kubeconfig 的 `server` 被改成 `https://127.0.0.1:6443`。
- 第二，`cluster`、`user`、`context` 這三個概念可以收斂成三個問題：
- `cluster` 回答的是「我要連哪個 Kubernetes API server，以及我要怎麼驗證這台 API server 的身分」。所以這裡常會看到 `server` 與 `certificate-authority-data`。
- `user` 回答的是「我用什麼身分去登入這個 cluster」。所以這裡常會放 client certificate、token 或其他認證資訊。
- `context` 回答的是「目前要用哪個 cluster + 哪個 user 的組合」，有時也會順便帶 namespace。也就是說，`context` 比較像一個方便切換的『連線組合』，不是新的基礎元件。
- 第三，你看到 `default` 這個值時會覺得有點空，這很正常。它不代表有特殊魔法，只是這份 kubeconfig 的命名比較樸素而已。重點不是名字叫不叫 `default`，而是它實際指向哪個 cluster、配哪個 user。
- 第四，`server` 之所以改成 `https://127.0.0.1:6443`，不是因為 kubectl 好像「在 control-plane 本機上執行」，而是因為 SSH tunnel 在你本機開了一個 local port 6443，然後把這個 local port 轉發到遠端 API server。因此 kubectl 眼中看到的是本機 localhost，但它實際上是透過 tunnel 在打遠端的 control-plane API。
- 換句話說，`127.0.0.1` 指的是「kubectl 的連線入口在本機」，不是指「Kubernetes API server 真的部署在你這台 Mac 的本機」。
- 第五，你補的堡壘機對照也很有價值。若在堡壘機上直接打 control-plane 內網 IP，那 kubeconfig 的 `server` 就不一定要改成 localhost。這剛好說明 kubeconfig 裡的 `server` 不是抽象固定值，而是會跟你從哪台機器、透過哪條網路路徑連進叢集直接相關。
- 這題在 WeaMind 裡最小可講版可以收斂成：本機的 kubectl 會讀 `~/.kube/config`，其中 `cluster` 定義 API server 位址與 CA、`user` 定義登入身分、`context` 決定當前要用哪組 cluster + user。因為這個專案是透過 SSH tunnel 把遠端 control-plane API 映射到本機 `127.0.0.1:6443`，所以 kubeconfig 的 `server` 才會改成 localhost；這代表的是連線入口被本機轉發，不代表 API server 真正在本機執行。

## Q4

### 題目

如果今天要補 Deployment 的 rollout 細節，你會怎麼區分 `kubectl rollout status`、Deployment conditions 與 rolling update strategy 這三者各自在回答什麼問題？

### 對照檔案

- `manifests/deployment.yaml`
- `PROGRESS.md`
- `learning/lessons/2026-03-16-deployment-basics/04-report.md`
- `learning/lessons/2026-03-17-pod-management-and-probe/04-report.md`

### 使用者回答摘要

- 使用者已能先抓到 `kubectl rollout status` 的主用途：它通常要接一個具體資源，最常見是 Deployment，用來看這次 rollout 是否成功完成。
- 使用者目前的理解是：`rollout status` 回答的重點是「這次 rollout 的結果如何」，但因為目前幾乎只看過 `successfully rolled out`，所以還不確定其他常見狀態與 Deployment conditions 的關係。
- 使用者對 rolling update strategy 的直覺方向是對的：新舊 ReplicaSet 之間不是一次全切，而是漸進式交接；例如新版 Pod 先加一個，總數暫時變多，再把舊版減一個，逐步把新版補上、舊版降下來。
- 使用者目前還不夠確定 rolling update strategy 具體有哪些策略，也還不夠確定 conditions 與 rollout status 到底各自站在哪一層。

### AI 修正與補充

- 你的核心直覺其實已經抓到了，尤其是你對 rolling update「不是一次全切，而是新舊逐步交接」的理解，這是這題最重要的主幹。
- 第一，先把三者各自回答的問題切開：
- `kubectl rollout status` 回答的是「這次 rollout 目前有沒有走到完成狀態」。它站在 CLI 觀察入口的層級，給你一個相對濃縮的結論，像 `successfully rolled out`，或告訴你還在等待更新完成。
- Deployment conditions 回答的是「Deployment 物件目前有哪些狀態訊號」。它是 Deployment status 裡比較結構化的狀態資訊，常見像 `Available`、`Progressing` 這類條件，幫你判斷 controller 目前怎麼看這個 Deployment。
- rolling update strategy 回答的則是「Deployment 應該用什麼更新規則去交接新舊 Pod」。它站在 spec / 策略設定層，不是在回報結果，而是在定義更新時允許多少額外 Pod、允許多少舊 Pod 先下線。
- 第二，所以這三者不是同一件事的三種名稱，而是三個不同層次：
- strategy 是「怎麼更新」
- conditions 是「物件目前呈現哪些狀態訊號」
- rollout status 是「從使用者角度濃縮後，這次 rollout 現在算不算完成」
- 第三，你剛剛猜 conditions 很像 success / pending，這方向接近但還不夠精準。比較穩的說法是：`successfully rolled out` 比較像 CLI 對多個 Deployment 狀態訊號做出的收斂結論；conditions 則是 Deployment 物件本身較細的狀態欄位，不是單純只有 `success` 或 `pending` 這種一維結果。
- 第四，回到 WeaMind 的 `manifests/deployment.yaml`，你會發現這份 YAML 沒有明寫 `strategy`。這代表它目前使用的是 Deployment 的預設 RollingUpdate 策略，而不是完全沒策略。也就是說，你今天在腦中想像的「先加新的、再減舊的」那條路，其實正是這個專案預設會走的更新模型。
- 第五，RollingUpdate 之外，Deployment 還有另一個常見策略叫 `Recreate`。`Recreate` 的概念比較接近先把舊 Pod 全部停掉，再把新 Pod 建起來；相較之下，RollingUpdate 才是你剛剛描述的那種漸進式交接。這也說明 strategy 不是在描述結果，而是在描述 controller 被允許怎麼做更新。
- 第六，你前面提到 rollout 指令除了 Deployment 外還有別的資源，這個印象也是對的。常見還包含 DaemonSet、StatefulSet 等 controller 類資源。不過今天在 WeaMind 裡，我們先聚焦 Deployment 就夠，不需要把所有 controller 一次混進來。
- 這題在 WeaMind 裡最小可講版可以收斂成：`kubectl rollout status` 是用來看 Deployment 這次 rollout 有沒有完成；Deployment conditions 是物件本身較細的狀態訊號；rolling update strategy 則是在定義更新時新舊 Pod 要怎麼交接。WeaMind 這份 Deployment 沒有明寫 strategy，因此目前走的是預設 RollingUpdate，而不是 `Recreate`。
