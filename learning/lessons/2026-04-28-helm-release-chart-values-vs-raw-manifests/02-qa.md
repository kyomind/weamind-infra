### 使用者回答摘要

### AI 修正與補充

- 你的方向是對的，但第一小題要切得更準。W7 當時手上**不是 raw YAML**，也不能說「沒有 chart」。更精確地說，我們手上有的是：**一個來自遠端 chart repository 的 chart 參考、準備安裝的 release 名稱、target namespace，以及預設 values 或少量 override。**
- 這裡最容易混的是 `chart` 和 `chart repo`。`chart` 是要被安裝的套件內容；`chart repo` 是分發這個 chart 的地方。你可以把它想成：repo 像套件來源，chart 才是被抓下來安裝的那個包。
- 第二小題你剛剛說「最小流程不就是下指令嗎」，這就是 Helm 這題最值得補清楚的地方。`helm install` 背後至少有這條最小鏈：**定位 chart -> 取回 chart 內容 -> 用 values render templates -> 把 render 後的 manifests 送進 Kubernetes API -> 記錄成一個 release。** 所以它不只是把一條指令交給 cluster；它先做了一層本地或 Helm 端的模板展開與 release 管理。
- 第三小題也是你這次問得最好的地方：**render 出來的 YAML 通常不會自動寫回你的 Git repo。** 這也是為什麼當時安裝完之後，infra repo 沒有任何 YAML 檔案被改掉。
- 更準確地說，這批 render 後的 manifests 會被 Helm 送到 Kubernetes API 建立成資源；同時 Helm 會把這次 release 的紀錄也存進 cluster。以 Helm 3 來說，release metadata 預設常見是存在 cluster 裡的 `Secret`。所以你如果問「那批 YAML 到底去哪了」，比較穩的答案是：**它沒有自動落回 Git repo，而是被送進 cluster；release 對應的 manifest 與 revision 資訊則由 Helm 存在 cluster 內的 release record 裡。**
- 這也解釋了為什麼 Helm 不只是「比較方便的 `kubectl apply`」。`kubectl apply` 比較像你自己拿已存在的 YAML 去套；Helm 則是先根據 chart 與 values 產生 YAML，再套進 cluster，還多了一層 release history 與 rollback 能力。
- 如果你想在事後把那批 render 後的 YAML 看出來，也不是完全看不到，而是要**向 Helm 要**，不是回 Git repo 找。最常見的方向是像 `helm get manifest <release>` 這類做法；另一個角度則是直接看 cluster 裡 Helm 儲存的 release record。
- 若把這題壓成最短版本，可以這樣講：W7 我們不是直接拿 raw YAML 安裝，而是從遠端 chart repo 取用一個 chart，給 Helm 用預設 values 或少量設定 render 成 Kubernetes manifests，再送進 cluster，並記錄成一個 release。那批 YAML 不會自動寫回 infra repo；它主要是被送去建立叢集資源，而 release 對應的 manifest 與 revision 資訊則由 Helm 存在 cluster 裡。

### AI 修正與補充

- 你的主線是對的，而且前兩個答案很穩。`image tag` 幾乎是最典型的 values 候選，因為它直接對應 deploy version；`replicas` 也很合理，因為它直接對應環境負載與容量需求。
- 第三個你後來補的 `PROCESSING_LOCK_TTL_SECONDS` 其實也是合理候選，這比你一開始把整個 ConfigMap 當成「不適合暴露」要更精準。因為 **不是 ConfigMap 整包都不適合做 values，而是要拆欄位看。**
- ⭐️對回目前 repo，若只挑 3 個最值得參數化的欄位，我會給這組更穩的答案：
- `image.tag`：對應 deploy version，最典型。
- `replicaCount`：對應容量與可用性。
- `ingress.host` 或 `BASE_URL`：目前 repo 裡寫死成 `k8s.kyomind.tw`，這類 domain / base URL 很常隨環境改變，所以也很適合 values。
- 你的 `PROCESSING_LOCK_TTL_SECONDS` 我會放在「次高價值候選」。它確實可以做成 values，尤其當不同環境或不同 debug 階段需要調整時；只是若要選最前面的 3 個，`host` / `BASE_URL` 這種環境差異 usually 更常見、更典型。
- 再來校正第二小題。你把整個 ConfigMap 放進「不適合暴露」這邊，這就太粗了。像目前 `BASE_URL`、`ENV`、甚至 `PROCESSING_LOCK_TTL_SECONDS`，其實都很像 Helm values 候選。更穩的講法應該是：**不是某個 resource kind 整包適不適合，而是某些欄位是否值得暴露。**
- ⭐️若對回目前 repo，兩類不應輕易暴露成 values 的東西，我會這樣收：
- ⭐️敏感值：例如 Secret 裡的 DB 密碼、token、access key。這不是因為 Helm 完全不能帶 secret，而是因為「把它當成一般 values 任意外露」通常會把安全邊界弄髒。
- ⭐️**結構性邊界欄位**：例如 `Service.selector`、`Deployment.selector.matchLabels`、某些固定命名、或 chart 內部資源關聯很強的欄位。這些不是完全不能參數化，而是亂 expose 後，很容易把 chart 的內部一致性拆壞。
- 像你提到的 DB 連線 URL，要再切細一點。若它包含敏感資訊，當然不該隨便暴露；但如果像目前 repo 這樣是 `POSTGRES_HOST`、`POSTGRES_PORT`、`POSTGRES_DB`、`POSTGRES_USER` 分開放在 ConfigMap，它們本身不一定都屬於「完全不該 values 化」的類型。真正要避免的是把高風險或高耦合的欄位，沒有邊界地全部丟進 values。
- 你第三小題的 Jinja 類比是好的。最短版本可以這樣講：**`values` 不是任意 yaml merge，因為只有 chart template 事先暴露出來的欄位，Helm 才有地方可以帶值。** 沒有在 template 裡留入口的欄位，你不能光靠 values 就憑空改掉整份 manifest 的任意位置。
- 若把 Q2 壓成最短版，可以這樣回答：在 WeaMind 目前這份 repo 裡，最值得做成 values 的通常是 `image tag`、`replicas`、以及 `ingress.host` / `BASE_URL` 這類環境差異明顯的欄位；`PROCESSING_LOCK_TTL_SECONDS` 也可以是次高價值候選。相對地，像 Secret 內的敏感值，或 selector / label 這類牽涉 chart 內部一致性的結構欄位，不應輕易暴露。這也反過來證明 `values` 不是任意 yaml merge，而是只能填進 chart template 事先留好的入口。

## Q3

### 題目

請對照 Helm 的 `release` 概念與目前 repo 的資源結構，說明如果 deploy 壞掉，Helm rollback 和 `kubectl rollout undo deployment/...` 各自能救回什麼、救不回什麼。

### 答題引導

1. 先說 `kubectl rollout undo` 主要是在對哪個資源物件做回退。
2. 再說 Helm rollback 為什麼是以 release 為單位，而不是只看 Deployment。
3. 最後用目前 WeaMind 的 Deployment、Service、Ingress 脈絡收斂一句：兩者恢復邊界哪裡不同。

### 對照檔案

- learning/prework/2026-04-28-helm-core-model-basics.md
- manifests/deployment.yaml
- manifests/service.yaml
- manifests/ingress.yaml

### 使用者回答摘要

- 使用者已正確抓到大方向：`kubectl rollout undo` 的作用範圍主要在 `Deployment` 這類 rollout controller 管理的工作負載，核心是在把 Pod template 對回前一版，而不是回退整套服務。
- 使用者也正確抓到 Helm rollback 的核心差異：它不是只看 Deployment，而是看整個 release revision，因此理論上可把 Service、Ingress 等同一個 release 管理下的資源一起回退。
- 使用者目前最想釐清的補充疑問是：如果某次 Helm revision 實際上只有改 Deployment / Pod 相關內容，而 Service、Ingress 沒變，那 Helm 會怎麼看待這個 revision？那些沒變的部分，是否仍然算這個 revision 的內容。

### AI 修正與補充

- 你的主線是對的，但第一小題可以再切得更準。`kubectl rollout undo deployment/...` 不是直接對「Pod 資源」做版本管理，而是對 **Deployment 的 rollout history** 做回退。
- 更白話地說，它會把 Deployment 的 Pod template 與相關 rollout 狀態退回前一版，然後由 Deployment 控制器重新建立對應 Pods。
- ⭐️所以最穩的說法不是「它控制 Deployment 和 Pod 的內容」，而是：**它回退的是 Deployment 這個 workload controller 的版本歷史，Pod 則是跟著新的舊版 template 被重建出來。**
- ⭐️第二小題你的方向也是對的。Helm rollback 比 `rollout undo` 大一層，因為 Helm 看的是 **release revision**，不是**單一 controller 的 rollout revision**。只要某個資源當時是由這個 Helm release 管理，且該 revision 的 manifest 裡有它，rollback 時它就屬於回退範圍。
- 所以對回目前 WeaMind 脈絡，若今天只有 [manifests/deployment.yaml](manifests/deployment.yaml) 出問題，而 [manifests/service.yaml](manifests/service.yaml) 與 [manifests/ingress.yaml](manifests/ingress.yaml) 都沒變，那 `kubectl rollout undo deployment/weamind` 只會處理 Deployment 這一層；Helm rollback 則是回到某個 release revision 對應的**整份 manifest 集合**。
- 你後面的補充問題很重要，而且答案是：**對，你可以這樣理解。** 某個 Helm revision 可以只改 Deployment / Pod 相關欄位，其他資源雖然沒變，但仍然屬於那個 revision 的整體內容。
- 這一段我另外整理到 Note，因為它比較像 Helm revision 心智模型補充，不適合塞太長在 QA 主答案裡。可直接回看 [learning/lessons/2026-04-28-helm-release-chart-values-vs-raw-manifests/05-note.md](learning/lessons/2026-04-28-helm-release-chart-values-vs-raw-manifests/05-note.md)。
- 若把這題壓成最短版，可以這樣回答：`kubectl rollout undo` 回退的是 Deployment 這類 rollout controller 的歷史，主要影響 Pod template 與重建出來的 Pods；Helm rollback 回退的是整個 release revision，理論上可涵蓋 Deployment、Service、Ingress 等所有納入這個 release 的資源。若某次 revision 實際只改了 Deployment，那其他沒變的資源仍然屬於該 revision 的內容，只是 rollback 時它們和上一版沒有差異，因此通常不會出現可見變動。
