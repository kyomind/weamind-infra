### AI 修正與補充

- 你這題的核心方向其實是對的，但要收得更準一點：`kubectl get` 第一眼最常拿到的，不是 YAML 級設定細節，而是 **高層狀態摘要**，例如 `STATUS`、`READY`、`RESTARTS`、`AGE` 這類欄位。它回答的是「目前哪個資源看起來不對勁」，而不是「為什麼它不對勁」。
- 所以 `get` 適合當第一輪，是因為它 **便宜、快、視野廣**。你可以先用它快速掃一圈，判斷是只有單一 Pod 異常、整個 Deployment 有問題，還是 namespace 裡多個資源都不健康。它很適合做第一層縮圈，但不適合直接拿來做最後定案。
- 只看 `get` 還少了兩種重要證據：第一，是 **更細的 Pod / resource 描述證據**，例如 container state、reason、conditions、events；這通常要靠 `kubectl describe`。第二，是 **更完整的時間序列或應用輸出證據**，例如 event 順序或 app log；這些也不是 `get` 最擅長提供的。
- 你提到 `describe` 像是「Kubernetes 怎麼看這個東西」，這個方向是對的，而且可以當成暫時口訣。更準一點地說：`get` 比較像 **列表式狀態摘要**，`describe` 比較像 **針對單一資源的展開式 Kubernetes 視角說明**。
- 先不用把兩者的所有差異都塞進 Q1；你剛剛指出這塊還不夠穩，這很合理，我們把 `get` vs `describe` 的更完整對照另外整理進 `05-note.md`，避免這題答案膨脹。

## Q2

### 題目

`kubectl describe pod` 和 `kubectl get events --sort-by=.lastTimestamp` 都在看 Kubernetes 層的資訊，但它們各自更適合回答什麼問題？

### 答題引導

1. 先分別說出 `describe` 比較像在看什麼。
2. 再說 `events` 為什麼更像時間序列，而不是靜態狀態摘要。
3. 最後補一句：兩者怎麼互補，而不是互相取代。

### 對照檔案

- `darkmind/README.md`
- `darkmind/scenarios/image-pull-error.yaml`

### 使用者回答摘要

- 使用者已經抓到 `describe` 是以單一 resource 為中心展開的 Kubernetes 視角，這個理解是對的。
- 使用者也提出一個很好的推測：`events` 可以視為把多個 resource 發生過的事件拉到同一個時間序列裡觀察，而不只侷限於單一 Pod。
- 使用者目前還不穩的地方主要在 `events` 本身到底是什麼：它是不是 resource、是不是只記錯誤、和 `describe` 裡的 `Events` section 到底是什麼關係。
- 使用者對兩者互補方式的回答是合理的：先用 `events` 看最近整體發生了什麼，再針對其中較關鍵的 resource 做 `describe` 深挖。

### AI 修正與補充

- 你這題的主體回答其實已經很不錯，尤其是你把 `describe` 和 `events` 的視角差異抓到了。可以先收成一句話：`describe` 比較像 **單一 resource 的展開式說明**，`events` 比較像 **跨 resource 的時間序列線索**。
- 更精準地說，`kubectl describe pod ...` 主要回答的是：「**這個 Pod / resource 本身現在是什麼狀態，Kubernetes 對它記了哪些重要描述與事件**？」你會在裡面看到 container state、conditions、reason，以及和這個 resource 高度相關的 `Events`。
- `kubectl get events --sort-by=.lastTimestamp` 主要回答的則是：「**最近整個 namespace 裡，Kubernetes 先後記錄了哪些事件？**」所以它的價值不是單點展開，而是補出時間順序與橫向關聯，特別適合你想知道「剛剛到底先發生了什麼、後發生了什麼」。
- 你問 `Events` 是不是 resource，答案是：**是，`Event` 本身就是 Kubernetes API 裡的一種 resource kind**。只是它通常是輔助型、短生命週期的紀錄資源，不像 `Pod`、`Deployment` 那樣是你主動管理的主要工作負載物件。
- 你問它是不是只收錯誤，答案是：**不是，只要值得記錄的狀態變化，正常或異常都可能有 event**。例如 successful pull、scheduled、started 這類正常流程也可能有；失敗時則會看到例如 image pull back-off、probe failed 之類的 warning event。也就是說，event 不是「錯誤清單」，而是 Kubernetes 記錄下來的事件流，只是 debug 時我們常特別關注 warning 與 failure 訊號。
- 所以兩者的互補關係可以再收得更準一點：先用 `events` 看「**最近整體發生了什麼**」，再用 `describe` 看「**這個特定 resource 現在到底是什麼狀態，Kubernetes 怎麼描述它**」。反過來也常成立：若你已經先靠 `get` / `describe` 鎖定 Pod，再回頭用 `events` 補時間序列，也很合理。
- 這也順手回答你剛剛的直覺：`describe` 裡的 `Events` section，和 `kubectl get events` 並不是兩套完全不同的資訊來源；它們都和 Kubernetes 記錄的 event 有關，只是前者是 **以單一 resource 為中心的摘錄**，後者是 **以 event 列表為中心的觀察方式**。

### 題目

為什麼 Day 1 要先建立 `darkmind-healthy` 的健康基準，再套壞情境，而不是一開始就只看錯誤 Pod？

### 答題引導

1. 先回答健康基準幫你建立的是哪種比較基線。
2. 再回答這件事如何幫助你之後判讀 `get`、`describe` 或 `events` 的輸出。
3. 最後補一句：這個做法和真正 production debug 有什麼相通之處。

### 對照檔案

- `darkmind/healthy.yaml`
- `darkmind/README.md`

### 使用者回答摘要

- 使用者已抓到健康基準的核心角色：先知道正常情況下 `get`、`describe`、`events` 大致長什麼樣，之後看到錯誤狀態時，才知道哪些欄位、哪些訊號是偏離基準的新資訊。
- 使用者也明確指出：若只看錯誤 Pod，而沒有正常基準，很容易不知道哪些訊號是錯誤特有的，哪些只是平常就會出現的正常輸出。
- 使用者目前雖然還沒有把 production debug 的類比完全講滿，但已經抓到很重要的比較思路：正常與異常的對照，能讓問題意識更清晰。

### AI 修正與補充

- 這題你的主體答案是對的，而且抓到最關鍵的 debug 思維：**先知道正常長什麼樣，才知道異常到底偏離了哪裡**。
- 健康基準建立的不是抽象安全感，而是 **可比較的基線**。例如健康 Pod 時，`kubectl get` 的 `READY`、`STATUS`、`RESTARTS` 通常會長什麼樣；`kubectl describe` 裡哪些欄位可能穩定正常、哪些 event 屬於正常生命週期；有了這個基線，之後看到 image pull fail、probe fail、restart 增加時，你才知道哪些訊號是新出現的異常證據。
- 你提到「如果正常時是這樣，出 bug 時長得不一樣，我才知道哪裡偏掉」這句非常重要。這其實就是很多真實 debug 的核心：不是只盯著錯誤訊息，而是先找 **和健康基準相比，哪裡開始分岔**。
- 若把它拉回 production debug，這個思路也完全成立。真實環境裡我們常做的事，不是憑空猜錯，而是先找一個健康的對照組，例如另一個正常 Pod、前一天正常的輸出、健康 service 的 endpoints、或已知正常的 rollout 狀態。也就是說，Darkmind Day 1 練的不是 toy skill，而是 production 也會用到的比較式排查方法。
- 所以這題可以收成一句話：**健康基準不是多餘前置作業，而是後續辨認異常訊號的比較座標系**。
