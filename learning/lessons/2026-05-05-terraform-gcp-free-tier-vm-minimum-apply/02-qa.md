# 2026-05-05 Terraform GCP Free Tier VM Minimum Apply QA

> 原則：這份 QA 是 post-implementation 收斂，不在實作前搶主體。

## Q1

### 題目

如果今天的 Step 1 停在 preflight gate，這代表問題最可能落在哪一層，而不是哪一層？

### 答題引導

1. 先回答：今天的 preflight gate 在驗證哪些平台或工具前提？
2. 再回答：如果這一步卡住，為什麼不能直接怪 Terraform HCL 寫錯？
3. 最後補一句：這種卡點對後續 `plan` / `apply` 的可信度有什麼影響？

### 對照檔案

- `.privatedocs/Phase2三週計畫.md`
- `references/phase2/w9-iac-minimum-spec.md`
- `terraform/gcp-free-tier-vm/README.md`

### 使用者回答摘要

- 使用者回答的主軸是對的：Step 1 主要是在驗證 GCP CLI 與 Terraform CLI 等工具前提是否已具備。
- 使用者也正確指出，若 preflight gate 卡住，不能直接怪 Terraform HCL 寫錯，因為更前面的工具或平台層還沒有正常運作。
- 對 `plan` / `apply` 的影響方面，使用者的理解是：若這一層卡住，就可能無法正常連到雲端資源，因此後續 `plan` 也很難可信地執行。

### AI 修正與補充

- 這題可以再講得更精準一點：Step 1 驗證的不是只有 Terraform CLI 與 gcloud CLI 是否存在，還包含 gcloud auth、current project、billing 狀態，以及 Compute Engine API 是否已可用。
- 所以如果今天停在 preflight gate，問題最可能落在「平台前置條件層」或「工具 / 認證層」，而不是先落在 HCL 語法或 resource schema 層。
- 不能直接怪 HCL 的原因是：這時 Terraform 甚至可能還沒有走到真正讀 provider、查 API、或準備建立資源的階段；你看到的失敗訊號，可能只是本機工具缺件、尚未登入、billing gate、或 API 尚未啟用。
- 對後續 `plan` / `apply` 的影響，最精準的說法不是單純「一定不能跑」，而是「即使勉強執行，結果也不可信」，因為失敗原因可能根本和 HCL 無關，而是前置條件沒過，這會讓你無法正確判斷問題到底出在 Terraform 設定還是平台本身。
- 若要把這題壓成面試可用的一句話，可以這樣說：**preflight gate 卡住，代表問題先落在工具、認證或平台前置條件，而不是先落在 Terraform HCL；在這種情況下，後續 `plan` / `apply` 就算執行，也沒有足夠可信度拿來判斷設定本身對不對。**

## Q2

### 題目

對照今天實際留下的 `.tf` 骨架，你會怎麼說明第一版為什麼先收斂成 provider、variables、compute instance、必要 firewall 與 outputs，而不是一開始就展開更多 GCP 資源？

### 答題引導

1. 先回答：今天的最小實作目標到底是什麼？
2. 再回答：哪些資源是為了對齊 Free Tier VM 規格而必要，哪些是刻意不做的擴張？
3. 最後補一句：這樣的收斂對面試或重講有什麼好處？

### 對照檔案

- `references/phase2/w9-iac-minimum-spec.md`
- `terraform/gcp-free-tier-vm/README.md`

### 使用者回答摘要

- 使用者回答的主軸是：今天的最小實作目標，就是先完成一台可以獨立跑起來、而且符合 Free Tier 邊界的 VM。
- 使用者也抓到，VM 不可能脫離網路單獨存在，因此最小版本仍需要補上必要的網路相關設定。
- 在 Free Tier 規格對齊上，使用者有正確提到幾個關鍵點：external network tier 要用 `STANDARD`、disk 要用 HDD 類型而且容量不要超過 30GB，因此這次收斂成 `pd-standard` 與 25GB。
- 使用者也提到 region / zone 需要落在美國可接受區域內，並指出這次實作有刻意收斂在受 Free Tier 支援的美國區域。
- 最後使用者認為，這樣的收斂主要是在展示對 Terraform 基本操作與最小 IaC workflow 的掌握，而不是故意把更多雲端資源一次展開。

### AI 修正與補充

- 你的主方向是對的，這題最重要的核心就是：今天的目標不是做「完整 GCP 架構」，而是做「一版最小但真的可執行的 Free Tier VM Terraform 練習」。
- 這裡可以再講得更精準一點：第一版收斂成 provider、variables、compute instance、必要 firewall 與 outputs，是因為這五層剛好足以支撐從宣告、輸入、建資源、暴露對外流量，到最後觀察結果的最小閉環。
- 其中哪些是必要的：provider 與 variables 是 Terraform 能真正操作 GCP 的入口；`google_compute_instance` 是主體；兩條 firewall 是為了讓帶 tag 的 VM 能吃到 HTTP / HTTPS 規則；outputs 則是為了在 apply 後快速驗證結果。
- 哪些是刻意不做的擴張：今天沒有展開自建 VPC、subnetwork、IAM、service account、startup script、自動化配置、module 化或多環境拆分，因為那會把 lesson 重心從「最小可驗證」拉成「完整雲端設計」。
- 你剛提的 Free Tier 規格也可以再修準成一句完整說法：這次最重要的核對點是 `machine_type = e2-micro`、region / zone 落在可接受的美國區域、disk 使用 `pd-standard` 且容量 25GB、external network tier 為 `STANDARD`。
- region 這裡不是單純「美東」而已，更精準是：Free Tier 支援的是特定美國區域，這次實作收斂在 `us-east1` / `us-east1-b`，屬於可接受邊界之一。
- 若要把這題壓成面試可用的一句話，可以這樣說：**第一版先收斂成 provider、variables、VM、必要 firewall 與 outputs，是因為今天的目標是完成一個符合 Free Tier 邊界、可 plan、可 apply、可驗證的最小 Terraform workflow，而不是過早展開完整的 GCP 網路與 IAM 設計。**

## Q3

### 題目

如果今天真的成功做到 `plan` / `apply`，你會用哪幾個最小證據證明這台 VM 沒偏離 Free Tier 邊界，而且資源真的有被建出來？

### 答題引導

1. 先列出和 VM 規格直接相關的 3 到 5 個核對點。
2. 再回答：哪些證據是在 Terraform 輸出裡看得到，哪些需要從 GCP resource 資訊再確認？
3. 最後補一句：這些證據之後怎麼幫你講 drift 或手動修改風險？

### 對照檔案

- `references/phase2/w9-iac-minimum-spec.md`
- `terraform/gcp-free-tier-vm/README.md`

### 使用者回答摘要

- 使用者先列出了幾個和 Free Tier 直接相關的核對點：region / zone、boot disk 規格、external network tier，以及 `machine_type = e2-micro`。
- 在「哪些證據從 Terraform 輸出就看得到」這一段，使用者有正確意識到目前 apply 後的 output 已因 destroy 而消失，所以改回頭對照 implementation 與當時 CLI 輸出來判斷。
- 使用者指出，至少 `machine_type` 與 `zone` 這兩類資訊可以直接從 Terraform 輸出或 apply 結果看出來。
- 使用者也正確分辨出：像 disk 與 network 這類更細的規格，通常要靠 GCP resource 資訊或其他更細的 state / resource 檢查才能補齊。
- 對 drift 風險的理解上，使用者的主軸是：先知道正確規格是什麼，之後如果實際資源偏離這些規格，就能判斷它已經和預期狀態不符。

### AI 修正與補充

- 你的方向是對的，這題真正要證明的是兩件事要分開講：第一，規格沒偏離 Free Tier；第二，資源真的有被建立出來。
- 如果把最小證據壓成 3 到 5 個核對點，這次最值得講的是：`machine_type = e2-micro`、`zone = us-east1-b`、disk `type = pd-standard` / `size = 25`、external network tier `STANDARD`、以及 apply 後真的拿到 external IP。
- 哪些證據可以從 Terraform 輸出直接看到：`instance_name`、`instance_zone`、`machine_type`、`project_id`，以及 apply 完成後的 `external_ip`。
- 哪些證據需要從 GCP resource 或 state 再確認：disk 的實際 `type` / `size`、network tier、firewall 規則細節、以及 VM 在雲端上是否真的進入 `RUNNING`。
- 這題還可以再補一句：`apply complete` 本身只能證明 Terraform 認為建立成功，但如果要更有說服力，就要再加上 `gcloud` 查詢或 `terraform state show` 這類第二層證據，去驗證資源真的存在而且規格沒跑掉。
- 你最後講 drift 的方向也是對的，可以再修成更精準的版本：先把「正確規格基準」講清楚，之後若有人手動改了 machine type、disk、network tier 或 firewall，這些都會變成可對照的 drift 線索。
- 若要把這題壓成面試可用的一句話，可以這樣說：**證明這台 VM 沒偏離 Free Tier，至少要同時拿出規格證據和存在證據；規格證據包含 `e2-micro`、可接受 zone、`pd-standard` 25GB、`STANDARD` network tier，存在證據則包含 apply 後拿到 external IP，以及用 GCP resource / state 再確認資源真的存在。**

## Q4

### 題目

今天你會怎麼用自己的話區分 HCL、plan、apply、state 這四者各自扮演的角色？

### 答題引導

1. 先回答：HCL 在這次練習裡代表什麼。
2. 再回答：plan 與 apply 的差別是什麼，為什麼不用 `-out` 時 apply 會重新計算。
3. 最後回答：state 為什麼不是單純把 HCL 再存一份，而是 Terraform 對真實世界狀態的記錄。

### 對照檔案

- `terraform/gcp-free-tier-vm/*.tf`
- `learning/lessons/2026-05-05-terraform-gcp-free-tier-vm-minimum-apply/05-note.md`

### 使用者回答摘要

- 使用者回答的第一個主軸是正確的：HCL 在這次練習裡就是用來定義目標規格與資源宣告的語言。
- 在 plan / apply 的差別上，使用者也抓到重點：plan 是先根據當下條件去推算這次執行會產生什麼差異，apply 則是把要做的動作真正執行出去。
- 對 `-out` 的理解上，使用者也正確指出：若沒有先把 plan 存下來，apply 前會再依據當下的雲端狀態與 Terraform 規格重新計算一次；若有 `-out`，則可以直接執行當時保存下來的那份結果。
- 在 state 的角色上，使用者已經抓到核心：state 不是單純重存 HCL，而是 Terraform 用來對照 Terraform 規格與真實雲端資源之間對應關係的記錄，這會影響 Terraform 判斷是要新建還是更新。

### AI 修正與補充

- 這題你的方向已經很接近完整答案，我只把幾個詞修準。
- 第一，HCL 更精準的說法不是只有「定義規格的語言」，而是：**HCL 是你用來描述目標基礎設施狀態的宣告式語言。** 也就是說，你不是在寫操作步驟，而是在寫「你希望最後世界長成什麼樣子」。
- 第二，plan 不是單純「先確認 state 再比對雲端」而已，更精準的說法是：Terraform 會綜合 HCL、輸入值、state，以及 provider 從雲端查回來的當前資訊，算出這次如果執行，會新增、修改或刪除哪些東西。
- 第三，apply 的角色不是去執行「檔案本身」，而是去執行 Terraform 根據目前條件算出來的變更動作；所以不用 `-out` 時，apply 會先重算一次最新 plan，再依那次結果執行。
- 第四，state 之所以不是 HCL 的備份，是因為裡面會包含很多 HCL 裡原本沒有的實際值，例如 `instance_id`、`creation_timestamp`、`cpu_platform`、`network_ip`、`nat_ip`，以及 Terraform 用來追蹤資源關係的識別資訊。
- 你最後提到的「建立新的還是 update」這個點很好，可以再往前補一句：Terraform 就是靠 state，才知道某個 HCL 宣告目前對應到哪個真實雲端資源，不然它很難正確判斷現在應該 create、update 還是 destroy。
- 若要把這題壓成面試可用的一句話，可以這樣說：**HCL 是我宣告目標狀態的語言，plan 是 Terraform 根據 HCL、輸入值、state 與雲端現況算出的差異預覽，apply 是把這份差異真正執行出去，而 state 則是 Terraform 用來記錄目前真實資源狀態與資源對應關係的依據。**
