## Q1

### 題目

如果今天給你一個壞 Pod 情境，你在第一步要怎麼決定先看哪一種證據？

### 答題引導

1. 先回答第一步的目標是什麼：找完整答案，還是先縮小問題範圍。
2. 再回答你會怎麼判斷應先看 `get` / `describe` / `events`，還是先看 `logs` / `rollout`。
3. 最後補一句：什麼情況下你不會一開始就直接 `exec` 進去。

### 對照檔案

- `darkmind/README.md`
- `darkmind/scenarios/image-pull-error.yaml`
- `darkmind/scenarios/crash-loop.yaml`
- `darkmind/scenarios/bad-rollout-02-bad.yaml`

### 使用者回答摘要

- 使用者明確把第一步目標放在 **先縮小問題範圍**，而不是一開始就想直接找到完整答案；理由是 Kubernetes 的因果鏈很長，必須先判斷問題大致落在哪一層。
- 使用者目前的預設順序是先看 `get`、`describe`、`events` 這組，先辨認錯誤形式與目前卡在哪個環節，再決定是否往 `logs` 或 `rollout` 縮圈。
- 使用者也有把 `CrashLoopBackOff` 和「Pod 已經有跑起來，但 container 內部可能有問題」這條線抓出來，並認為這種情況通常仍會先看 `describe`，再看 `logs`。
- 對於什麼情況下不會先 `exec`，使用者已抓到一個重要邊界：如果連流量是否有真的到 Pod 都還不確定，或還沒確認 `Service`、`endpoints`、selector、Pod 存在與否，這時不該先把問題縮成 container 內部題。

### AI 修正與補充

- 你的主體方向是對的，而且今天這題最重要的核心你已經抓到了：**第一步的目標不是直接找答案，而是先做高槓桿縮圈。**
- 你把 `get`、`describe`、`events` 當成預設第一組，這個方向也對。更精確地說：`get` 比較像 **先看資源快照與異常形式**；`describe` 比較像 **把某個物件的狀態、conditions、probe、近期 events 黏在一起看**；`events` 則是 **補時間序列**，幫你看這個問題是先發生 image pull、probe fail，還是排程／拉鏡像／重啟這種順序。
- `logs` 不一定是第二步，但通常是在你已經有理由懷疑 **container 確實有啟動過，而且問題更像 app 內部或程序啟動期** 時，才會變得高價值。你用 `CrashLoopBackOff` 來舉例是合理的，因為這類情境確實常要接 `logs` 或 `logs --previous`。
- `rollout` 也不是「只要看到錯誤就一起看」；它比較適合部署切版、版本交接、ReplicaSet 轉換、revision 回退這類 **Deployment 層** 問題。也就是說，它回答的是「這次部署交接有沒有卡住」，不是「這顆 Pod 裡的 app 為什麼炸掉」。
- 你最後講「不會先 `exec`」的方向也是對的，但可以再切得更準成兩類：第一類是 **container 根本還沒穩定存在**，例如 `ImagePullBackOff`、`CreateContainerError`，這時通常連可進去的 target 都不穩；第二類是 **外層路徑還沒確認**，例如還不知道請求有沒有真的走到 Pod、`Service` selector / `endpoints` 是否正常、Ingress / path / routing 是否先出問題。這兩種情況都不適合把第一步直接縮成 container 內部檢查。
- 這題可以收成一句話：**壞 Pod 的第一步要先選最能縮圈的證據入口；預設多半先看 `get` / `describe` / `events` 來辨認問題型態，只有在已懷疑 container 曾成功啟動且問題落在 app 或部署交接層時，才再接 `logs`、`logs --previous` 或 `rollout`；而在 container 還沒穩定存在、或外層流量路徑尚未確認前，都不應一開始就先 `exec`。**

## Q2

### 題目

今天如果你要把 W6 Day 1 到 Day 3 練過的內容串成一段完整排查敘述，最少要保住哪幾個轉折點？

### 答題引導

1. 先列出你認為一定要出現的 3 到 5 個關鍵節點。
2. 再回答每個節點主要在回答哪一層問題，例如狀態、事件、app 輸出、container 內部、部署交接。
3. 最後補一句：今天的整合題裡，`port-forward` 為什麼只能是其中一步，而不是整條主線。

### 對照檔案

- `.privatedocs/六週版學習計畫.md`
- `darkmind/README.md`

### 使用者回答摘要

- 使用者把今天整合排查最少要保住的轉折點，先收斂成三段：第一段先用 `get` / `describe` 定位出問題的資源與異常類型；第二段再切成 **Pod 內** 與 **Pod 外** 兩條線；第三段才進入各自的修理、回復與必要的 rollback。
- 使用者認為第一步一定要先看資源狀態，因為只有先辨認它是什麼類型的異常，後面才知道應往哪一種排查線走。這裡也明確把 Pod 放在主要觀察中心，因為它承載 workload。
- 在第二步的切分上，使用者已抓到一個很有價值的實務分界：若較像 Pod 外問題，就去看 routing、`Service`、`endpoints`、Ingress 這條外層流量鏈；若較像 Pod 內問題，就去看 `logs`、`logs --previous` 等 app / container 內部證據。
- 在第三步上，使用者已把「診斷」和「暫時恢復」接起來，並指出 production 情境下若要 `rollout undo`，應先留下 `describe`、`events`、`logs` 等關鍵證據，再做回復。
- 對於 `port-forward` 的定位，使用者已明確把它視為 optional 工具：它比較像在已縮圈後，用來做某個局部驗證；若情況緊急要先 rollback，`port-forward` 很可能根本不是優先手段，甚至可能因壞版本被移除而失去對象。

### AI 修正與補充

- 你的回答方向是對的，而且今天這題最重要的核心你已經抓得很準：**整合式排查不是把所有工具串成固定清單，而是保住幾個關鍵轉折點。**
- 第一個轉折點你抓得對，就是先做 **異常類型辨認**。這裡最穩的說法是：先用 `get` 看資源快照與異常字樣，再用 `describe` / `events` 補 Kubernetes 視角，回答「現在卡在 image、probe、重啟、排程，還是部署交接」。你把 Pod 當主要觀察中心是合理的，但也要記得：**有些問題雖然最後表現在 Pod，真正的切點仍可能在 Deployment、Service 或 Ingress。**
- 第二個轉折點是你講得很好的 **Pod 內 / Pod 外切分**。這個切分很實務，因為它直接決定下一步工具：若較像 Pod 外，重點是 `Service`、selector、`endpoints`、Ingress / routing；若較像 Pod 內，重點才會變成 `logs`、`logs --previous`、必要時 `exec`。這一段其實就是把 Day 1 到 Day 3 的觀察點重新組起來。
- 第三個轉折點是 **要不要先修復、以及修復前要不要先留證據**。你提到 production 先留 `describe`、`events`、`logs` 再 `rollout undo`，這非常對。更精確地說：當問題已明顯影響服務，而且你已經足夠懷疑是壞版本 rollout 時，`rollout undo` 的優先級會高過很多 deeper inspection；但前提是要先留住足夠證據，避免回滾後關鍵訊號消失。
- 你對 `port-forward` 的定位也很準。今天這題最適合收斂成：**`port-forward` 不是整條主線，而是縮圈後的局部驗證工具。** 它回答的是某個 Pod / Service port 本身能不能經由 debug tunnel 被打到，不是拿來決定整體排查方向，也不是 production 緊急恢復時的優先動作。
- 這題若要再壓成更像面試回答的版本，可以記成四個最小轉折點：**先看異常類型、再切 Pod 內 / Pod 外、再選對應證據工具、最後決定是深入診斷還是先恢復服務。**
- 這題可以收成一句話：**W6 Day 1 到 Day 3 真正要串起來的，不是哪條指令先背，而是四個轉折點：先辨認異常類型，再切 Pod 內 / Pod 外，接著選對應的證據工具，最後再決定要深入診斷、局部驗證，還是先 rollback 恢復服務；其中 `port-forward` 只屬於局部驗證，不是整條排查主線。**
