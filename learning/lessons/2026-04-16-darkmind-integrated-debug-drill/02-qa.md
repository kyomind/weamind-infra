## Q1

### 題目

如果今天給你一個壞 Pod 情境，你在第一步要怎麼決定先看哪一種證據？

### 答題引導

1. 先回答第一步的目標是什麼：找完整答案，還是先縮小問題範圍。
2. 再回答你會怎麼判斷應先看 `get` / `describe` / `events`，還是先看 `logs` / `rollout`。
3. 最後補一句：什麼情況下你不會一開始就直接 `exec` 進去。

### 對照檔案

- `darkmind/scenarios/crash-loop.yaml`

### 使用者回答摘要

- 使用者明確把第一步目標放在 **先縮小問題範圍**，而不是一開始就想直接找到完整答案；理由是 Kubernetes 的因果鏈很長，必須先判斷問題大致落在哪一層。
- 使用者目前的預設順序是先看 `get`、`describe`、`events` 這組，先辨認錯誤形式與目前卡在哪個環節，再決定是否往 `logs` 或 `rollout` 縮圈。
- 使用者也有把 `CrashLoopBackOff` 和「Pod 已經有跑起來，但 container 內部可能有問題」這條線抓出來，並認為這種情況通常仍會先看 `describe`，再看 `logs`。
- 對於什麼情況下不會先 `exec`，使用者已抓到一個重要邊界：如果連流量是否有真的到 Pod 都還不確定，或還沒確認 `Service`、`endpoints`、selector、Pod 存在與否，這時不該先把問題縮成 container 內部題。

### AI 修正與補充

- 你的主體方向是對的，而且今天這題最重要的核心你已經抓到了：**第一步的目標不是直接找答案，而是先做高槓桿縮圈。**
- 你把 `get`、`describe`、`events` 當成預設第一組，這個方向也對。更精確地說：`get` 比較像 **先看資源快照與異常形式**；`describe` 比較像 **把某個物件的狀態、conditions、probe、近期 events 黏在一起看**；`events` 則是 **補時間序列**，幫你看這個問題是先發生 image pull、probe fail，還是排程／拉鏡像／重啟這種順序。
- `logs` 不一定是第二步，但通常是在你已經有理由懷疑 **container 確實有啟動過，而且問題更像 app 內部或程序啟動期** 時，才會變得高價值。你用 `CrashLoopBackOff` 來舉例是合理的，因為這類情境確實常要接 `logs` 或 `logs --previous`。
- `rollout` 也不是「只要看到錯誤就一起看」；它比較適合部署切版、版本交接、ReplicaSet 轉換、revision 回退這類 **Deployment 層** 問題。也就是說，它回答的是「這次部署交接有沒有卡住」，不是「這顆 Pod 裡的 app 為什麼炸掉」。
- 你最後講「不會先 `exec`」的方向也是對的，但可以再切得更準成兩類：第一類是 **container 根本還沒穩定存在**，例如 `ImagePullBackOff`、`CreateContainerError`，這時通常連可進去的 target 都不穩；第二類是 **外層路徑還沒確認**，例如還不知道請求有沒有真的走到 Pod、`Service` selector / `endpoints` 是否正常、Ingress / path / routing 是否先出問題。這兩種情況都不適合把第一步直接縮成 container 內部檢查。
- 這題可以收成一句話：**壞 Pod 的第一步要先選最能縮圈的證據入口；預設多半先看 `get` / `describe` / `events` 來辨認問題型態，只有在已懷疑 container 曾成功啟動且問題落在 app 或部署交接層時，才再接 `logs`、`logs --previous` 或 `rollout`；而在 container 還沒穩定存在、或外層流量路徑尚未確認前，都不應一開始就先 `exec`。**
