## Q1

### 題目

如果一個 Pod 顯示 `Running`，但 `READY` 是 `0/1`，這代表什麼？為什麼這時候不能直接把它當成「app 正常可服務」？

### 答題引導

1. 先回答 `Running` 比較是在說哪一層狀態。
2. 再回答 `Ready` 比較是在說哪一層能力。
3. 最後補一句：這個差異會怎麼影響 Service 是否把流量送進去。

### 對照檔案

- `darkmind/healthy.yaml`
- `darkmind/scenarios/readiness-fail.yaml`
- `darkmind/README.md`

### 使用者回答摘要

- 使用者已抓到最核心的差異：Pod 顯示 `Running`，不代表它已經能正常接收流量；`READY 0/1` 表示 Kubernetes 目前仍判定它 **not ready**。
- 使用者也正確區分了兩個層次：`Running` 比較偏向 **Pod / container 已經啟動並在運作**，`Ready` 比較偏向 **這個 Pod 內的服務是否已能正常處理請求**。
- 使用者進一步把這個差異接到 Service 流量，方向也是對的：只有 Pod 處於 Ready 狀態時，Service 才會把它納入可送流量的後端；換句話說，`endpoints` 只會保留目前可服務的 Pod。

### AI 修正與補充

- 你的主體答案是對的，而且最重要的判斷已經抓到了：**`Running` 不等於可服務，`Ready` 才更接近「能不能接流量」這件事。**
- 這題可以再收得更準一點：`Running` 在 Kubernetes 裡更接近 **Pod phase / Pod 已被排到某個 node、主要 container 已經跑起來** 的狀態，而不只是單獨在講某個 app 功能是否正常。也就是說，它回答的是「這個 Pod 有沒有活著在跑」，不是「它現在能不能安全接流量」。
- `Ready` 則更接近 **服務可用性**。在今天這個 `readiness-fail` 情境裡，container 其實可能還活著，甚至你還 `exec` 得進去；但因為 readiness probe 打到錯的 path，Kubernetes 仍會把這個 Pod 視為 **尚未準備好對外服務**。
- 你把它接到 Service 也接得對。更準的說法是：Service 不是看 `Running` 就送流量，而是看 **這個 Pod 有沒有通過 readiness、是否該出現在對應的 `endpoints` 裡**。所以今天很重要的一個觀念是：**Pod process 可能還活著，但如果沒 Ready，Service 仍不應把它當成健康後端。**
- 最後再補一個精度：`endpoints` 指向的是 **Pod IP / 可用後端 Pod**，不是在 Service 裡再細分到某個「container 物件」層級。你原本的方向是對的，只是面試時講成「Service 只會把 Ready 的 Pod 納入 endpoints」會更準。
- 這題可以收成一句話：**`Running` 代表 Pod / container 已啟動在跑，`Ready` 代表它是否已具備接流量的服務能力；只有 Ready 的 Pod 才會被 Service 納入可送流量的 endpoints。**

## Q2

### 題目

`kubectl exec` 和 `kubectl port-forward` 各自更適合回答什麼問題？為什麼它們不是互相取代的工具？

### 答題引導

1. 先用一句話分別定義 `exec` 與 `port-forward` 的核心用途。
2. 再回答它們各自在看哪一種證據或連線路徑。
3. 最後補一句：哪一個比較容易繞過正常 Service 流量路徑。

### 對照檔案

- `darkmind/README.md`
- `darkmind/healthy.yaml`
- `darkmind/scenarios/readiness-fail.yaml`

### 使用者回答摘要

- 使用者明確說明：`kubectl exec` 這個工具較熟，`kubectl port-forward` 則是最近才從 Kubernetes 初學書與 AI 規劃中接觸到，過去尚未真正實作過。
- 使用者對 `exec` 的核心用途掌握是對的：它是 **進到 Pod 內的某個 container 執行指令**，很像 Docker 的 `exec`，適合直接看 container 內部狀態，例如環境變數、檔案、程序或手動做最小測試。
- 使用者也已抓到一個重要方向：`port-forward` 比較容易 **繞過正常 Service 流量路徑**，只是對它的實際操作與證據邊界還不夠熟。

### AI 修正與補充

- 你目前對 `exec` 的理解是對的，而且這題最重要的核心其實已經抓到了：**`exec` 是進 container 內部看東西，`port-forward` 是把本機流量臨時導到叢集內某個 Pod 或 Service。**
- 先把兩者最精簡地分開講：`kubectl exec` 比較適合回答 **「container 裡面現在長什麼樣、服務程序有沒有起來、我在容器內自己打 localhost 會看到什麼」**；`kubectl port-forward` 比較適合回答 **「如果我從本機臨時打到這個 Pod / Service，能不能連到它暴露的 port」**。
- 兩者看的證據不是同一層。`exec` 比較像 **container 內部視角**，你進去後看到的是 process、env、檔案、container 內部連線結果。`port-forward` 比較像 **從你本機臨時建立一條 tunnel，到 Pod 或 Service 的 port**，所以它回答的是「透過這條臨時通道，我能不能打到這個 HTTP / TCP 端點」。
- 也因為這樣，它們不能互相取代。你就算 `exec` 得進去，也不代表本機到服務的連線一定沒問題；反過來說，你就算 `port-forward` 打得通，也不代表正式 Ingress / Service / readiness 這條正常流量路徑就一定健康。
- 你第三點的方向完全正確：**比較容易繞過正常 Service 流量路徑的是 `port-forward`。** 更精確一點說，`kubectl port-forward` 常常是 debug 用的臨時通道，它的價值在於快速驗證「某個 Pod / Service port 本身有沒有回應」，但它不等於正式使用者流量真的能同樣進來。今天這也是為什麼它要跟 `readiness`、`endpoints` 一起學。
- 你提到以前沒有實作過 `port-forward`，這很正常；但這不表示它不該放在 W6，反而代表這個安排是合理的。因為它正好卡在你現在已經有 `kubectl` 基礎、但還沒把「container 內部觀察」和「本機臨時連線驗證」分開之前的這個點。
- 這題可以收成一句話：**`exec` 用來看 container 內部，`port-forward` 用來建立本機到叢集內 Pod / Service 的臨時通道；兩者回答的是不同層級的問題，其中 `port-forward` 更容易繞過正式流量路徑，所以不能把它當成線上流量健康的直接證據。**

## Q3

### 題目

當 `readinessProbe` 失敗時，為什麼除了看 Pod 本身，還要把 `Service endpoints` 一起納入排查？

### 答題引導

1. 先回答 readiness probe 失敗時，Pod 和 container 可能仍然處於什麼狀態。
2. 再回答 `endpoints` 比較像在回答哪個流量層問題。
3. 最後補一句：這和 `exec` 或 `port-forward` 能不能成功，為什麼可能不是同一件事。

### 對照檔案

- `darkmind/scenarios/readiness-fail.yaml`
- `darkmind/README.md`

### 使用者回答摘要

- 使用者已抓到第一個核心點：當 `readinessProbe` 失敗時，Pod 不一定整個掛掉，container 也可能仍在跑，但 Kubernetes 不會把它視為 Ready。
- 使用者也正確指出 `endpoints` 回答的是 **這個 Pod 現在能不能被當成可接流量的後端**；若尚未 Ready，對應的 Service 就不應把它收進 `endpoints`。
- 使用者第三點方向也是對的：`exec` 與 `port-forward` 的成功條件，和 readiness / Service backend membership 並不是同一件事；就算 Pod 還沒 Ready，`exec` 仍可能成功，而 `port-forward` 也可能仍能建立 debug 用的連線。

### AI 修正與補充

- 你的主體答案是對的，而且你已經抓到今天這題最重要的切分：**readiness 失敗，重點不是「container 有沒有活著」，而是「這個 Pod 能不能被 Service 當成健康後端」。**
- 第一點可以再收得更準一點：readiness probe 失敗時，Pod 常見的狀態其實是 **`Running`，但 Ready condition 為 false，所以 `READY` 欄位會是 `0/1`**。也就是說，它不是一定整個 Pod 掛掉，而是 **process 可能還活著、container 也還在跑，只是 Kubernetes 判定它還沒準備好接流量**。
- 第二點你講 `endpoints` 的方向是對的。`endpoints` 比較像在回答 **Service 這一層的流量收斂問題**：現在這個 Service 後面，哪些 Pod 真的應該被納入可送流量的後端名單。今天為什麼一定要一起看它，就是因為只看 Pod 本身，你只知道它活不活；但看 `endpoints`，你才知道 **Service 會不會真的把請求送進去**。
- 第三點你也抓得對，而且這正是 `exec`、`port-forward` 和 readiness 最容易混掉的地方。`kubectl exec` 不要求 Pod 必須 Ready，它主要只需要 container 還在、可執行 shell 或命令
- 所以 **Pod 雖然 `0/1 Ready`，你仍可能 `exec` 得進去**。`kubectl port-forward` 也常常是在建立 **debug 用的臨時 tunnel**，它回答的是「這條臨時通道能不能打到 port」，不是「正式 Service 流量是否已健康收斂」。
- 所以今天要刻意分開三件事：**container 是否活著**、**我能不能透過 debug 手段連進去**、**Service 是否真的會把流量送到它身上**。這三件事可以同時出現不同答案，不能混成一題。
- 這題可以收成一句話：**當 readiness probe 失敗時，Pod / container 可能仍在 `Running`，但 Service 不會因此自動把它當成健康後端；所以除了看 Pod 狀態，還要看 `endpoints`，才能確認正式流量是否真的會送進去。**
