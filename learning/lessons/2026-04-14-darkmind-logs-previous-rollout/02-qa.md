### AI 修正與補充

- 你這題主體方向是對的，而且已經抓到 Day 2 最重要的切換點：當問題從 image pull 類，進到 **container 有啟動、但 app 自己出錯或很快退出** 的類型時，`kubectl logs` 的價值就會大幅上升，因為它開始直接回答「**container 內到底輸出了什麼**」。
- 你把 Day 1 和 Day 2 的關係講成先後鏈，這個說法是對的。更準一點地說：`get`、`describe`、`events` 比較像 **Kubernetes 怎麼看這個 Pod**，而 `logs` 比較像 **這個 container / app 自己說了什麼**。所以不是誰取代誰，而是排查時在不同證據層之間切換。
- 要補正一個關鍵點：`CrashLoopBackOff` 通常不代表卡在 `CreateContainer` 前段，而比較像 **container 已成功啟動過，但又很快退出，進入反覆重啟與 backoff 的循環**。如果是純 image pull 失敗，常見狀態會更接近 `ErrImagePull` 或 `ImagePullBackOff`；那時候你通常拿不到有價值的 app log。
- 你最後提到只看 `logs` 可能還不夠，這個方向也是對的，但可以再收得更完整：少的通常有兩層。第一層是 **previous log**，也就是前一輪已退出 container 的最後輸出；這對 CrashLoopBackOff 特別重要。第二層是 **Kubernetes 視角的狀態與事件證據**，例如 `restart count`、`state`、`reason`、`events`。也就是說，`logs` 幫你看 app 發生了什麼，但它本身不會完整告訴你 Kubernetes 怎麼判讀這次重啟。
- 這題可以先收成一句話：當 Pod 已經進到 `CrashLoopBackOff`，`logs` 的價值在於它開始提供 **app / process 本身的直接輸出證據**；但它仍要和 Day 1 的 Kubernetes 視角工具互補，不能單獨取代整條排查鏈。

## Q2

### 題目

`kubectl logs` 和 `kubectl logs --previous` 都在看 Pod log，但它們各自更適合回答什麼問題？為什麼在 CrashLoopBackOff 裡兩者常常要一起看？

### 答題引導

1. 先分別說出 current log 和 previous log 在看哪一次 container 執行。
2. 再回答什麼情況下 `--previous` 特別有訊號價值。
3. 最後補一句：什麼情況下你可能拿不到 `--previous`。

### 對照檔案

- `darkmind/README.md`
- `darkmind/scenarios/crash-loop.yaml`

### 使用者回答摘要

- 使用者已正確抓到 `kubectl logs` 比較是在看 **目前這一次 container 執行實例** 的輸出，而 `kubectl logs --previous` 比較是在看 **上一個已終止 container 實例** 的輸出。
- 使用者也正確指出：在 `CrashLoopBackOff` 這種重複重啟情境裡，若 current log 還沒走到真正失敗點，`--previous` 往往更有訊號價值，因為它能補到上一輪完整執行到退出前的最後證據。
- 使用者對拿不到 `--previous` 的條件也抓得對：若 container 還沒有完成過一次重啟循環，通常就沒有 previous 可看。

### AI 修正與補充

- 你這題的主體答案是對的，而且已經抓到 `logs` 與 `logs --previous` 的真正分工。可以先收成一句話：`kubectl logs` 看 **現在這一輪**，`kubectl logs --previous` 看 **上一輪已退出的那一輪**。
- 你第二點也答得很準。`--previous` 在 `CrashLoopBackOff` 特別有價值，因為這類問題常見的情況是：container 一啟動很快就退出，新的 instance 又立刻被拉起來。這時 current log 可能只看到很前段、很短的輸出，甚至什麼都還沒來得及印完；反而是 previous log 比較有機會保留 **上一輪真正走到失敗點前的完整尾段證據**。
- 你第三點也正確：如果 container 還沒真正重啟過，或者目前看到的是第一次啟動失敗前的狀態，那就可能拿不到 `--previous`。CLI 常見的回應會接近「previous terminated container not found」這類訊息。
- 再補一個小邊界，讓說法更準：`--previous` 不是任意歷史回放，它通常只會拿到 **上一個已終止的 container instance**，不是更早好幾輪的完整歷史。所以它很適合用來抓「剛剛上一輪到底怎麼死的」，但不是長期審計工具。
- 這題可以收成一句話：在 `CrashLoopBackOff` 裡，current log 幫我看 **現在這輪正在發生什麼**，previous log 幫我看 **上一輪到底怎麼結束**；兩者一起看，才比較容易把重啟循環的前因後果接起來。

## Q3

### 題目

當 `Deployment` rollout 卡住時，`kubectl rollout status`、`kubectl rollout history`、`kubectl rollout undo` 三者各自更適合回答什麼問題？

### 答題引導

1. 先用一句話分別定義這三個指令最核心的用途。
2. 再回答它們和單一 Pod 排查的層級差異。
3. 最後補一句：哪個指令最接近「恢復動作」，而不只是觀察。

### 對照檔案

- `darkmind/README.md`
- `darkmind/scenarios/bad-rollout-01-good.yaml`
- `darkmind/scenarios/bad-rollout-02-bad.yaml`

### 使用者回答摘要

- 使用者對三個指令的第一層直覺方向是對的：`kubectl rollout status` 偏向看 **這次 rollout 目前進展到哪裡、是否卡住**；`kubectl rollout history` 偏向看 **這個 Deployment 的 revision / rollout 軌跡**；`kubectl rollout undo` 則是 **把 Deployment 回退到前一個 revision**。
- 使用者也有抓到一個重要層級差異：rollout 類指令看的不是單一 Pod，而是 **Deployment 及其 revision / ReplicaSet 演進** 這個控制面層級。
- 使用者目前比較需要補強的地方是：`rollout history` 不只是「每次 rollout 的結果」，而是更接近 **revision 歷史與版本切換軌跡**；此外，rollback 與事後保留壞 Pod 證據之間的取捨，也需要更精準地分清楚操作順序。

### AI 修正與補充

- 你這題的方向是對的，而且其實已經抓到 rollout 類指令和單一 Pod 排查的核心差異。先用一句話收：`kubectl rollout status` 看 **這次 rollout 現在有沒有順利往完成前進**，`kubectl rollout history` 看 **這個 Deployment 之前有哪些 revision / 版本軌跡**，`kubectl rollout undo` 則是 **把 Deployment 指回前一個或指定 revision，屬於恢復動作**。
- 你第二點也抓得對：這些指令看的層級不是「單一 Pod 到底怎麼壞」，而是 **Deployment 這個控制器現在要把哪個 Pod template 推成新版本、過程順不順、該不該退版**。單一 Pod 排查比較像在回答「這顆 Pod 為什麼不健康」；rollout 指令比較像在回答「這次版本發布有沒有成功、失敗時要不要回退」。
- 補一個更準的說法：`rollout history` 不是直接告訴你「每次 rollout 的結果摘要」那麼單純，它更接近 revision 歷史。你通常會藉由它看到 Deployment 曾經有哪些 revision，必要時也可配合 `--revision` 看某次 revision 的 Pod template 細節。它回答的是「**我之前推過哪些版本**」，不是單靠它就能完整回答「每次到底為什麼失敗」。
- 第三點你答得準：三者裡最接近恢復動作的確實是 `kubectl rollout undo`。它不是觀察，而是直接改變 Deployment 目標版本，讓控制器開始把工作負載往先前 revision 收斂。
- 這題可以先收成一句話：當問題提升到 rollout 層級時，重點不再只是盯著某顆 Pod，而是要看 **Deployment 的發布進度、revision 軌跡，以及是否需要回退**；其中 `undo` 是恢復動作，`status` 與 `history` 則偏觀察。
