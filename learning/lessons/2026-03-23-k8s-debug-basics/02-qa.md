## Q1

### 題目

如果今天要把外部預習裡的抽象骨架 `Client → DNS → LB → Ingress → Service → Pod → App` 對回 WeaMind，你會怎麼用這個 repo 內真正存在的元件名稱，把整條路徑講成一段完整敘述？

### 對照檔案

- `README.md`
- `manifests/ingress.yaml`
- `manifests/service.yaml`
- `manifests/deployment.yaml`

### 使用者回答摘要

- 使用者已能先把外層骨架講出來：Cloudflare DNS 會把 `k8s.kyomind.tw` 解析到 Hetzner Load Balancer 的 IP，之後 LB 再把流量送往兩台 worker node 的私網 IP。
- 使用者也能把 Ingress 規則與 Service 關係對起來：`manifests/ingress.yaml` 會把 host `k8s.kyomind.tw`、path `/` 的流量導向 `weamind-line-bot` Service，port 為 `80`。
- 使用者能進一步對照 `manifests/service.yaml`，說出 Service 會透過 selector 選到 `app=weamind` 的 Pods，並把 Service port `80` 導到 Pod / container 的 `8000`。
- 使用者目前較不確定的地方有兩個：第一，LB 把流量送到 worker nodes 後，是怎麼被 Traefik / Ingress 接住；第二，Ingress backend 中的 Service port `80` 到底代表哪一層的 port。

### AI 修正與補充

- 主方向是對的，而且你已經把這題最重要的幾個錨點抓到了：Cloudflare DNS、Hetzner LB、Traefik、`weamind-line-bot` Service、`weamind` Pods、container port `8000`。這表示你的抽象骨架已經開始能對回 WeaMind 的真實元件。
- 第一，對 DNS 這段的理解是對的。從 [README.md](README.md) 與 [PROGRESS.md](PROGRESS.md) 來看，`k8s.kyomind.tw` 會指向 Hetzner LB 的公網 IP；所以外部請求一開始確實是先進到 LB，而不是直接進 K3s node。
- 第二，你說 LB 會把流量打到兩台 worker node 的私網 IP，這也對，而且這正好對回 [README.md](README.md) 裡的架構圖與 [PROGRESS.md](PROGRESS.md) 裡的 LB 配置紀錄。更精準的說法是：Hetzner LB 不是「直接打 ingress 規則」，而是把 TCP 流量轉送到 worker nodes；在這些 nodes 上，真正接住 HTTP / HTTPS 流量的是 Traefik 這個 Ingress Controller。也就是說，Ingress 是規則，Traefik 才是實際收流量並執行這些規則的元件。
- 第三，你對 `manifests/ingress.yaml` 的描述基本正確。這份 Ingress 規則定義的是：當 host 為 `k8s.kyomind.tw`、path 為 `/` 時，把流量交給後端 Service `weamind-line-bot`。這裡 backend 裡的 `port.number: 80`，不是在說「來源流量原本是 80」，而是在說「Traefik 轉送時，要去找這個 Service 暴露的哪個 Service port」。也就是 Service 這一層的 port。
- 第四，回到 [manifests/service.yaml](manifests/service.yaml)，這份 Service 定義的是 `port: 80`、`targetPort: 8000`。因此這條路的正確理解是：Traefik 依照 Ingress 規則，把流量交給 `weamind-line-bot` 這個 Service 的 `80`；然後 Service 再把它導向被 selector `app=weamind` 選到的 Pods，實際打到 container 的 `8000`。換句話說，Ingress backend 裡的 `80` 指的是 Service port，不是 container port，也不是單純「外部來源 port」。
- 第五，這題若要用 WeaMind 的最小可講版收斂，可以講成：LINE webhook 會打到 `k8s.kyomind.tw`，Cloudflare DNS 先把它解析到 Hetzner LB 的公網 IP；LB 再用私網把流量轉到兩台 worker nodes，Traefik 作為 Ingress Controller 在那裡接住流量，依照 [manifests/ingress.yaml](manifests/ingress.yaml) 的 host / path 規則，把請求轉給 `weamind-line-bot` 這個 ClusterIP Service 的 port `80`；Service 再根據 selector `app=weamind` 找到後端 Pods，並把流量導到 container port `8000`，最後由 Pod 裡的 uvicorn app 處理。
- 第六，你剛剛卡住的「node 接到之後怎麼送到 ingress」其實不算答錯，而是剛好碰到 Ingress Controller 的執行細節。對今天 Day 1 來說，先記住這個層次就夠：LB 把流量送到 worker nodes，而在那裡真正接流量並執行 Ingress 規則的是 Traefik；因此 debug 時如果外部請求已進到 nodes，但沒被正確導到 Service，Traefik / Ingress 就會成為高價值觀察點。

## Q2

### 題目

如果今天 WeaMind 的 Pod 出現 Pending、ImagePullBackOff、CreateContainerError 或 CrashLoopBackOff，你會優先回頭對照 repo 裡哪些設定？請不要只解釋名詞，而是直接說在這個 repo 應該先看哪個檔案、哪一段設定。

### 對照檔案

- `manifests/deployment.yaml`
- `README.md`
- `PROGRESS.md`

### 使用者回答摘要

- 使用者已能先抓到這題的主幹：這四種狀態雖然不同，但第一輪最重要的 repo 入口大多仍是 `manifests/deployment.yaml`，因為 image、`imagePullPolicy`、`nodeSelector`、command、`envFrom`、probe 等高價值設定都集中在這裡。
- 對 Pending，使用者會優先回看 Deployment 內和 Pod 排程有關的設定，例如資源是否足夠、`nodeSelector` 或其他節點選擇條件是否讓 Pod 找不到符合條件的 worker node。
- 對 ImagePullBackOff，使用者能直接對回 Deployment 內 `containers.image` 與 `imagePullPolicy` 這段設定，認為第一輪應先確認 image URL、tag 與拉取策略。
- 對 CreateContainerError，使用者目前還不夠穩，直覺上仍會先回看 Deployment，但會把 command、port、`envFrom`、ConfigMap、Secret 這些可能性混到一起，並懷疑自己有些其實比較像 CrashLoopBackOff。
- 對 CrashLoopBackOff，使用者的直覺是：比較像 container 已經啟動，但 app 因 command、環境變數、ConfigMap、Secret 等設定問題而無法正常活下去。

### AI 修正與補充

- 主方向是對的，而且你已經抓到這題最重要的一件事：這四種狀態雖然都發生在 Pod 身上，但它們不是同一種故障；真正的價值在於，你能不能把它們分回不同的 repo 入口與不同的故障階段。
- 第一，對 Pending 的理解是對的。回到 [manifests/deployment.yaml](manifests/deployment.yaml)，第一輪最有價值的確實是 `spec.template.spec.nodeSelector` 與 `resources` 這種排程條件。WeaMind 這個專案裡明確寫了 `nodepool: worker`，而且現在也補上了 `requests.cpu=250m`、`requests.memory=256Mi`；因此如果沒有符合 label 的 node，或節點可用資源無法滿足 requests，Pod 都可能 Pending。更準確地說，Pending 比較像「Pod 還沒真正被放上可執行的節點」，所以第一輪優先懷疑排程、節點選擇與資源，不是 app 本身。
- 第二，對 ImagePullBackOff 的理解也對。第一輪應先看 [manifests/deployment.yaml](manifests/deployment.yaml) 裡的 `containers.image` 與 `imagePullPolicy`。在 WeaMind 裡，這代表要先確認 `ghcr.io/kyomind/weamind:latest` 這條 image 參照是否正確、GHCR pull 是否可行，以及是否曾在 [README.md](README.md) / [PROGRESS.md](PROGRESS.md) 提到 registry 或 image 發布相關問題。這一層還是在「材料拿不拿得到」，不是 app 啟動邏輯。
- 第三，你對 CreateContainerError 和 CrashLoopBackOff 會混在一起，這很正常，但這裡可以再修得更精準。CreateContainerError 比較像「container 還沒真正成功建立起來」，所以第一輪更該優先看會影響 container 建立前置條件的設定，例如 `envFrom` 對到的 ConfigMap / Secret、volume 掛載、引用值是否合法等。WeaMind 在 [PROGRESS.md](PROGRESS.md) 就有一個非常直接的案例：`CreateContainerError (invalid UTF-8)`，根因是 Secret 使用方式錯誤。這個案例很能說明：CreateContainerError 更像在 container 建立階段就卡住，而不是 app 啟動後才掛掉。
- 第四，CrashLoopBackOff 才比較像你後面描述的那些問題：container 有啟動，但 app 活不下來，所以 command、環境變數、依賴連線、probe 或啟動邏輯才會變成更優先的懷疑點。回到 [manifests/deployment.yaml](manifests/deployment.yaml)，這一層的高價值入口包含 `command`、`envFrom`、`readinessProbe`、`livenessProbe`，以及 app 會用到的資料庫 / Redis 連線設定。這也對回你外部預習裡抓到的重點：CrashLoopBackOff 是很強的內層訊號。
- 第五，所以這題若要用 WeaMind 的最小可講版收斂，可以分成這樣：Pending 先看 Deployment 裡的排程條件與資源；ImagePullBackOff 先看 Deployment 裡的 image 參照與拉取條件；CreateContainerError 先看 `envFrom` 對到的 ConfigMap / Secret 等 container 建立前置設定，`PROGRESS.md` 的 invalid UTF-8 就是現成案例；CrashLoopBackOff 則優先回到 command、環境變數、依賴連線與 probe，因為那代表 container 已經起來，但 app 撐不住。
- 第六，你最後那句「四個都還是先回 Deployment YAML，但確認的地方略有不同」其實是很好的收斂。更精準的說法是：第一輪 repo 入口可以相同，但真正要看的欄位與你懷疑的階段不同；這正是今天這題的核心。

## Q4

### 題目

`CreateContainerError (invalid UTF-8)` 與 Hetzner LB health check 未帶 Host header 造成 `/health` 回 404，這兩個故事如果放回今天的 debug 框架，各自是在提示哪一層的問題？為什麼它們不應該用同一條排查起點？

### 對照檔案

- `PROGRESS.md`
- `manifests/ingress.yaml`
- `manifests/deployment.yaml`

### 使用者回答摘要

- 使用者判斷 `CreateContainerError (invalid UTF-8)` 比較像第 5 層，也就是 Pod / Container 建立層，理由是 container 根本沒有成功建立起來，而這個案例已知和 Secret 資料有問題有關。
- 使用者也判斷 LB health check 未帶 Host header 導致 `/health` 回 404，嚴格來講比較像第 2 層，也就是 LB / 外部入口層；因為真正出錯的是 LB health check 沒有帶正確 Host header，才導致後面的 Ingress host 規則無法命中。
- 使用者認為兩者不應該用同一條排查起點，因為它們反映的是完全不同階段的問題：前者是 container 建立失敗，後者是外層 routing / health check 設定錯誤。共同點只是「都應**先處理當前最明顯的異常訊號**」。

### AI 修正與補充

- 你的分層判斷是合理的，而且已經很接近今天這題要的完整答案。
- 第一，`CreateContainerError (invalid UTF-8)` 放在第 5 層，也就是 Pod / Container 建立層，是對的。這個案例在 [PROGRESS.md](PROGRESS.md) 的根因也寫得很清楚：當時錯誤使用了 Secret 的 `data` 欄位，卻放了非 base64 的字串，導致 container 在建立與注入環境變數的前置階段就卡住。後來改成 `.privatedocs/secrets/secret.yaml` 使用 `stringData` 才修好。所以這不是 app 啟動後才掛掉，而是 container 還沒真正成功建起來。
- 第二，LB health check 未帶 Host header 導致 `/health` 回 404，若今天用我們定義的最小分層來放，確實可以把它優先歸在第 2 層，也就是 LB / 外部入口層。因為第一個應修的錯就在 LB health check 設定：它沒有帶正確 Host header，才導致後面的 [manifests/ingress.yaml](manifests/ingress.yaml) host 規則無法命中。再更細一點說，這個案例其實橫跨第 2 層與第 3 層，但第一個異常訊號與第一個修正點都在第 2 層，所以你把它先歸在第 2 層是合理的。
- 第三，你最後的收斂也對：這兩個案例不應該用同一條排查起點，不是因為它們互斥，而是因為它們當下最強的異常訊號出現在不同階段。CreateContainerError 直接告訴你 Pod / container 建立就失敗；LB health check 404 則是在告訴你外層入口的 request shaping / routing 還沒命中正確規則。若這兩種情況都用同一條固定起手式，就會浪費很多時間在錯的層級上。
- 第四，這題若要用 WeaMind 的最小可講版收斂，可以講成：`CreateContainerError (invalid UTF-8)` 是第 5 層的問題，因為 Secret 寫法錯誤讓 container 在建立前置階段就卡住；LB health check 未帶 Host header 導致 `/health` 回 404，則優先是第 2 層的問題，因為 LB health check 沒帶對 Host header，讓後面的 Ingress host 規則無法命中。兩者不該用同一條排查起點，因為它們最強的異常訊號出現在完全不同的層。
