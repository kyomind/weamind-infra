# 2026-04-06 CI Image Pipeline Skeleton QA

> 原則：今天不把 CI/CD 當抽象名詞背誦，而是回到 WeaMind 目前真實存在的 workflow、image registry 與 Deployment 引用方式。

## Q1

### 題目

請先對照 reference/weamind-app-ci.yml，說明 app repo 的 CI workflow 在做什麼。

這題不要只列步驟，還要講一層：哪些是程式品質檢查、哪些是在驗證 Docker image 可被成功 build，以及這些檢查對後續 publish 有什麼前置意義。

### 對照檔案

- reference/weamind-app-ci.yml
- reference/weamind-ci-to-k8s-flow.md

### 使用者回答摘要

- CI workflow 主要分成兩個 job：一個是 Code Quality & Tests，另一個是 Docker Build Validate。
- 第一個 job 先準備執行環境與工具，接著做一連串程式品質檢查，包括 `ruff check`、`ruff format`、`pyright`、`bandit`、`pip-audit`，最後再跑 `pytest`，並把 coverage 結果送到 Codecov。
- 第二個 job 的重點是驗證 Docker image 能不能成功 build，這是為了避免等到後面的 publish 階段才發現 image build 有問題。
- 使用者也補了這條 workflow 的歷史脈絡：Docker build validation 在還沒接上 GHCR 前就存在，主要是先確認 Docker build 這條路本身可用。
- 對後續 publish 的前置意義在於：先把品質檢查、測試與 Docker build 驗證做完，降低後面 publish workflow 才爆掉的機率。

### AI 修正與補充

- 你的主體判斷是對的，尤其是 **CI 不是只跑 lint，而是把品質檢查、測試與 Docker build validation 分成兩個 job**，這個分層抓得準。
- 更精準地拆，`Install dependencies` 與 `Install git and other tools` 比較像 **workflow setup**，不是品質檢查本身；真正的品質檢查主體是 **`ruff`、`pyright`、`bandit`、`pip-audit`、`pytest` 與 coverage upload**。
- 另外一個要收緊的點是：`docker-build-validate` **不是沒有真的 build image**。它執行的是 `docker buildx build --load`，並且用 `weamind-ci-test:${{ github.sha }}` 這個 tag 把 image build 到 runner 本地 Docker 環境中；只是它的目的在 **validation**，不是 push 到 registry。
- 所以更準確的說法是：**CI 第一個 job 驗證程式碼與測試品質，第二個 job 驗證 Dockerfile 真的能把 app 打包成可 build 的 image；這兩者一起形成 publish workflow 的前置保護網。**
- 再往後接一層就是：今天的 publish workflow 並不是沿用這個 validation job 產出的 image artifact 去直接上傳，而是 **在另一個 workflow 裡重新 checkout、重新 build，再 push 到 GHCR**。因此 CI 的價值不是「把同一顆 image 傳下去」，而是 **先證明這個 commit 通過品質檢查，且 Docker build 路徑可成立，才值得進入 publish 階段**。
- 若把 Q1 壓成最短版本：**WeaMind 的 CI 先做 code quality、security、dependency 與 unit test 檢查，再額外驗證 Docker image 能成功 build；這些都不是部署本身，而是 publish 到 GHCR 之前的品質閘門。**

## Q2

### 題目

請對照 reference/weamind-app-publish-ghcr.yml，說明新 image 是怎麼被 push 到 GHCR 的。

這題至少要包含三層：publish workflow 是被什麼事件觸發、它何時才真的會執行 build-and-push、最後產出了哪些 tag。

### 對照檔案

- reference/weamind-app-publish-ghcr.yml
- reference/weamind-ci-to-k8s-flow.md

### 使用者回答摘要

- 使用者先抓到 publish workflow 的觸發點是 `workflow_run`，而且對象是名為 `CI` 的 workflow 完成事件，並注意到它還有限制 `branches: [main]`。
- 使用者也抓到真正執行 `build-and-push` 還要再通過 job-level `if`，其中至少包含三個條件：前一個 workflow 成功、事件型別是 `push`、以及 `head_branch` 是 `main`。
- 對 tag 的觀察是正確的：目前這份檔案明確看到的 tag 只有兩種，也就是 `latest` 與 `sha-<short_sha>`。
- 使用者同時提出幾個關鍵疑問：`workflow_run.conclusion == 'success'` 的 success 到底是誰的 success、PR merge 到 main 算不算 push、以及既然 `on.workflow_run` 已有限制，為什麼 job 裡還需要多一層 `if`。
- 對「為什麼不把兩個 workflow 合併成一份」的回答重點是：CI 的適用範圍比較廣，PR 與 main push 都要驗證；但真正 push 到 GHCR 應只發生在 main 更新之後，所以兩者 scope 不同，不適合混成同一段自動化。

### AI 修正與補充

- 你的主體方向是對的，而且你已經抓到 Q2 的核心：**publish workflow 不是自己直接聽 push，而是聽前一份 `CI` workflow 跑完之後的 `workflow_run` 事件。**
- 第一個要收緊的點是：`github.event.workflow_run.conclusion == 'success'` 這裡的 `success`，指的是 **被觸發的那份 `CI` workflow 的整體執行結果成功**，不是某個單一 step，也不是 publish workflow 自己的成功狀態。
- 第二個要收緊的點是：你問「PR merge 算不算 push 嗎」，在這個題目裡更準確的說法是：**PR 本身的檢查屬於 `pull_request` 事件；但當 PR 真正 merge 進 main 時，GitHub 會在 main 產生新的 commit，這件事會形成一個 `push` 到 main。** 所以 publish 不是因為 PR 檢查成功就直接發生，而是因為 **merge 後 main 上那次 `push` 觸發的 CI 成功**，才會進到 build-and-push。
- 你問「既然 `on.workflow_run` 已有限制，為什麼還要再寫 job-level `if`」，這個問題問得很好。更實務的理解是：**`on` 負責決定 publish workflow 什麼時候被喚起；`if` 則負責決定 workflow 被喚起後，這個 job 到底要不要真的執行。**
- 在 WeaMind 這份設計裡，這層 `if` 是一個 **第二道保護**。因為前面的 `CI` workflow 同時會因 `push` 與 `pull_request` 觸發，所以作者不只想表達「CI 跑完我就來看看」，還想明確保證：**只有來自 main 的 push，而且 CI 結果成功，才真的 build 並 push image 到 GHCR。**
- 對 tag 這題，你的觀察也需要收斂一下：**就這份 snapshot 而言，目前看得到、能被 repo 證據支持的 tag 只有兩種：`ghcr.io/<owner>/weamind:latest` 與 `ghcr.io/<owner>/weamind:sha-<short_sha>`。**
- 你記得好像還有 release tag，這很可能是你過去某個版本、其他 workflow，或你腦中原本的設計，但 **至少在這份目前帶回 repo 的 `reference/weamind-app-publish-ghcr.yml` 裡，沒有看到 semantic version / release tag 的證據**。所以 lesson 裡不能把它寫成既有事實。
- 這個 workflow 的實際 build-and-push 路徑可以壓成這樣：**先 checkout 觸發 CI 的那個 commit，再 setup buildx、登入 GHCR、算出 short SHA，最後用 `docker/build-push-action` 同時 build 多平台 image，並 push 兩個 tag：`latest` 與 `sha-<short_sha>`。**
- 若再接你最後那個延伸題，最精準的回答是：**這兩份 workflow 分開，不只是因為「第二份才需要 push」，而是因為它們服務的是兩個不同 scope。CI 要涵蓋 PR 與 main push 的品質閘門；publish 只該在 main 的成功 push 之後執行，避免每次 PR 檢查都把 image 推進 registry。**
- 若把 Q2 壓成最短版本：**WeaMind 的 publish workflow 由 `CI` 的 `workflow_run` 觸發，但只有當那次 `CI` 是 main 分支上的成功 push 時，才會真的 build 並 push image 到 GHCR；目前可證實的 tag 只有 `latest` 與 `sha-<short_sha>`。**
