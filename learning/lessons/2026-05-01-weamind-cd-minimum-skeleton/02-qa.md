## Q1

### 題目

今天這版 WeaMind CD，實際上已經把哪一條最小路徑打通了？還刻意停在哪一層沒有繼續往下做？

### 答題引導

1. 先指出這次真正完成的是哪段自動化。
2. 再說它停在什麼邊界，不繼續往 cluster apply / rollout 自動化走。
3. 最後補一句：這個停點為什麼合理。

### 對照檔案

- learning/lessons/2026-05-01-weamind-cd-minimum-skeleton/06-implementation.md
- references/phase2/w8-cd-minimum-spec.md
- docs/WeaMind實作CD討論與實踐.md

### 使用者回答摘要

- 這次完成的是：當 app repo 的 release tag image 發布之後，會自動對 infra repo 發出 version update PR；流程先停在 PR 這一層，不會直接自動 apply 到 cluster。
- PR 合併之後，cluster 也不會立刻自動接受變更；第一版仍保留由人手動執行 deploy。
- 這個停損點合理，因為 app repo 的變動只影響到「開 PR」這一步，不會立刻碰到 infra 的實際 running state，避免 app 端的變動直接影響部署環境。
- 至於 infra PR 合併後不直接自動 deploy，則是因為這只是第一版，先讓自己看過、判斷何時要 deploy，比較符合目前需求；不一定每個版本都要立即 deploy，但每個版本都要先發 PR。

### AI 修正與補充

- **已完成的最小路徑是 release → infra PR，不是 release → cluster 自動更新。**
- 這個停點的核心價值是把 app repo release 與 infra runtime state 切開：app 的 release 只能推進到「提出變更」，不能直接改動部署環境。
- 第一版先保留人工 deploy 是合理的，因為它提供一個人類確認點，讓你可以決定是否、何時把某個 PR 的版本真正送進 cluster，而不是每個 release 都強迫自動上線。
- 換句話說，今天這版不是不完備，而是**刻意把風險控制在 PR / review / human gate**，把 cluster 變更留到下一階段。

## Q2

### 題目

PR merge 之後，為什麼第一版先收斂成手動 `make deploy` / `make rollback`，而不是直接做成全自動 deploy？

### 答題引導

1. 先說明 `deploy` 和 `rollback` 各自代表什麼。
2. 再說這次為什麼先保留人工觸發。
3. 最後補一句：第一版如果只留一個指令，會把什麼風險放大。

### 對照檔案

- /Users/kyo/Code/weamind-infra/Makefile
- learning/lessons/2026-05-01-weamind-cd-minimum-skeleton/06-implementation.md
- docs/todo-weamind-cd-future-optimizations.md

### 使用者回答摘要

- `deploy` 的內容就是 `kubectl apply` 加上對新版 Deployment 的 rollout 觀察，實際上會推動 Pod 更新。
- `rollback` 的內涵就是 `kubectl rollout undo`，本質上是退回上一版的 Deployment 狀態。
- 之所以保留人工觸發，是因為現階段想自己決定什麼時候要重新 deploy，而不是讓每個 merge 都自動上線。
- 第一版如果只留一個指令，主要影響比較像是操作彈性變少，不一定會放大風險；真正重要的是 rollback 要保留成完整指令，方便在發現問題時直接回退。

### AI 修正與補充

- **`deploy` 應該被理解成「apply + rollout status」的標準化入口，而不是只做單一步驟。**
- **`rollback` 對應的是 `kubectl rollout undo`，這樣命名最能表達它的語意。**
- 保留人工觸發的核心理由，不是因為 deploy 本身不可靠，而是因為第一版 CD 想保留一個人類確認點，讓使用者決定何時把 infra PR 真正送進 cluster。
- 如果第一版只留一個指令，重點問題不是風險一定放大，而是**操作語意會變得不夠清楚**；拆成 `deploy` / `rollback` 之後，日常上線與回退的**責任邊界更明確**。
- 用 lesson 的語言來說，這版是把 merge 後的人工作業面標準化，而不是把最後一跳直接做成全自動。

## Q3

### 題目

這版 first-pass CD 裡，`GH_TOKEN`、`WEAMIND_INFRA_PR_TOKEN` 與 fine-grained token 的關係，最精確應該怎麼講？

### 答題引導

1. 先區分「環境變數名」和「實際 token 類型」。
2. 再說這次 workflow 裡哪一層實際承載了哪一顆 token。
3. 最後補一句：為什麼這樣的命名 / 承載關係在 runtime debug 時容易混淆。

### 對照檔案

- references/phase2/w8-release-to-infra-auth-debug.md
- learning/lessons/phase2/w8-release-to-infra-auth-debug.md
- .github/workflows/publish-release.yml

### 使用者回答摘要

- `WEAMIND_INFRA_PR_TOKEN` 是我們自己建立並覆蓋進去的 fine-grained token，這是 secret 名稱對應的實際憑證來源。
- `GH_TOKEN` 是 workflow / script 內 runtime 會直接使用的環境變數名；它在這次流程裡承載的是 `WEAMIND_INFRA_PR_TOKEN` 的值。
- `GITHUB_TOKEN` 則是 GitHub Actions 預設內建的 token，和這次自訂的 `GH_TOKEN` 不是同一個東西。
- 這種命名 / 承載關係在 runtime debug 時容易混淆，因為你會同時看到 secret 名稱、環境變數名和 token 類型三層字樣。

### AI 修正與補充

- **`WEAMIND_INFRA_PR_TOKEN` 是 secret 名稱，裡面裝的是 fine-grained token；`GH_TOKEN` 是 workflow / script 透過環境變數傳遞的入口。**
- `GH_TOKEN` 在這次流程裡確實有被直接使用，`publish-release.yml` 會把 `secrets.WEAMIND_INFRA_PR_TOKEN` 注入成 `GH_TOKEN`，而 `scripts/open_infra_version_pr.sh` 也會直接讀它。
- `GITHUB_TOKEN` 是 GitHub Actions 內建的預設 token，這次不靠它來做跨 repo PR。
- runtime debug 容易混淆的點在於：你看到的是不同層級的名稱，但它們各自代表的是不同責任；若不分清楚，很容易把「環境變數名」誤當成「token 類型名」。
