# 2026-04-01 LB Health Check Skeleton QA

## Q1

### 題目

請先對照 `README.md` 的架構圖與 `manifests/deployment.yaml`，說明為什麼 WeaMind 的 Hetzner LB 後端只放 worker，而不是把 control-plane 一起放進去。

這題不要只回答「因為 worker 是跑 app 的地方」，還要再講一層：control-plane 的責任是什麼、這個 repo 怎麼把 app Pod 固定到 worker、為什麼這會影響 LB 後端設計。

### 對照檔案

- `README.md`
- `manifests/deployment.yaml`
- `PROGRESS.md`

### 使用者回答摘要

- control-plane 主要負責叢集管理與調度，不應承接應用流量，避免資源競爭與故障面擴大。
- `manifests/deployment.yaml` 透過 `nodeSelector` 把 app Pod 固定在 `nodepool=worker` 的節點上。
- LB 後端只放 worker，代表外部流量入口也限制在 worker；這和 Pod 固定在 worker 是兩個分開控制的設計。
- 即使 Pod 已固定在 worker，若 LB 仍把 control-plane 放進後端，流量還是可能先打到 control-plane，再由入口層轉發到 worker 上的 Pod。

### AI 修正與補充

- 這題的關鍵不是只背「worker 跑 app」，而是把兩個層次拆開：`nodeSelector` 決定 workload placement，LB target 決定 traffic entry placement。
- WeaMind 的設計是同時把 workload 與入口流量都留在 worker，讓 control-plane 只保留管理面角色。
- 因此，`nodeSelector` 與 LB 後端配置雖然是分開控制，但它們共同服務於同一個目標：避免把 control-plane 拉進資料面與外部流量路徑。

## Q2

### 題目

請你對照 `manifests/ingress.yaml` 與 `PROGRESS.md`，解釋為什麼 Hetzner LB 的 Health Check 不能只是打 `http://<node>/health`，而是需要帶正確的 Host header。

這題至少要包含三層：Ingress 規則是怎麼寫的、沒帶 Host header 時請求實際會在哪一層失敗、為什麼帶上 `k8s.kyomind.tw` 後就能從 `404` 變回 `200`。

### 對照檔案

- `manifests/ingress.yaml`
- `PROGRESS.md`
- `README.md`

### 使用者回答摘要

- `manifests/ingress.yaml` 的 `spec.rules.host` 明確要求請求必須命中 `k8s.kyomind.tw`。
- 沒帶正確 host 資訊時，請求看起來會在 Ingress 這一層對不到規則，因此推測會回 `404`。
- 帶上 `k8s.kyomind.tw` 後，請求才符合規則，後續才能被轉到正確的 Service 與 Pod，所以回 `200`。
- 目前最不確定的點是：為什麼可以直接把這題理解成 `Host` header 問題，以及 repo 是怎麼確認這件事的。

### AI 修正與補充

- 你的主體方向是對的，差的只是一個機制點：**Ingress 裡的 `rules.host` 在 HTTP 層實際就是靠 `Host` header 來做匹配**。對 Traefik 這類 Ingress controller 來說，它看到的不是「DNS 查詢過程」，而是已經送到入口層的 HTTP request；它判斷要不要命中這條 rule，看的就是 request 裡的 `Host` 值。
- 所以 `manifests/ingress.yaml` 中 [manifests/ingress.yaml](manifests/ingress.yaml#L9) 到 [manifests/ingress.yaml](manifests/ingress.yaml#L17) 寫了 `host: k8s.kyomind.tw`，就等於在說：**只有帶著 `Host: k8s.kyomind.tw` 的 HTTP request，才會被這條 Ingress 規則接住**。
- `PROGRESS.md` 已經把這個判定過程記下來了：先看到 [PROGRESS.md](PROGRESS.md#L109) 到 [PROGRESS.md](PROGRESS.md#L112) 的現象，也就是 **`curl http://127.0.0.1/health` 回 `404`，但 `curl -H 'Host: k8s.kyomind.tw' http://127.0.0.1/health` 回 `200`**。這是一個非常直接的對照實驗，表示 app 的 `/health` endpoint 本身沒有壞，真正失敗的是 **Ingress host-based routing 沒被命中**。
- 更精準地說，**沒帶正確 `Host` header 時，請求已經到 Traefik 了，但 Traefik 找不到任何符合 `host: k8s.kyomind.tw` 的路由規則，所以在入口層直接回 `404`，根本還沒進到後面的 `weamind-line-bot` Service 或 app Pod**。
- 為什麼 Hetzner LB 一開始會失敗？因為它的健康檢查預設只是打 `http://<node>/health`，這種檢查不會自動模擬真實使用者對 `k8s.kyomind.tw` 的請求情境。直到在 LB 設定裡補上 `Domain: k8s.kyomind.tw` 後，健康檢查才會帶出正確的 `Host` 值，於是 Traefik 能命中 Ingress 規則，回應也才從 `404` 變成 `200`。
- 若要補一句最短版本：**這題不是 `/health` endpoint 壞掉，而是健康檢查沒有帶正確 `Host` header，導致 Traefik 在 Ingress 層無法匹配 `host: k8s.kyomind.tw` 的規則，所以先回了 `404`。**

## Q3

### 題目

請用 WeaMind 的實際架構說明：Hetzner LB 的 TCP passthrough 跟 Traefik 的 TLS termination / HTTP routing 各自落在哪一層？

這題不要泛泛比較名詞，而是要把 `README.md` 的流量圖與 `PROGRESS.md` 的 TLS 決策接起來，說清楚為什麼這個專案沒有把 TLS 終止放在 Hetzner LB。

### 對照檔案

- `README.md`
- `PROGRESS.md`
- `docs/WeaMind Infra核心架構.md`

### 使用者回答摘要

- 原本曾想把 TLS termination 放在 Hetzner LB，但這條路不可行，因為 Hetzner Managed Certificate 與 DNS 綁定條件不符合目前使用 Cloudflare 託管 DNS 的架構。
- 因此專案改採 `443` TCP passthrough，讓加密流量先穿過 Hetzner LB，再進入 K8s 叢集。
- 為了讓叢集內可以處理 TLS，專案安裝了 `cert-manager`，並透過 Cloudflare DNS-01 申請憑證，再把憑證綁到 Ingress / Traefik 這一層。
- 目前最不確定的點是：真正做 TLS termination 的到底是 `cert-manager`，還是 `Traefik`。

### AI 修正與補充

- 你的決策脈絡是對的，而且已經抓到 Q3 最重要的一半：**Hetzner LB 在這個專案裡只做 TCP 443 passthrough，不做 TLS termination。** 這點在 [README.md](README.md#L84) 與 [PROGRESS.md](PROGRESS.md#L123) 到 [PROGRESS.md](PROGRESS.md#L124) 都有直接證據。
- 更精準地拆層可以這樣說：**Hetzner LB 落在 L4 / TCP 層，負責把 `443` 連線原樣轉送進 K3s；Traefik 落在叢集內入口層，負責 TLS termination 與後續的 HTTP routing。**
- 這個專案沒有把 TLS 終止放在 Hetzner LB，根因不是抽象偏好，而是很具體的產品限制：`PROGRESS.md` 已記錄 [PROGRESS.md](PROGRESS.md#L119) 到 [PROGRESS.md](PROGRESS.md#L123) 的決策，亦即 **Hetzner Managed Certificate 僅支援 Hetzner DNS**，而 WeaMind 的 DNS 仍在 Cloudflare，所以改採 **`cert-manager + Cloudflare DNS-01`** 這條路。
- 你剛剛最關鍵的不確定點，要這樣拆開：**`cert-manager` 不是做 TLS termination 的元件，它的工作是申請、簽發、續期，並把憑證放進 Kubernetes Secret。真正拿著這張憑證與客戶端完成 TLS handshake、把 HTTPS 解開的人，是 `Traefik`。**
- 所以在這個專案裡，分工應該講成：**`cert-manager` 負責 certificate lifecycle，`Traefik` 負責 TLS termination 與 HTTP routing，Hetzner LB 則只負責 TCP passthrough。**
- 若把整條流量壓成 repo 版答案，就是：**LINE / client 先連到 Hetzner LB 的 `443`，LB 只在 TCP 層把連線轉進叢集；Traefik 在叢集內拿 `k8s-kyomind-tw-tls` 這張憑證完成 TLS termination，之後再依 Ingress 的 host / path 規則把 HTTP 流量轉到 `weamind-line-bot` Service 與 Pod。**
- 再補一句很容易被問到的追問：**cert-manager 很重要，但它不是 request path 上的即時流量處理元件；它比較像憑證供應與維護者。Traefik 才是每次請求進來時真正站在流量路徑上的那個元件。**
