# 2026-04-24 Observability Targets ServiceMonitor Dashboard QA

> 原則：今天的 QA 是 implement-heavy mode 下的 post-implementation QA，重點是把 target discovery、`ServiceMonitor` / `PodMonitor` 邊界與 dashboard 驗收訊號收斂成可口述答案。

## Q1

### 題目

今天這套 `kube-prometheus-stack` 裡，Prometheus target discovery 的最小工作模型是什麼？為什麼不能把它簡化成「Prometheus 自己掃整個 cluster」？

### 答題引導

1. 先分開講 Prometheus、Prometheus Operator、`ServiceMonitor` / `PodMonitor` 各自站在哪一層。
2. 再回答 target 是怎麼從 Kubernetes 資源一路變成 Prometheus 可 scrape 的 endpoint。
3. 最後補一句為什麼這不是「自己亂掃整個 cluster」。

### 對照檔案

- `.privatedocs/Phase2三週計畫.md`
- `references/phase2/w7-observability-minimum-spec.md`

### 使用者回答摘要

- Prometheus 是實際執行 scrape 的元件；Prometheus Operator 會把 `ServiceMonitor` 這類 Kubernetes 監控規格轉成 Prometheus 可讀的 scrape config。
- `ServiceMonitor` 除了描述抓取規則，也負責指定要抓哪一個 `Service`，而該 `Service` 後面再連到對應的 Pods，所以它會影響 Prometheus 能不能找到正確 endpoint。
- `PodMonitor` 則是跳過 `Service`，直接對 Pod 建立抓取規則；一般有穩定 `Service` 的 web app，通常先考慮 `ServiceMonitor`。
- target 變成 Prometheus 可抓 endpoint 的順序是：Pod 先提供 `/metrics`，前面有 `Service`，`ServiceMonitor` 指定這個 `Service`，Prometheus Operator 再把它轉成 scrape config，最後 Prometheus 依這份設定去 scrape。
- 這不是 Prometheus 自己亂掃整個 cluster，因為 cluster 內 Pod 很多，必須依照明確規則與 selector 決定要抓誰，不然會失去結構。

### AI 修正與補充

- 這題的核心回答方向是對的，結構也有抓到。最需要補強的是兩個精度點。
- 第一，`ServiceMonitor` 的 selector 直接選的是 `Service`，不是 Pod。本題裡真正的鏈路應該講成：app 在 Pod 內提供 `/metrics`，`Service` 用 `spec.selector` 把流量導到 Pods，`ServiceMonitor` 用 `metadata.labels` 去選 `Service`，Prometheus Operator 再把這些規格轉成 Prometheus 的 scrape config。
- 第二，為什麼不是「Prometheus 自己掃整個 cluster」，更準確的說法不是只有「不然會很混亂」，而是：在 `kube-prometheus-stack` 這套模型裡，Prometheus 的 target discovery 不是無條件掃所有 Pod，而是⭐️**依賴 Operator、CRD 與 selector 規則**，去形成一個**明確且可控的 target 集合**。
- 所以這題最穩的短版答案可以收斂成：Prometheus 負責真的 scrape；Prometheus Operator 負責把 `ServiceMonitor` / `PodMonitor` 這些 Kubernetes 規格翻成 scrape config；`ServiceMonitor` 透過 label selector 指定要抓哪個 `Service` 與哪個 endpoint；Prometheus 最後不是亂掃整個 cluster，而是根據這套規則化的 discovery 結果去抓 target。

## Q2

### 題目

如果今天要讓 WeaMind app 被 Prometheus scrape，你會先優先考慮 `ServiceMonitor` 還是 `PodMonitor`？判斷依據是什麼？

### 答題引導

1. 先回答 WeaMind 現在的 `Deployment` / `Service` 結構比較適合哪一種接法。
2. 再回答你要看哪些條件，例如 `/metrics` 暴露方式、port、label selector、是否已有 stable Service。
3. 最後補一句另一種方案什麼情況下才會比較合理。

### 對照檔案

- `manifests/deployment.yaml`
- `manifests/service.yaml`

### 使用者回答摘要

- 會先優先考慮 `ServiceMonitor`，因為 WeaMind 現在是標準的 `Deployment` + `Service` 結構，Pods 本來就不是直接暴露或直接被使用的對象，而是先由 `Service` 做導流。
- `/metrics` 的暴露方式和一般 HTTP API 共用同一個應用與同一組 Pod；現在的 `Service` 已經提供 stable Service boundary，port 也已經固定，label selector 也已存在，所以最自然的接法就是讓 `ServiceMonitor` 去選這個 `Service`。
- 目前 `Service` 的對外 port 是 `80`，再轉到 Pod 的 `8000`，而 `ServiceMonitor` 只需要指定 `port: http` 與 `/metrics` 路徑即可，不需要繞過 `Service` 直接找 Pod。
- 對 `PodMonitor` 什麼時候比較合理，目前還不夠確定，但直覺上是當沒有 stable Service、或就是想直接監看 Pod 時才比較會考慮。

### AI 修正與補充

- 這題主判斷是正確的：以 WeaMind 現在這個 case，優先考慮 `ServiceMonitor` 才是最自然的答案。
- 原因不是單純「Pod 不是直接被接觸」，而是更具體地說：目前 repo 已經有穩定的 `Deployment` 與 `ClusterIP Service`，`Service.spec.selector` 會把流量導到帶 `app: weamind` 的 Pods，而 `ServiceMonitor` 又剛好是設計來描述「請透過某個 Service 去抓某個 endpoint」的做法，這和現在的結構完全對齊。
- 第二個精度點是 port。這裡如果要講準一點，應該說 app 在 Pod 內實際監聽的是 `8000`，`Service` 對外暴露的是 `80`，然後透過 `targetPort: 8000` 導到容器；`ServiceMonitor` 在這一層只需要抓 `Service` 上名為 `http` 的 port，再打 `/metrics` 即可。
- 第三個精度點是為什麼 `PodMonitor` 這次不是首選。不是因為它「比較少用」而已，而是因為它比較適合那些沒有 stable Service、想直接逐 Pod 抓 metrics、或 metrics target 本來就不想經過 Service abstraction 的情境。對一般已有穩定 Service 的 web app，它通常不是第一個最自然的選擇。
- 所以這題最穩的短版答案可以收斂成：WeaMind 目前已經有穩定的 `Deployment` + `Service` 結構，而且 `/metrics` 與一般 API 共用同一批 Pods 與同一個 HTTP surface，因此優先使用 `ServiceMonitor` 最合理；只有在沒有 stable Service、或刻意要直接對 Pod 建立 scrape 規則時，才比較會考慮 `PodMonitor`。

## Q3

### 題目

站在 W7 demo MVP 角度，今天如果最後只能完成部分結果，怎樣算是合理收尾，怎樣又還不能說自己已完成 observability baseline？

### 答題引導

1. 先回到 Node 3、App 4、1 個 dashboard 這個最低交付物。
2. 再分辨 cluster metrics、app metrics、dashboard 三者哪個今天若缺席會影響驗收程度。
3. 最後用一句話收斂今天最合理的完成線。

### 對照檔案

- `references/phase2/w7-observability-minimum-spec.md`

### 使用者回答摘要

- 站在 W7 demo MVP 角度，合理收尾應該還是回到原本定義的最低交付物，也就是 Node 3、App 4、1 個 dashboard 這三塊都要有。
- 如果問怎樣才算真的完成 observability baseline，直覺上也是這三者都不能缺席，因為少任何一塊都會讓整體驗收不完整。
- 特別是 dashboard 不能沒有；如果沒有 dashboard，而只能自己打 PromQL 查值，那就不太符合這次想完成的最終展示與驗收目標。
- 如果真的要勉強退一步，至少也會希望 dashboard 和 node metrics 先成立，但比較完整的判斷還是這三者都應該具備。

### AI 修正與補充

- 這題的方向基本正確，但要把「合理收尾」和「已完成 observability baseline」切成兩個層次，不然容易把 demo MVP 與完整完成線混在一起。
- 第一層是 W7 demo MVP 的最低交付物。依照今天的 spec，Node 3、App 4、1 個 dashboard 就是最小完成線；少掉其中任何一塊，都不能說完整達到今天原本設定的目標。
- 第二層是如果今天時間不夠、只能部分收尾，什麼叫合理。這時比較合理的說法不是「這樣也算完成 baseline」，而是：如果 cluster metrics 與 app metrics 的 scrape 鏈都已經成立，至少能證明資料有進 Prometheus；但只要 dashboard 還沒落地，就比較像完成了資料收集與驗證，還不能說已經把 W7 的 observability demo baseline 完整收尾。
- 這題裡 dashboard 特別重要，因為它代表你不只抓到資料，還完成了可展示、可讀取、可驗收的觀察入口。若只有 PromQL 查詢或 Prometheus UI 探查， technically 已經有部分 observability data path，但 demo MVP 的展示面仍然不完整。
- 所以最穩的短版答案可以收斂成：W7 的完整完成線是 Node 3、App 4、1 個 dashboard 三者都到位；如果今天只能部分收尾，那合理的最低停損點是至少先把 cluster metrics 與 app metrics 的 scrape 鏈驗通，但在 dashboard 缺席的情況下，還不能說自己已完成這次的 observability baseline。
