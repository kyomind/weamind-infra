## Q1

### 題目

如果你只看 `manifests/deployment.yaml`，你會怎麼把 Deployment、ReplicaSet、Pod 三者的關係講成一條管理鏈？

### 對照檔案

- `manifests/deployment.yaml`
- `README.md`

### 使用者回答摘要

- Pod 是最底層的執行單位。
- 同一種 Pod 的數量由 ReplicaSet 維持，這裡可從 `spec.replicas: 2` 理解成需要維持 2 個副本。
- Deployment 比 ReplicaSet 更高層，會管理底下的 ReplicaSet，版本更新時也會建立新舊不同版本的 ReplicaSet。
- 目前 repo 沒有獨立手寫 ReplicaSet YAML，而是透過 Deployment YAML 來宣告這條管理鏈。

### AI 修正與補充

- 主骨架是對的，但有兩個地方要再修得更精準。
- 第一，`replicas: 2` 是寫在 Deployment 的 `spec` 裡，⭐️**代表 Deployment 宣告自己想維持 2 個 Pod 副本**；真正**持續盯著** Pod 數量是否符合期望的下一層，則是 Deployment **底下建立出的 ReplicaSet**。
- 第二，Deployment 不是憑空知道自己要管哪些 Pod；它是透過 `spec.selector.matchLabels.app=weamind` 去對應 `spec.template.metadata.labels.app=weamind`，也就是說它管理的是這個模板建立出來、且 labels 符合 selector 的**那批 Pods**。
- 在 repo 裡雖然沒有手寫 ReplicaSet YAML，但執行期仍然會有 ReplicaSet 物件存在；比較精準的說法是：這個 repo 只宣告 Deployment，ReplicaSet 由 Kubernetes 根據 Deployment 自動建立與管理。
- 這題在 WeaMind 裡可以收斂成：`manifests/deployment.yaml` 宣告 line-bot 這個 workload 的期望狀態，Deployment 依 selector 與 Pod template 管理對應的 ReplicaSet，ReplicaSet 再持續維持 2 個符合條件的 Pods 存在。

## Q2

### 題目

WeaMind 的 `replicas: 2` 寫在哪裡？在這個專案裡，它實際解的是什麼問題？

### 對照檔案

- `manifests/deployment.yaml`
- `manifests/service.yaml`
- `docs/WeaMind Infra核心架構.md`

### 使用者回答摘要

- `replicas: 2` 寫在 `manifests/deployment.yaml` 的 Deployment `spec` 裡。
- 當其中一個 Pod crash 掉時，底下的 ReplicaSet 會補出新的 Pod，盡量把總數維持在 2。
- Service 會根據 selector 找到目前符合條件的 Pods；如果有兩個可用 Pod，就會把流量分配到這兩個 Pod，若其中一個掛掉，流量就會先集中到剩下那個，等新 Pod 補上後再恢復到兩個後端。
- 在部署更新時，Deployment 會建立新的 ReplicaSet，讓新舊版本 Pod 逐步輪替，而不是一次全部砍掉重建。

### AI 修正與補充

- 主體已經答到位了，這題可以再收斂成三個專案內的實際價值，而不只講抽象的高可用。
- 第一，單 Pod 故障時不中斷：`replicas: 2` 讓這個 line-bot workload 不會因為單一 Pod crash 就整個沒有後端；ReplicaSet 會補新 Pod，Service 在這段期間至少還有另一個 Pod 可導流。
- 第二，Service 導流有彈性：`manifests/service.yaml` 透過 `selector.app=weamind` 選到符合條件的 Pods，**所以當後端有 2 個 Pod 時，Service / Endpoints 會對到兩個後端**；少一個時就縮成一個，新的 Pod 補上後又會回到兩個。這題的關鍵不是 Service 自己去算副本數，而是它依賴目前符合 selector 且 Ready 的後端清單。
- 第三，滾動更新不需要整批停機：因為 Deployment 是在更高層管理 ReplicaSet，更新 Pod template 時可以逐步增加新版本、逐步減少舊版本，而不是把兩個舊 Pod 一次全刪掉再重建。
- 你剛剛追問的「Service 是否能即時知道 Pod 掛掉」可以先用比較精準但不過度展開的說法回答：⭐️**Service 不是自己輪詢後端；執行期實際可導流的對象會反映在 Endpoints / EndpointSlice**，當 Pod 狀態與 readiness 改變後，這份後端清單會跟著更新。對今天這題來說，只要先記住 Service 依賴的是當下的後端清單，而不是寫死某兩個 Pod。
- 在 WeaMind 裡更完整的收斂說法是：`replicas: 2` 不只是「高可用」四個字，它實際同時支撐了單 Pod 故障時不中斷、Service 能對多個後端導流，以及部署更新時能平滑地在新舊版本之間切換。

## Q3

### 題目

為什麼 WeaMind 的 line-bot 應該掛在 Deployment，而不是直接手寫一個 Pod？

### 對照檔案

- `manifests/deployment.yaml`
- `references/docker-compose.prod.yml`
- `docs/WeaMind Infra核心架構.md`

### 使用者回答摘要

- 單獨運行一個 Pod 雖然可行，但缺乏自動化管理能力，更新、關閉與補救都會變得很手動。
- Deployment 透過 ReplicaSet 維持宣告的副本數，某個 Pod 掛掉時，會把數量補回目標值。
- Pod 應該被當成可替換的執行個體，而不是像 VM 一樣細心維護的固定單位。
- ⭐️在 Kubernetes 的整體模型裡，Service、Pods **與更高層控制器是連動的**；若只手寫一個裸 Pod，會脫離這種較穩定的管理方式。
- Deployment 最核心的價值包含**自動修復與滾動更新**。

### AI 修正與補充

- 這題的方向是對的，而且你已經抓到「Pod 不應是主要管理單位」這個核心。
- 第一，要把 `line-bot` 先定義成長期常駐的 Web app 服務，而不是一次性工作。對這種 workload 來說，重點不是把某一個 Pod 顧好，而是持續維持這個服務一直有足夠且可替換的執行個體。
- 第二，比較精準的說法是：Deployment 宣告期望狀態，Deployment 底下的 ReplicaSet 負責把 Pod 數量維持在目標值，而不是 Deployment 自己直接去重建某個舊 Pod。
- 第三，WeaMind 後面還要接 `Service`、`Ingress`、`readinessProbe`、`livenessProbe`；如果只手寫一個 Pod，雖然資源能跑起來，但會失去副本管理、滾動更新與較穩定的修復機制，整體會很脆弱。
- 在這個專案裡更好的收斂方式是：line-bot 是一個需要長期對外提供 webhook 服務的 app，因此應掛在 Deployment 上，讓 Kubernetes 以 Deployment → ReplicaSet → Pod 的層級去管理它，而不是把單一 Pod 當成穩定存在的單位。
- `workload` 這個詞在今天先做最小理解即可：它指的是「Kubernetes 裡要被執行與管理的應用工作負載」，像這裡的 line-bot 服務就是一種 workload。

## Q4

### 題目

`manifests/deployment.yaml` 沒有直接寫出 ReplicaSet 物件，但為什麼它仍然能支援自動修復與滾動更新？

### 拆題

1. 這份 YAML 直接宣告的，是 Deployment 自己的期望狀態，還是 ReplicaSet 自己的期望狀態？
2. repo 雖然沒手寫 ReplicaSet YAML，為什麼執行期還是會出現 ReplicaSet？
3. Pod template 變更時，Deployment 會怎麼讓新舊 ReplicaSet 一起參與更新？

### 對照檔案

- `manifests/deployment.yaml`
- `README.md`

### 使用者回答摘要

- 使用者目前對「哪一層的期望狀態」這句還不夠清楚，但知道 ReplicaSet 至少和 Pod 數量維持有關。
- 使用者理解 Deployment 在後端機制中整合了 ReplicaSet，因此即使沒手寫 ReplicaSet YAML，執行期仍會有這層控制。
- 使用者也知道 ReplicaSet 可以獨立被手寫成 YAML。
- 對滾動更新的理解方向是：Deployment 偵測到新版本後會建立新的 ReplicaSet，讓新舊 ReplicaSet 一起存在，最後新 ReplicaSet 升到目標副本數，舊 ReplicaSet 降為 0。

### AI 修正與補充

- 使用者對滾動更新與「執行期會有新舊 ReplicaSet 並存」的方向是對的。
- 這題的完整收斂應分成三層來講。
- 第一，`manifests/deployment.yaml` 直接宣告的是 Deployment 這一層的期望狀態：想要幾個副本、要用什麼 Pod template、更新時要如何替換，而不是直接手寫某個固定的 ReplicaSet 或 Pod。
- 第二，repo 雖然沒有手寫 ReplicaSet YAML，但 Deployment controller 會根據這份 Deployment 宣告，自動建立並管理對應的 ReplicaSet，所以執行期仍然會有 ReplicaSet 這層資源存在。
- 第三，當 Pod template 變更時，Deployment 會建立新的 ReplicaSet，舊的 ReplicaSet 不會立刻消失，而是新舊兩者一起參與 rollout；比較接近的實際行為是新 ReplicaSet 先逐步增加 Pod，舊 ReplicaSet 再逐步減少，最後新 ReplicaSet 達到目標副本數，舊 ReplicaSet 降為 0。
- 以 WeaMind 目前 `replicas: 2` 來看，你說的「可能先到 3 再回到 2」是合理的理解，這也比「先砍舊 Pod 再補新 Pod」更接近預設 rolling update 的方向，因為 Deployment 預設會盡量避免把可用副本一次降太低。
- 這題最終可以收斂成：雖然 YAML 沒有直接寫 ReplicaSet，但 Deployment 這個高層控制器會自動建立並管理 ReplicaSet；因此它既能靠 ReplicaSet 維持 Pod 數量達成自動修復，也能在 Pod template 更新時讓新舊 ReplicaSet 逐步交接，達成滾動更新。

### 狀態

- 已完成
