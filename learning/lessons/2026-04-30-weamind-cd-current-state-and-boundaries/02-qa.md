### AI 修正與補充

- 你的主幹是對的，第三小題也已經碰到核心。
- 第一小題要再講準一點：**不是單一一條 `CI` 做完所有事，而是 `CI` 先驗證，再由 `workflow_run` 觸發 `publish-ghcr` 做真正的 build-and-push。**
- 更精準地說，`CI` 先做品質檢查、型別檢查、測試與 Docker build validation；之後 `publish-ghcr.yml` 再 checkout `workflow_run.head_sha`，把 image push 到 `ghcr.io/kyomind/weamind`。
- 所以目前更準確的描述是：WeaMind 已有 **`CI` + image publishing**。
- 第二小題的主體也對：infra repo 的 [manifests/deployment.yaml](manifests/deployment.yaml) 確實直接引用 `ghcr.io/kyomind/weamind:latest`。
- 但 `imagePullPolicy: Always` 的邊界要收緊：**它只保證 Pod 在建立或重新建立時會重新拉取 image，不保證現有 Pod 會因 registry 裡的 `latest` 更新就自動換版。**
- 所以它不保證三件事：
  - registry 更新後，現有 Pod 會自動重拉
  - cluster 會自動 rollout
  - 重新 apply 同一份還是寫 `latest` 的 Deployment，就一定會換到新 image
- 你剛剛說「如果直接 apply 的話，還是會是最新版」這句要再收緊。
- 若重新 apply 時 **Pod template 沒有變化**，Kubernetes 不一定會重建 Pod；沒有新 Pod，就沒有重新 pull，也就不會保證吃到新的 `latest`。
- 第三小題你的方向是對的：現在缺的不是 artifact，也不是完全沒有 deployment config。
- 真正缺的是：**artifact 產出後，沒有一條被正式定義好的鏈路，把版本變更帶到 deployment config，再把這個 config 可靠地套進 deployment state。**
- 再對回 WeaMind 現況，infra repo 雖然有 deployment config，但現在只寫 `latest`，所以 Git 裡沒有明確記錄 cluster 想跑的正式版本。
- 所以目前缺的其實是兩段：**artifact -> deployment config version update**，以及 **deployment config -> cluster rollout / state update**。
- 最短版可收成：WeaMind 已有 `CI` 與 image publishing，但 `Deployment` 目前只追 `latest`，而 `imagePullPolicy: Always` 不會讓現有 Pod 因 registry 更新而自動換版。
- 所以它還不能算完整 `CD`；真正缺的是把明確版本更新到 deployment config，並再把這個 config 正式套進 cluster state 的最後一跳。

## Q2

### 題目

若今天要替 WeaMind 收斂正式 deploy source，infra repo 應該追哪一種版本？請說明為什麼不應繼續追 `latest`，也不要把完整 release version、minor、major tag 混成同一件事。

### 答題引導

1. 先說目前 WeaMind 已知有哪些 image tag 類型，以及它們各自比較像什麼用途。
2. 再比較 `latest`、完整 release version、minor、major tag 在可追溯性、回滾與溝通上的差異。
3. 最後收斂一句：第一版正式 deploy source 應該追哪種版本，為什麼。

### 對照檔案

- references/phase2/w8-cd-minimum-spec.md
- docs/WeaMind實作CD討論與實踐.md
- references/weamind-ci-to-k8s-flow.md

### 使用者回答摘要

- 使用者先抓到目前已知的三類 tag：`latest`、`sha-<short_sha>`、release version tag。
- 使用者也抓到一個相關方向：不同 tag 的變動頻率不同，而越完整的版本通常更適合精準溝通。
- 使用者目前的主結論是對的：第一版正式 deploy source 應該追完整 release version，也就是同時包含 major、minor、patch。
- 目前還需要再收緊兩點：`sha` 和 release version 的用途差異；minor / major 為什麼不能當正式 deploy source。

### AI 修正與補充

- 你的主結論是對的：**第一版正式 deploy source 應該追完整 release version。**
- 先收第一小題。WeaMind 目前已知至少有三類 tag：
  - `latest`
  - `sha-<short_sha>`
  - release version tag
- 但這裡要再講準一點：release version tag 裡面還要分 **完整版本**、minor、major。
- 第二小題你抓到一個重要方向：顆粒度越細，通常越容易溝通。
- 不過更關鍵的不是「變動頻率小」本身，而是 **它是不是 ⭐️immutable、可追溯、可回滾。**
- `latest` 的問題最明顯：它是 mutable tag。
- 也就是說，今天的 `latest` 和明天的 `latest` 可能不是同一個內容。
- 所以它不適合拿來當正式 deploy source，因為 Git 很難清楚記錄「環境到底採用了哪個正式版本」。
- `sha-<short_sha>` 比 `latest` 好，因為它能指回某個具體 commit。
- 但它比較像工程內部識別，**適合 debug 與追 build 來源，不是最適合人類溝通的正式 release version。**
- release version 之中，也不是 major、minor、patch 都一樣穩。
- 真正嚴格 immutable 的，只有 **完整 release version**，例如 `1.1.2`。
- minor tag 像 `1.1`，之後可能會前移到 `1.1.3`、`1.1.4`。
- major tag 像 `1`，之後也會一路前移。
- 所以 major 與 minor 雖然比 `latest` 更有語意，但它們仍然不是最穩的正式 deploy source。
- 若把這題壓成最短版，可以這樣回答：WeaMind 目前已知有 `latest`、`sha-<short_sha>` 和 release version tag。
- `latest` 太模糊又會漂移；`sha` 可追 commit，但比較像 debug / build 識別；major 與 minor 雖有版本語意，但仍會前移。
- 所以第一版正式 deploy source 應該追 **完整 release version**，因為它最可追溯、最好溝通，也最容易回滾。

## Q3

### 題目

請把 WeaMind 的 app repo 與 infra repo 責任邊界切清楚，並提出明天 implement 前最合理的最小方向。回答時請特別說明，為什麼第一版不建議讓 app repo 直接拿 cluster credentials 去改叢集。

### 答題引導

1. 先分開說 app repo 應負責哪些事，infra repo 又應負責哪些事。
2. 再描述一條從正式 release image，到 infra repo version state，再到 deploy decision 的最小鏈路。
3. 最後補一句：這條方向為什麼比「image push 完就直接改 cluster」更穩，也更適合 WeaMind 目前階段。

### 對照檔案

- references/phase2/w8-cd-minimum-spec.md
- docs/WeaMind實作CD討論與實踐.md
- references/weamind-ci-to-k8s-flow.md
- manifests/deployment.yaml

### 使用者回答摘要

- 使用者已先抓到 Q3 的主幹：app repo 偏向 app / artifact，infra repo 偏向部署規格與環境宣告。
- 使用者也明確提出一條合理的最小方向：只有完整 release tag 更新時，才進入第一版 `CD` 鏈路。
- 使用者也抓到 app repo 影響邊界應該先停在「對 infra repo 提交版本變更」，而不是直接進 cluster。
- 在 review 與 deploy 這一段，使用者也已經碰到核心：infra repo 合併後，還需要自己的 deploy 機制，不能把 app repo 的 `CI` 直接延伸成 cluster 變更。

### AI 修正與補充

- 你的主線是對的，而且整體方向已經很接近 W8 想收斂的第一版方案。
- 第一小題先收責任邊界：**app repo 負責 app 版本與 artifact；infra repo 負責 deployment config 與環境要採用哪個版本。**
- 你說「app repo 負責 app 的規格，infra repo 負責部署的規格」方向是對的，只是可以再講得更準一點：
- app repo 應負責 build image、publish image、定義什麼是正式可部署版本。
- infra repo 應負責宣告 cluster 目前要跑哪個版本、保存 deployment state 的 Git 歷史，以及決定何時把這個版本套進 cluster。
- 第二小題你提出「只有完整 release tag 更新時才觸發第一版 CD」，這個方向是對的。
- 但更準確的理由不是「非 release tag 的變動太小」，而是：**只有完整 release version 才被定義成正式可部署版本。**
- 也就是說，main push 產出的 `latest` 與 `sha` 仍有價值，但它們屬於持續交付中的快速版本，不自動進入正式 deploy source。
- 所以你這條最小鏈路可以收成：
  - app repo 發佈完整 release
  - release workflow push 正式版本 image
  - app repo 對 infra repo 提交 Deployment image version 的變更
  - 先經過 review / merge，再由 infra repo 自己決定怎麼 deploy
- 第三小題你也抓到關鍵了：**app repo 的影響邊界先停在 infra repo PR，這樣比較符合分工與權限邊界。**
- 這裡你問到人工 review 要怎麼放，我會先給第一版最穩的答案：**review 就落在 infra repo PR。**
- 也就是 app repo release 成功後，自動開 PR 到 infra repo；PR 只更新 Deployment image 的完整 release version。
- review / merge 之後，要不要立刻 deploy，才交給 infra repo 這一側的 automation 決定。
- 這樣做的好處是：
  - app repo 不直接持有 cluster credentials
  - deployment state 仍由 infra repo 的 Git 歷史保存
  - 版本採用與 deploy decision 不會混在 app CI 裡
- 至於你說「那 infra repo 合併後也還需要自己的 CI/CD」，這個判斷是對的。
- 因為合併 infra repo 只是 Git 狀態更新，不等於 cluster 已經更新。
- 所以第一版最穩的收法通常是兩段：
  - app repo release 後自動開 PR 到 infra repo
  - infra repo merge 後，再由人工或 infra-side workflow 去 apply / deploy
- 最後一題你回答「不要讓 app repo 直接改 cluster，因為這違反分工跟權限」，這個方向完全正確。
- 再講得更精準一點：**app repo 直接拿 cluster credentials，會把 artifact 產出責任和 deployment state 控制權混在一起。**
- 這會讓 repo 邊界變模糊，也會讓 production 版本採用的決策不再清楚落在 infra repo。
- 若把這題壓成最短版，可以這樣回答：app repo 應負責 build / publish image，並定義正式 release；infra repo 應負責宣告 cluster 要跑哪個版本，保存 deployment state，並決定何時 deploy。第一版最合理的方向，是只有完整 release version 進入 CD 鏈路，由 app repo release 成功後自動開 PR 到 infra repo，先經 review / merge，再由 infra repo 自己決定 deploy。這比 app repo 直接拿 cluster credentials 改叢集更穩，因為它保住了 repo 邊界、權限分工與 deployment state 的 Git 可追溯性。
