### AI 修正與補充

- 你的主幹是對的，第三小題也已經碰到核心。
- 第一小題要再講準一點：**不是單一一條 `CI` 做完所有事，而是 `CI` 先驗證，再由 `workflow_run` 觸發 `publish-ghcr` 做真正的 build-and-push。**
- 更精準地說，`CI` 先做品質檢查、型別檢查、測試與 Docker build validation；之後 `publish-ghcr.yml` 再 checkout `workflow_run.head_sha`，把 image push 到 `ghcr.io/kyomind/weamind`。
- 所以目前更準確的描述是：WeaMind 已有 **`CI` + image publishing**。
- 第二小題的主體也對：infra repo 的 [manifests/deployment.yaml](manifests/deployment.yaml) 確實直接引用 `ghcr.io/kyomind/weamind:latest`。
- 但 `imagePullPolicy: Always` 的邊界要收緊：**它只保證 Pod 在建立或重新建立時會重新拉取 image，不保證現有 Pod 會因 registry 裡的 `latest` 更新就自動換版。**
- 所以它不保證三件事：
  - registry 更新後，現有 Pod 會自動重拉
  - cluster 會自動 rollout
  - 重新 apply 同一份還是寫 `latest` 的 Deployment，就一定會換到新 image
- 你剛剛說「如果直接 apply 的話，還是會是最新版」這句要再收緊。
- 若重新 apply 時 **Pod template 沒有變化**，Kubernetes 不一定會重建 Pod；沒有新 Pod，就沒有重新 pull，也就不會保證吃到新的 `latest`。
- 第三小題你的方向是對的：現在缺的不是 artifact，也不是完全沒有 deployment config。
- 真正缺的是：**artifact 產出後，沒有一條被正式定義好的鏈路，把版本變更帶到 deployment config，再把這個 config 可靠地套進 deployment state。**
- 再對回 WeaMind 現況，infra repo 雖然有 deployment config，但現在只寫 `latest`，所以 Git 裡沒有明確記錄 cluster 想跑的正式版本。
- 所以目前缺的其實是兩段：**artifact -> deployment config version update**，以及 **deployment config -> cluster rollout / state update**。
- 最短版可收成：WeaMind 已有 `CI` 與 image publishing，但 `Deployment` 目前只追 `latest`，而 `imagePullPolicy: Always` 不會讓現有 Pod 因 registry 更新而自動換版。
- 所以它還不能算完整 `CD`；真正缺的是把明確版本更新到 deployment config，並再把這個 config 正式套進 cluster state 的最後一跳。
