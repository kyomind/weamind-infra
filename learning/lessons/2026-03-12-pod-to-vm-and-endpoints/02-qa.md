## Q1

### 題目

在 WeaMind 這個專案裡，line-bot Pod 如果要連 PostgreSQL 和 Redis，它實際上會連到哪裡？這個答案你可以從哪些 repo 檔案直接看出來？

### 對照檔案

- `manifests/configmap.yaml`
- `manifests/deployment.yaml`
- `docs/WeaMind Infra核心架構.md`

### 使用者回答摘要

- 先看 `Deployment` 時，無法直接看到 PostgreSQL / Redis 的位址資訊。
- 進一步看 `ConfigMap`，可找到 `POSTGRES_HOST`、`POSTGRES_PORT`、`POSTGRES_DB`、`POSTGRES_USER` 與 `REDIS_URL` 等環境變數。
- 目前判斷 Pod 內 app 能連到 PostgreSQL / Redis，主要是因為容器載入了 `ConfigMap` 內的環境變數；K8s 版與單機版的值可能不同，但 app 讀取的 key 應維持一致。
- 目前回答重點放在 `ConfigMap` 是哪裡提供連線資訊。

### AI 修正與補充

- 這題的核心答案是：line-bot Pod 不是連 K8s 內的 Service 名稱，也不是連某個 Pod IP，而是直接連原 VM 的內網 IP。
- 依 `ConfigMap` 可直接看出 PostgreSQL 連到 `10.0.0.2:5433`，Redis 連到 `redis://10.0.0.2:6379/0`。
- 你的判斷方向是對的，但更精準的說法是：`manifests/configmap.yaml` 負責提供「連到哪裡」的值，`manifests/deployment.yaml` 則用 `envFrom` 證明這些值會被注入容器。
- `docs/WeaMind Infra核心架構.md` 進一步補強了為什麼會這樣設定：這個 repo 是 K8s + VM 混合架構，只有 line-bot 在 K8s，PostgreSQL / Redis 仍留在原 VM。
- 所以這題若要用一句面試式回答收斂，應該是：line-bot Pod 透過 `Deployment` 注入的 `ConfigMap` 環境變數，直接連到原 VM 的內網 IP 上的 PostgreSQL 與 Redis，而不是連 cluster 內的 Service。

## Q2

### 題目

為什麼這個專案沒有把 PostgreSQL / Redis 也搬進 K8s，或至少包成 cluster 內的 Service 名稱給 app 連？

### 對照檔案

- `docs/WeaMind Infra核心架構.md`
- `README.md`
- `manifests/configmap.yaml`

### 使用者回答摘要

- PostgreSQL 與 Redis 都帶有明顯的 stateful 特性，不像 app Pod 那樣偏向無狀態、較適合直接多副本部署。
- 雖然 Kubernetes 可以用 StatefulSet 處理這類工作負載，但一旦把資料層搬進 cluster，整體部署與維運複雜度會顯著上升。
- 因此本專案選擇把資料層留在 VM，只把 line-bot 搬進 Kubernetes，比較符合務實做法。
- 從 production 經驗來看，資料庫通常也常交給專門的資料庫服務處理，而不是自己在 cluster 內重建一套高可用資料層。

### AI 修正與補充

- 你的主方向是對的，但這題若要更貼近 repo，核心理由應先回到「這是一個 K8s + VM 混合架構，而且這次遷移的範圍本來就只有應用層」。
- `README.md` 與 `docs/WeaMind Infra核心架構.md` 都明確寫到：line-bot 在 K8s，PostgreSQL / Redis 保留在原 VM；這不是漏做，而是刻意的架構決策。
- 所以第一層答案不是只有「DB 很 stateful」，而是「為了控制遷移範圍、維持資料層穩定性，先只把 line-bot 搬到 K8s」。
- 第二層才是你提到的原因：如果把 PostgreSQL / Redis 也搬進 K8s，會引入 Stateful workload 的部署、儲存、備份、故障切換與維運複雜度，對這個專案目前的規模與目標不划算。
- 至於「為什麼不至少包成 cluster 內的 Service 名稱」，更準確的說法是：因為 PostgreSQL / Redis 根本不在 cluster 裡，這個 repo 直接把原 VM 內網 IP 寫進 `ConfigMap`，讓 Pod 透過 private network 直接連外部 VM；這樣設計更直白，也更符合現在的混合架構。
- 所以這題的面試式收斂可以講成：WeaMind 這次只遷移應用層，不遷移資料層；PostgreSQL / Redis 保留在原 VM，是為了把資料層穩定性放在優先位置，避免在目前規模下引入不必要的 Stateful 維運複雜度，因此 app 直接走 VM 內網 IP，而不是改包成 cluster 內的 Service。

## Q3

### 題目

`weamind-line-bot` Service、Endpoints、Pods 三者在這個專案裡各自代表什麼？如果我想最快確認 Service 後面到底有沒有健康 Pod，最該看哪個？

### 拆題

- Service 最接近哪個角色？
- Endpoints 最接近哪個意思？
- 如果想最快確認 Service 後面到底有沒有健康 Pod，第一眼最該看哪個？

### 對照檔案

- `manifests/service.yaml`
- `manifests/deployment.yaml`
- `docs/LINE-Webhook-切換流程.md`

### 使用者回答摘要

- Service 被理解成穩定入口，會把流量導向符合 selector 的 Pod，這一點回答正確。
- 對 Endpoints 的理解目前還不穩，但傾向認為它代表 Service 目前實際對到的 Pod IP 或 Pod 清單。
- 如果要最快確認 Service 後面有沒有健康 Pod，會先看 `kubectl get endpoints weamind-line-bot`，因為健康 Pod 是動態狀態，不能只看 YAML。

### AI 修正與補充

- 你的 Q3-1 與 Q3-3 都答對了，真正需要補的是 Endpoints 的精確意思。
- 在這個專案裡，Pod 是實際跑 `line-bot` 容器的執行單位；`Deployment` 會維持這些 Pod 的副本數，`Service` 則提供一個穩定的 cluster 內入口，把流量轉給符合 selector 的 Pod。
- Endpoints 可以把它理解成「⭐️Service 在**執行期實際對到哪些後端位址**」。在這個專案裡，最常看到的就是被 `weamind-line-bot` Service ⭐️**選到的 Pod IP 與對應 port**。
- 所以 Endpoints 不是另外一個獨立服務，也不是 YAML 裡手寫的固定清單，而是 Kubernetes 根據 Service selector 與 Pod 狀態**動態整理**出來的**後端對照結果**。
- 也因此，如果 `kubectl get endpoints weamind-line-bot` 有內容，代表這個 Service 後面**目前至少有可導流的 Pod**；如果是空的，⭐️就表示 selector **沒選到** Pod，或 Pod **還沒進入可提供流量的狀態**。
- 這就是為什麼 `docs/LINE-Webhook-切換流程.md` 會把 `kubectl -n weamind get endpoints weamind-line-bot` 列成切換前必看的檢查項：它比只看 Service YAML 更接近「現在流量到底能不能打到 app」。
- 這題的面試式收斂可以講成：Pod 是實際跑 app 的單位，Service 是穩定入口，Endpoints 是 Service 目前實際對到的後端 Pod IP/port 清單；如果我要最快確認 Service 後面有沒有可接流量的 Pod，第一眼會看 Endpoints。

## Q4

### 題目

如果今天 `kubectl get endpoints weamind-line-bot` 是空的，你第一輪會先查哪幾件事？如果 Endpoints 正常，但 app 還是連不到 PostgreSQL / Redis，又該切到哪條排查路徑？

### 拆題

- 如果 Endpoints 是空的，第一輪最該先查哪一層？
- 如果 Endpoints 正常，但 app 還是連不到 PostgreSQL / Redis，這兩件事之間是什麼關係？
- 在這種情況下，排查應該切到哪一條路徑？

### 對照檔案

- `manifests/service.yaml`
- `manifests/deployment.yaml`
- `manifests/configmap.yaml`
- `docs/LINE-Webhook-切換流程.md`

### 使用者回答摘要

- 如果 `kubectl get endpoints weamind-line-bot` 是空的，先判斷目前沒有對到 Pod；**可能是 selector 沒選到，也可能是 Pod 沒有正常運作**。
- 第一輪會先回頭看 Service selector 是否正確，再用 `kubectl get pods` 之類的方式確認 Pod 是否真的在運作。
- 對第二段問題目前不太確定，但直覺上認為 Endpoints 正常與 app 連不到 PostgreSQL / Redis 應該不是同一層問題；後者比較像 `Deployment` / `ConfigMap` 或 app 自己的連線設定問題。

### AI 修正與補充

- 你的前半段方向是對的。若 Endpoints 是空的，第一輪就是先查 cluster 內的 `Service → selector → Pods` 這條路，而不是先查 VM 上的 PostgreSQL / Redis。
- ⭐️在這個專案裡，最先要核對的是 `manifests/service.yaml` 的 selector 是否真的對得到 `Deployment` 建出來的 Pod labels；再來看 Pod 是否 Running / Ready，因為 Pod 沒 Ready，也可能讓 Service 後面沒有可導流的 Endpoints。
- `docs/LINE-Webhook-切換流程.md` 也把 `kubectl get pods`、`kubectl logs`、`kubectl get endpoints weamind-line-bot` 放在同一輪排查裡，這代表第一輪目標是先確認流量有沒有進到 app，而不是先跳去查資料庫。
- 你後半段的直覺也對：如果 Endpoints 正常，但 app 還是連不到 PostgreSQL / Redis，這通常不是同一層問題。Endpoints 正常，代表 `Service → Pod` 這段大致成立；接下來要切去查的是 `Pod → VM` 這條路。
- 也就是說，Endpoints 在這裡的價值是幫你「切問題」：它不能證明資料庫一定連得上，但它能幫你排除掉一大段 cluster 內轉送問題。
- 切到 `Pod → VM` 路徑後，第一輪應看 `manifests/configmap.yaml` 的 `POSTGRES_HOST`、`POSTGRES_PORT`、`REDIS_URL` 是否正確，`manifests/deployment.yaml` 是否真的把這些值注入容器，然後再看 app logs 是否出現資料庫或 Redis 連線錯誤。
- 所以這題的面試式收斂可以講成：如果 Endpoints 是空的，我先查 Service selector、Pod labels 與 Pod Ready 狀態，因為這是 cluster 內流量還沒接起來的訊號；如果 Endpoints 正常但 app 還是連不到 PostgreSQL / Redis，就代表問題要切到 `Pod → VM` 路徑，去查環境變數、應用設定與對外連線，而不是繼續卡在 Service / Endpoints。
