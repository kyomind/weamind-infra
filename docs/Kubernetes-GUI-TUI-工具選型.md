# Kubernetes GUI / TUI 工具選型

## 文件目的

這份文件整理目前在 WeaMind 學習與實作脈絡下，對 Kubernetes GUI / TUI 工具的選擇與思考。

這不是單純列工具名單，而是要回答三個問題：

1. 目前最適合用哪一組工具
2. 為什麼選它們
3. 其他看起來也合理的工具，為什麼暫時不選

## 目前結論

在目前這個階段，主力組合是：

1. k9s：TUI 主力
2. Headlamp Desktop：GUI 輔助

這個組合的核心前提是：

1. 目前需求偏向觀察、理解、排查
2. 暫時不需要重型管理平台能力
3. 不想為了 GUI 再把一整套額外元件部署進 cluster
4. 希望工具能直接搭配現有 kubeconfig 與 SSH tunnel 工作流

更白話地說，目前要的是：

1. 快速看 cluster 狀態
2. 更清楚看資源關係
3. 不要為了 GUI 再引入過多維運成本

## 選型原則

這次選型不是看哪個工具最有名，而是用下面幾個標準來判斷。

| 評估面向   | 這次的判斷標準                                         |
| ---------- | ------------------------------------------------------ |
| 操作模式   | 優先選擇直接使用本機 kubeconfig 的工具                 |
| 部署成本   | 優先避免需要在 cluster 內額外部署一整套 UI             |
| 學習價值   | 工具應該幫助理解 Kubernetes，而不是遮蔽它              |
| 日常實用性 | 工具要能直接支援看 Pod、Deployment、Node、Logs、Events |
| 維護風險   | 優先選擇仍在維護、方向清楚的工具                       |
| 複雜度     | 現階段避免過早引入平台級或商業化較重的工具             |

## 為什麼是 k9s + Headlamp Desktop

### k9s 的角色

k9s 是目前最適合當主力 TUI 的工具。

原因很直接：

1. 它很快
2. 直接吃 kubeconfig
3. 非常貼近排查場景
4. 不需要在 cluster 裡安裝任何東西

對目前學習節奏來說，k9s 最有價值的地方不是炫，而是它剛好覆蓋高頻操作：

1. 看 Pod 狀態
2. 看 Deployment 與 ReplicaSet
3. 看 Node 狀態
4. 看 Events
5. 進 Logs
6. 做快速切換與定位

它很適合遠端 K3s 這種情境，因為本質上仍然是 terminal-first 的工作流。

### Headlamp Desktop 的角色

Headlamp Desktop 是目前比較合理的 GUI 補充。

它適合的位置不是取代 k9s，而是補上下面幾種需求：

1. 想更直觀地看資源關係
2. 想更舒服地看 YAML
3. 想用 GUI 協助理解 Deployment、ReplicaSet、Pod 的關聯
4. 想保留一個輕量 GUI，但不想回到 in-cluster dashboard 的舊模式

它最大的優勢是：

1. 可以直接用本機 kubeconfig
2. 不一定要部署進 cluster
3. 不需要額外暴露入口
4. 比較符合現在 client-side GUI 的方向

## 核心比較表

下面這張表是目前這次決策最重要的部分。

| 工具                 | 類型              | 目前定位                  | 優點                                                    | 缺點                                                                | 目前結論 |
| -------------------- | ----------------- | ------------------------- | ------------------------------------------------------- | ------------------------------------------------------------------- | -------- |
| k9s                  | TUI               | 主力                      | 快、輕、直接、排查導向、不需部署到 cluster              | 對新手來說關係視覺化較弱                                            | 選用     |
| Headlamp Desktop     | GUI               | 輔助                      | 吃 kubeconfig、較現代、視覺化較好、不需 in-cluster 安裝 | 仍是輔助，不應取代 kubectl / k9s                                    | 選用     |
| Kubernetes Dashboard | GUI               | 過渡型學習工具            | 可以快速體驗傳統 browser dashboard 模式                 | 已封存、不再維護、要額外部署元件、要處理 token / RBAC / access path | 不選     |
| Lens                 | GUI               | 功能很完整的桌面工具      | 體驗成熟、功能很多、整合度高                            | 偏重、偏產品化、對目前學習節奏略過頭                                | 暫不選   |
| Rancher              | GUI / 平台        | 多 cluster / 平台治理工具 | 能力完整、適合平台管理                                  | 太重、超出目前需求、維運成本高                                      | 暫不選   |
| Prometheus + Grafana | Observability GUI | 指標與趨勢層              | 看時間序列、趨勢、告警，是真正 observability 主力       | 不是用來取代日常資源瀏覽工具                                        | 後續補上 |

## 為什麼不選 Kubernetes Dashboard

這個工具不是完全不能用，而是它已經不適合當新的長期選擇。

原因如下：

| 面向     | 問題                                                          |
| -------- | ------------------------------------------------------------- |
| 維護狀態 | 專案已在 2026-01-21 封存，進入 read-only                      |
| 生態方向 | 官方文件已明示 deprecated / unmaintained，並引導改看 Headlamp |
| 部署方式 | 必須在 cluster 內額外部署多個元件                             |
| 存取方式 | 需要處理 token、RBAC、port-forward 或額外入口                 |
| 長期價值 | 對學習一次流程有幫助，但不值得當長期主力                      |

這次實際裝過一次之後，更能感受到它為什麼像上一代思路。

它的問題不是不能打開，而是整個使用模式偏向：

1. 先在 cluster 裡架一套 Web UI
2. 再想辦法做認證與入口
3. 最後才開始看資源

這種路線在今天的單人 / 小型 cluster 情境下，通常不如直接使用 desktop client 或 TUI 實際。

## 為什麼不選 Lens

Lens 不是差，而是目前需求不需要它這麼重。

| 面向 | 判斷                                                 |
| ---- | ---------------------------------------------------- |
| 功能 | 很完整，甚至可以說偏豪華                             |
| 體驗 | 整體成熟，桌面感強                                   |
| 缺點 | 對目前需求而言偏重、偏產品化                         |
| 風險 | 容易太早把注意力放到工具體驗，而不是 Kubernetes 本質 |

如果未來需求變成：

1. 想要更強的桌面整合感
2. 願意接受較重的 GUI 工具
3. 更在意圖形化操作體驗

那 Lens 仍然可以重新評估。

但就目前來看，它不是最好的第一順位。

## 為什麼不選 Rancher

Rancher 的問題不是功能不夠，而是它解的問題層級太高。

| 面向         | 判斷                                  |
| ------------ | ------------------------------------- |
| 適用場景     | 多 cluster 管理、平台治理、團隊化環境 |
| 對目前的幫助 | 有限，因為目前並不是在建平台          |
| 成本         | 部署與維護成本都明顯偏高              |
| 結論         | 對目前單一 K3s 學習環境太重           |

現在的問題是如何看懂 cluster 與資源，而不是如何搭一個平台層入口。

## 為什麼 Prometheus + Grafana 不被歸在同一層比較

這組工具很重要，但它解的不是完全相同的問題。

| 類別               | 回答的問題                                                      |
| ------------------ | --------------------------------------------------------------- |
| GUI / TUI 資源工具 | 現在有哪些 Pod、Deployment、Node、Events、Logs 狀態如何         |
| Observability 工具 | 最近一段時間 CPU、memory、latency、error rate、restart 趨勢如何 |

所以它不是 Kubernetes Dashboard、Headlamp、Lens 的直接替代品。

比較精準的說法是：

1. k9s / Headlamp 用來看資源與即時狀態
2. Prometheus + Grafana 用來看時間序列、趨勢與告警

因此它應該被列為後續補強，而不是這次 GUI / TUI 二選一的一部分。

## 建議的工具分工

### 現在這個階段

| 目標                 | 工具             |
| -------------------- | ---------------- |
| 快速看 cluster 狀態  | k9s              |
| 看資源關係與 YAML    | Headlamp Desktop |
| 基本操作與排查基本功 | kubectl          |

### 接下來可補的工具

| 目標             | 工具                 |
| ---------------- | -------------------- |
| 多 Pod logs 聚合 | stern                |
| 指標、趨勢、告警 | Prometheus + Grafana |

## 簡化決策表

如果只想用一句話決定：

| 情境                              | 建議                                  |
| --------------------------------- | ------------------------------------- |
| 想要最快的日常觀察工具            | k9s                                   |
| 想要一個輕量 GUI 幫助理解         | Headlamp Desktop                      |
| 想要完整平台管理                  | 目前先不要走這條路                    |
| 想要瀏覽器型 in-cluster dashboard | 目前不建議再投資 Kubernetes Dashboard |

## 最終定案

在目前的 WeaMind 學習與實作階段，較合理的組合是：

1. k9s 作為 TUI 主力
2. Headlamp Desktop 作為 GUI 輔助
3. kubectl 持續作為基本功主軸
4. 之後再補 stern、Prometheus、Grafana

這個選擇的重點不只是工具本身，而是它背後的方向：

1. 保持 cluster 乾淨
2. 減少為了 GUI 額外引入部署成本
3. 工具服務於理解與排查，而不是掩蓋 Kubernetes 的本質
4. 先選擇對現在需求最合身的工具，而不是最重或最完整的工具
