## Q1

### 題目

如果你只看 `manifests/deployment.yaml`，你會怎麼解釋 WeaMind 的 readiness probe 與 liveness probe 雖然都打 `/health`，但它們的用途與失敗後行為其實不同？

### 對照檔案

- `manifests/deployment.yaml`
- `manifests/service.yaml`

### 使用者回答摘要

- readiness probe 主要在判斷 Pod 是否已準備好接收流量；就算 container 還活著，也可能因為尚未就緒而不該接流量。
- liveness probe 主要在判斷 Pod 背後的 container 是否已壞到需要重啟；即使 process 還在，也可能因內部狀態卡死而被判定不健康。
- readiness probe 失敗時，使用者理解為該 Pod 暫時不應再被導流；liveness probe 失敗時，使用者理解為 kubelet 會重啟 container。
- 使用者能說出 `initialDelaySeconds` 是首次檢查前的等待時間，並理解 liveness 比 readiness 更晚，是為了避免 app 還在啟動時就被過早判定為失敗。
- 使用者額外追問：既然 readiness probe 與 liveness probe 都打同一個 `/health` 端點，Kubernetes 是怎麼分辨這次失敗該算 readiness fail 還是 liveness fail。

### AI 修正與補充

- 主骨架是對的，現在只需要把兩三個說法再修得更精準。
- 第一，readiness probe 判斷的不是「Pod 有沒有活著」，而是「這個 Pod 現在是否該被放進可接流量的後端清單」。因此它失敗時，最直接的後果不是重啟，而是 Pod 的 Ready 狀態會變成 False，接著從 Service 對應的 Endpoints / EndpointSlice 可導流清單裡被移除。
- 第二，liveness probe 判斷的是「container 是否已經壞到不該繼續撐著跑」。它失敗時，kubelet 會依照 restart policy 對 container 做重啟；比較精準的說法是重啟 container，而不是把整個 Pod 物件刪掉重建。
- 第三，你對 `initialDelaySeconds` 的理解方向正確。這份 YAML 裡 readiness 比較早開始，是因為系統想先知道這個 Pod 什麼時候可以開始接流量；liveness 比較晚開始，則是刻意給應用更多啟動緩衝，避免在還沒完全穩定前就被當成壞掉而誤殺。
- 你最後那個問題很關鍵，答案是：Kubernetes 不是靠 `/health` 的回應內容去猜這是 readiness 還是 liveness，而是 kubelet 本來就分別執行兩組不同的 probe 設定。也就是說，同樣都是打 `/health`，但「這次請求是 readiness probe 發出的」還是「這次請求是 liveness probe 發出的」，是由 kubelet 自己的 probe 狀態機決定的。
- 換句話說，語意不在 `/health` 回傳 JSON 或文字裡，而在探針設定本身。若同一個 `/health` 回了非 2xx / 3xx、timeout 或連線失敗，readiness 那組檢查就會把 Pod 標成 NotReady；liveness 那組檢查則會累積失敗次數，達到條件後觸發 container restart。
- 這也代表同一個端點可以同時被兩種 probe 使用，但風險是兩者會被綁得很緊。若 `/health` 只要稍微出問題就同時讓 readiness 與 liveness 都失敗，那這個端點實際上同時承擔了「停止導流」和「觸發重啟」兩種責任。對簡單 app 可以接受，但對較複雜服務，常會把 readiness 與 liveness 拆成不同判斷邏輯，避免過度耦合。
- 這題在 WeaMind 裡可以先收斂成：兩個 probe 雖然都打 `/health`，但 readiness 負責決定 Pod 是否接流量，liveness 負責決定 container 是否要被重啟；差異來自 kubelet 對兩組 probe 設定的不同處理，而不是來自應用額外回傳不同型別的回應。

## Q2

### 題目

`nodeSelector.nodepool=worker` 在 WeaMind 這個架構裡扮演什麼角色？如果這個限制拿掉，最少要擔心哪一類問題？

### 對照檔案

- `manifests/deployment.yaml`
- `README.md`
- `docs/WeaMind Infra核心架構.md`

### 使用者回答摘要

- 使用者理解 `nodeSelector` 的作用，是把 Pod 可被排程的 node 範圍限制在符合指定條件的機器上。
- 使用者已抓到 WeaMind 這裡設定 `nodepool=worker` 的主要目的，是避免 scheduler 把 line-bot 這類實際應用 workload 排到 control-plane 上，導致 control-plane 也承擔 app 負載，進而增加穩定性風險。
- 使用者目前仍有兩個追問：第一，Kubernetes 怎麼知道哪些 node 是 worker、哪些是 control-plane；第二，`nodepool` 這個 key 是否只是其中一種標法，還有沒有更典型的 label 範例。

### AI 修正與補充

- 主方向是對的，而且你已經抓到這題真正的核心不是「功能會不會完全壞掉」，而是「角色邊界與穩定性是否還可控」。
- 第一，`nodeSelector` 不是直接告訴 kubelet 怎麼跑 container，而是 Pod 對 scheduler 提出的 node label 篩選條件。更精準的說法是：scheduler 在可選節點裡，只能挑出 labels 符合這組 key/value 的 node。
- 第二，WeaMind 這裡把 line-bot 固定到 worker，是在落實 README 裡的 control-plane / worker 分工。control-plane 主要承擔 API Server 等叢集控制職責，worker 才是預期用來承載 app Pods 的地方。即使某些環境技術上允許 Pod 跑到 control-plane，這個專案仍希望把應用負載和控制面責任分開，降低資源競爭與角色混雜的風險。
- 第三，所以把這個限制拿掉後，風險通常不是「整個 app 一定立刻不能跑」，而是 scheduler 的選擇邊界變鬆。若 control-plane 也可被排程，app workload 就可能和叢集控制元件搶 CPU、記憶體，之後碰到資源壓力、除錯或擴充時，整體穩定性會更難控。
- 你追問的「Kubernetes 怎麼知道誰是 worker、誰是 control-plane」要分兩層看。對 control-plane 而言，Kubernetes 常見會在 node 上放內建角色 labels，例如 `node-role.kubernetes.io/control-plane`，也常搭配 taint 來避免一般 Pods 被排上去。對 worker 而言，`worker` 並不是 Kubernetes 自帶的一個神奇身分；像這份 YAML 用的 `nodepool=worker`，通常是叢集管理者另外加在 node 上的自訂 label。
- 這也解釋了你為什麼不記得在這個 app repo 裡加過 `worker` label：因為那不是寫在 Deployment YAML 裡，而是寫在 cluster 的 node 物件上，常見做法是在建置或維運時用 `kubectl label nodes <node-name> nodepool=worker` 之類的方式加上去。
- 而且這件事在 repo 內其實有留下痕跡，不是我憑空猜的：`PROGRESS.md` 明確記了「對 worker 節點加上 label（`nodepool=worker`），並於 Deployment 加入 `nodeSelector`」。所以至少從專案文件來看，`nodepool=worker` 的確是這個專案曾經手動補上的 node label，而不是 Kubernetes 自動送你的固定欄位。
- `nodepool` 本身不是唯一或最典型的 key，它只是這個專案選用的一個自訂 label 名稱。更常見的例子包含自訂的 `disktype=ssd`、`nodepool=worker`、`dedicated=ingress`，或 Kubernetes 內建 labels，像 `kubernetes.io/arch=amd64`、`topology.kubernetes.io/zone=...`。重點不是 key 叫什麼，而是 Pod 的 `nodeSelector` 要和 node 上實際存在的 labels 對得起來。
- 另外，`PROGRESS.md` 也補了一個很有價值的背景：這個專案在 K3s 裡觀察到 worker 節點的 `ROLES` 顯示為 `<none>` 是正常的。這剛好說明了「worker」這個概念不一定會直接以內建 role 欄位出現；因此若你想把 workload 固定在 worker，額外補一個像 `nodepool=worker` 這樣的自訂 label，就變成很合理的做法。
- 這題在 WeaMind 裡可以先收斂成：`nodeSelector.nodepool=worker` 是 Pod 對 scheduler 提出的 node 篩選條件，目的是把 line-bot workload 固定在 worker，避免 control-plane 同時背叢集控制與 app 負載；拿掉後不一定立刻壞，但角色邊界、資源隔離與穩定性都會變得比較難控。
