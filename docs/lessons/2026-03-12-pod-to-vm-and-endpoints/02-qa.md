## Q1

### 題目

在 WeaMind 這個專案裡，line-bot Pod 如果要連 PostgreSQL 和 Redis，它實際上會連到哪裡？這個答案你可以從哪些 repo 檔案直接看出來？

### 對照檔案

- `manifests/configmap.yaml`
- `manifests/deployment.yaml`
- `docs/WeaMind Infra核心架構.md`

### 使用者回答摘要

- 先看 `Deployment` 時，無法直接看到 PostgreSQL / Redis 的位址資訊。
- 進一步看 `ConfigMap`，可找到 `POSTGRES_HOST`、`POSTGRES_PORT`、`POSTGRES_DB`、`POSTGRES_USER` 與 `REDIS_URL` 等環境變數。
- 目前判斷 Pod 內 app 能連到 PostgreSQL / Redis，主要是因為容器載入了 `ConfigMap` 內的環境變數；K8s 版與單機版的值可能不同，但 app 讀取的 key 應維持一致。
- 目前回答重點放在 `ConfigMap` 是哪裡提供連線資訊。

### AI 修正與補充

- 這題的核心答案是：line-bot Pod 不是連 K8s 內的 Service 名稱，也不是連某個 Pod IP，而是直接連原 VM 的內網 IP。
- 依 `ConfigMap` 可直接看出 PostgreSQL 連到 `10.0.0.2:5433`，Redis 連到 `redis://10.0.0.2:6379/0`。
- 你的判斷方向是對的，但更精準的說法是：`manifests/configmap.yaml` 負責提供「連到哪裡」的值，`manifests/deployment.yaml` 則用 `envFrom` 證明這些值會被注入容器。
- `docs/WeaMind Infra核心架構.md` 進一步補強了為什麼會這樣設定：這個 repo 是 K8s + VM 混合架構，只有 line-bot 在 K8s，PostgreSQL / Redis 仍留在原 VM。
- 所以這題若要用一句面試式回答收斂，應該是：line-bot Pod 透過 `Deployment` 注入的 `ConfigMap` 環境變數，直接連到原 VM 的內網 IP 上的 PostgreSQL 與 Redis，而不是連 cluster 內的 Service。

## Q2

### 題目

為什麼這個專案沒有把 PostgreSQL / Redis 也搬進 K8s，或至少包成 cluster 內的 Service 名稱給 app 連？

### 對照檔案

- `docs/WeaMind Infra核心架構.md`
- `README.md`
- `manifests/configmap.yaml`

### 使用者回答摘要

- PostgreSQL 與 Redis 都帶有明顯的 stateful 特性，不像 app Pod 那樣偏向無狀態、較適合直接多副本部署。
- 雖然 Kubernetes 可以用 StatefulSet 處理這類工作負載，但一旦把資料層搬進 cluster，整體部署與維運複雜度會顯著上升。
- 因此本專案選擇把資料層留在 VM，只把 line-bot 搬進 Kubernetes，比較符合務實做法。
- 從 production 經驗來看，資料庫通常也常交給專門的資料庫服務處理，而不是自己在 cluster 內重建一套高可用資料層。

### AI 修正與補充

- 你的主方向是對的，但這題若要更貼近 repo，核心理由應先回到「這是一個 K8s + VM 混合架構，而且這次遷移的範圍本來就只有應用層」。
- `README.md` 與 `docs/WeaMind Infra核心架構.md` 都明確寫到：line-bot 在 K8s，PostgreSQL / Redis 保留在原 VM；這不是漏做，而是刻意的架構決策。
- 所以第一層答案不是只有「DB 很 stateful」，而是「為了控制遷移範圍、維持資料層穩定性，先只把 line-bot 搬到 K8s」。
- 第二層才是你提到的原因：如果把 PostgreSQL / Redis 也搬進 K8s，會引入 Stateful workload 的部署、儲存、備份、故障切換與維運複雜度，對這個專案目前的規模與目標不划算。
- 至於「為什麼不至少包成 cluster 內的 Service 名稱」，更準確的說法是：因為 PostgreSQL / Redis 根本不在 cluster 裡，這個 repo 直接把原 VM 內網 IP 寫進 `ConfigMap`，讓 Pod 透過 private network 直接連外部 VM；這樣設計更直白，也更符合現在的混合架構。
- 所以這題的面試式收斂可以講成：WeaMind 這次只遷移應用層，不遷移資料層；PostgreSQL / Redis 保留在原 VM，是為了把資料層穩定性放在優先位置，避免在目前規模下引入不必要的 Stateful 維運複雜度，因此 app 直接走 VM 內網 IP，而不是改包成 cluster 內的 Service。
